## Context
Definitions (evaluators, personas, metric definitions, rubrics, pricing catalogs, test profiles) are edited over time. Runs must point at exactly the definition they used, forever. Benchmark suites (MVP-2) need immutable, checksummed versions. Phase 2 primary keys depend on this decision. Schema versioning (ADR 0008) is about the *shape* of data; entity versioning is about the *content* of one logical object.

## Decision
1. **`VersionedEntity`** extends EntityBase with `version: int >= 1` and `content_digest: ContentDigest` (ADR 0006).
2. **Identity.** A logical object keeps one `id` across edits. Each edit creates a new record with the same `id` and `version + 1`. `(id, version)` is immutable: its content, digest, `created_at` and `metadata` never change after creation.
3. **The digest is verified on load.** If `content_digest` does not match the recomputed digest, the record is rejected. (Revision 11, N20 decided by the owner, option A: the Evaluator's digest is computed over its domain without `test_profile.content_digest` (ADR 0006 Decision 5), so the Evaluator and a snapshot embedding it both still verify after a shared export drops or keys the profile digest; the Evaluator digest then pins the profile only by `test_profile.id` and `version`, not by its content.)
4. **References** to a versioned entity are JSON objects `{id, version, content_digest?}`, never strings. A reference without a version is not allowed. Whether the digest is required depends on the kind of reference (revision 9: E5 decided by the owner; this replaces the revision 3 sentence "a reference's digest may be absent only where ADR 0006 Decision 6 requires dropping it"):
   - **References between definitions may omit the digest.** These are `PersonaRef`, `MetricDefinitionRef` and `MetricBindingRef` (used by `Evaluator.persona`, `Evaluator.metric_bindings`, `MetricBinding.metric`, `RubricItem.binding` and `VerdictCheck.metric_ref`), and later references between definitions by the same rule. When the digest is present, it is verified against the resolved entity (I7). A mismatch is rejected, and a keyed digest that cannot be verified is never reported as matching (Decision 7).
   - **Rationale (E5).** The run snapshot embeds each referenced record and verifies it. A ConfigSnapshot embeds the Evaluator, Persona, MetricDefinitions, MetricBindings and Rubric themselves (ADR 0006 Decision 1). Each embedded record carries its own `content_digest`, which is verified on load (Decision 3), and the embedded digests are inside the snapshot digest (ADR 0006 Decision 5). A bundle cannot hold two contents under one `(id, version)` (I6). Inside a run, `(id, version)` therefore already names exactly one verified content, and a digest copied onto the reference would add no check. Outside a run, for example in a definition library, it would only add a field to keep in step on every edit. When an author wants to pin content across stores, they can still write the digest, and it is verified.
   - **`TestProfileRef` and `PricingCatalogRef` keep their own rules.** These references are not between definitions. They point at content that a snapshot does not embed: the profile is never embedded because it holds personal data, and the catalog is referenced rather than copied. A snapshot can verify such content only through the digest on the reference. `TestProfileRef.content_digest` is required and plain inside internal data, and is dropped or keyed in shared exports (ADR 0006 Decision 6). `PricingCatalogRef.content_digest` is always required (ADR 0006 Decision 1; revision 11, N26: renamed from `digest`, so every reference carries its digest under the one name that the bundle seam of Decision 7 reads).
   - Each referenced kind has a typed reference value object `<Entity>Ref`, a subclass of `VersionedRef` whose `id` is the typed ID of that kind (revision 8; ADR 0001 I14).
   - **Metric definitions have no semver.** A metric definition's version is this integer `version`. "key@version" (for example `p95_latency@3`) is display text only (`render_metric_ref()`), never stored and never parsed. A key does not identify a definition, because two definitions may share it.
5. **Which entities are versioned (accepted in revision 3):** Persona, TestProfile, Evaluator, MetricDefinition, MetricBinding, Rubric, PricingCatalog, AgentTarget, Dataset.
   - **Dataset membership (revision 11, N25 decided by the owner):** a Dataset version lists its members in `item_ids` (ordered, unique), so membership is inside the version's digest and immutable with it; adding or removing an item is a new Dataset version. A DatasetItem names no dataset, so one item may belong to several datasets and versions.
   - **Records of fact and their run (revision 11, N22 decided by the owner):** apart from `UsageRecord.run_id`, a record of fact does not name its run. A run's records are the records of its RunBundle (P1-14), and the rules "unique per run" and "of the same run" are bundle-level `check_*` functions over those records.
   - **Digested records of fact (not versioned, but carry `content_digest`):** ConfigSnapshot.
   - **Records of fact (not versioned):** Project, Run, Artifact, Transcript, Turn, Exchange, ToolCallEvent, StageSpan, MetricResult, RunVerdict, DatasetItem, UsageRecord, CostRecord, CostSummary, RunBundle, ExportBundle. They are written once and superseded only by new records with new IDs. A bundle that holds two different contents under one record-of-fact ID is rejected. (This is also how a privacy marker that is too loose is corrected: by a new record, never by editing the old one, ADR 0016 Decision 5.)
   - **PriceEntry** is a value object inside the `(id, version)` of its PricingCatalog (revision 15, N47 decided by the owner, option A; until revision 14 an entity with prefix `pce`) and is immutable with it. **Identity across catalog versions (P-24):** an entry unchanged between two catalog versions keeps its `entry_key`; a changed entry gets a new key. `CostRecord.pricing_snapshot` always names the catalog `(catalog_id, version)` and the `entry_keys`, which are meaningful only with that reference. (Revision 16, decided by the owner: the identifier is `entry_key: MachineKey`, N61 option B; P-24 is checked by the pure function `pricing.check_catalog_succession(previous, next)`, N47 remainder option A, ADR 0014 Decision 10a, test `test_entry_identifier_stable_across_catalog_versions`; enforcement at a publication step is later work. What counts as an unchanged entry is open, N65.) **Revision 17 (N65 decided, auto-approved, as recommended):** an entry is unchanged when every field except `entry_key`, `provenance` and `effective_to` is equal, so a key survives a re-checked price page and the closing of its range; `check_catalog_succession` requires the same catalog `id` and a later `version` (ADR 0014 Decision 10a). **Revision 18 (N72 decided, auto-approved, option A):** `applies_when` and `aliases` are compared as sets, so reordering them is no change; an entry's `aliases` hold no repeat and never its own `model` (ADR 0014 Decisions 10a, 11).
   - **Detected capabilities (P-23):** AgentTarget is versioned for its declared fields only. Capabilities detected during a run are recorded on that Run (`available_inputs`, plus `Run.detected_capabilities`), never written back into AgentTarget.
6. Phase 2 keys versioned tables on `(id, version)` and records-of-fact tables on `id`.
7. **Bundle consistency seam (revision 7).** The bundle rules of Decisions 2-5 are implemented in P1-05 as `bundle.check_bundle_consistency(docs, refs)` over JSON-mode documents, so they are testable before `RunBundle`/`ExportBundle` exist; P1-14 calls it. A reference's digest is compared with the resolved entity's `content_digest` only when the schemes are equal and either both are plain or both are keyed with an equal `key_ref` (same key, same content, same HMAC). Otherwise the comparison needs a key and is not made by this function: P1-14 verifies such a reference through `verify_digest()` with a key resolver, and a reference that cannot be verified is never reported as matching. (Revision 11: wherever the seam recomputes a digest, it uses the entity's own domain, which for an Evaluator excludes `test_profile.content_digest`, ADR 0006 Decision 5; and a `PricingCatalogRef` is read through `content_digest` like every other reference, N26.) **Revision 22 (P1-14, B10, B11; api-surface 25.5):** the signature is `check_bundle_consistency(docs, refs=(), *, require_resolved=False)`. With the default every earlier behaviour is unchanged (a reference to an `(id, version)` that no document holds is not an error). With `require_resolved=True` (keyword-only) such a reference raises `UnresolvedReferenceError` (a `BundleError`) naming the ID and version; a resolved reference still has its digest compared. `RunBundle` requires resolution for each result's `metric` and each verdict check's `metric_ref` against the snapshot's definitions, and verifies, when the target is embedded, the evaluator's `TestProfileRef`, the snapshot's `PricingCatalogRef` and each computed cost record's `pricing_snapshot` read as `{id: catalog_id, version, content_digest}`. A record of fact listed twice with identical content passes the seam (it merges sources) and is `[duplicate]` in a bundle (B2); two contents under one ID are `ConflictingRecordError`. A digest that cannot be compared without a key is accepted by the bundle models and never reported as verified; `verify_bundle_digests(bundle, key_resolver)` is deferred (B11). Rescoring (N33): a RunBundle holds one result per metric `(id, version)`; a rescoring is a new RunBundle (B5).

## Rejected alternatives
- **A new ID per version.** The logical identity is lost ("all versions of this evaluator" needs a separate lineage table), and dashboards cannot group across edits.
- **Mutable rows with an audit log.** Reproducibility then depends on replaying the log correctly. Snapshots pointing at a mutable row can silently change meaning.
- **Semver strings for entity versions.** Users editing a persona cannot meaningfully classify a change as minor or major. A monotonic integer is unambiguous and sorts correctly.
- **Content-addressed IDs only (the ID is the digest).** Identity then changes on every edit. A digest of low-entropy PII would also become the primary key, spreading it into every foreign key.
- **Version without a digest.** A store or import could reuse `(id, version)` for different content, and nothing would detect it. (This concerns the versioned record itself, which always carries a verified digest. It is not an argument for a digest on every reference: see Decision 4.)
- **(Revision 9, E5) A required digest on every reference between definitions.** It repeats a check that the snapshot already makes on the embedded record. Every edit of a persona or a binding would also force edits of every referring definition, only to update a copied hash.
- **Versioning records of fact.** A run or a result describes something that happened; editing it would rewrite history. Corrections are new records.

## Consequences
- Editing creates rows instead of updating them. Storage grows with edits, which is intended (auditability).
- Retention deletion of a TestProfile deletes all its versions. Snapshots keep only the reference, so they stay valid but cannot be resolved; the reader must report "unresolvable reference", not fail.
- A bundle may contain several versions of one entity, but never two different contents under one `(id, version)`.

## Decided items (formerly [Proposed]; all decided by the user in revision 5)
- **P-23. AgentTarget detected capabilities. Decided by the user (revision 5): accepted as recommended.** Decision: AgentTarget is versioned for its declared fields only; capabilities detected during a run are recorded on that Run (`available_inputs`, plus `detected_capabilities` if needed), never written back into AgentTarget. The field `Run.detected_capabilities` (named in Decision 5) was **accepted by the user in revision 6**. Reason: the plan says capabilities are auto-detected after the first run; if they lived on a versioned AgentTarget, every run that detects something would create a new version, and snapshots would point at versions that differ only by observations. Had it been decided otherwise: AgentTarget keeps a detected-capabilities field, and each detection is a new version; `test_declared_vs_detected_capabilities_separate` then checks the version bump instead.
- **P-24. PriceEntry identity across catalog versions. Decided by the user (revision 5): accepted as recommended.** Decision: an entry that is unchanged between two catalog versions keeps its `pce_` ID (revision 15: its entry identifier, since `PriceEntry` is a value object, N47; revision 16: its `entry_key`, N61); a changed entry gets a new ID. `CostRecord.pricing_snapshot` always names `(catalog_id, version, entry_keys)` (`entry_ids` until revision 15), so resolution is unambiguous either way. Reason: stable IDs let reports show "same price as before" without comparing contents. Had it been decided otherwise (new IDs per catalog version): nothing in cost computation changes; only cross-version comparison needs content comparison.
