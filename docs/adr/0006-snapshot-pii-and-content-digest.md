## Context
`Run.config_snapshot` must freeze everything that determines a run's result (evaluator, persona, metric definitions, bindings, rubric, pricing) so the run can be reproduced and audited. Test profiles hold caller identity for verification flows (names, dates of birth, account numbers), which is PII. Snapshots are copied into bundles and exports, so PII inside a snapshot leaks wherever the snapshot goes. Integrity also needs a content digest that any implementation can reproduce bit-for-bit. A plain digest of low-entropy personal data is itself a leak: anyone holding it can confirm guesses offline.

## Decision
1. **ConfigSnapshot** (entity `snap`, ADR 0001) is frozen and JCS-digested. It embeds Evaluator, Persona, MetricDefinitions, MetricBindings and Rubric. It holds only references for PII-bearing or large external content:
   - `TestProfileRef{id, version, content_digest: ContentDigest?}`. It never holds profile fields.
   - `PricingCatalogRef{id, version, content_digest: ContentDigest}` (the digest is required; revision 11, N26 decided by the owner: the field was named `digest` until revision 10 and is renamed `content_digest`, the name of every other reference's digest, so the bundle consistency seam of ADR 0009 Decision 7 compares it like the others). The same name applies to `CostRecord.pricing_snapshot.content_digest` (revision 12, O6 decided by the owner, ADR 0014 Decision 12).
2. **PII marking.** TestProfile fields that hold PII carry the JSON Schema annotation `x-pii: true`. A schema walk over ConfigSnapshot (recursively, including embedded entities) must find zero `x-pii` fields.
3. **ContentDigest** is a value object (no ID): `{scheme, value, key_ref?}` (P-18: the reserved field is named `key_ref`, not `salt_ref`, because for the keyed scheme it names a secret key, and a salt is public by definition; if a salted scheme is ever registered it gets its own separate `salt` field).
   - `scheme` comes from a **scheme registry**. 0.0.1 registers exactly two schemes:
     - `sha256-jcs/v1`: plain SHA-256 over the RFC 8785 (JCS) canonical UTF-8 JSON. `key_ref` MUST be absent.
     - `hmac-sha256-jcs/v1` (accepted in revision 3 to make the "key" option of user decision 2 usable; registered in 0.0.1 by user decision P-18): HMAC-SHA-256 over the same JCS bytes. `key_ref` is required and is a `KeyRef` naming the HMAC key. The key is resolved outside the schema and is never present in any export, bundle or snapshot, in any form.
   - `value` is 64 lowercase hex characters for both schemes.
   - An unknown scheme raises a typed error. It is never treated as "unverifiable, accept".
   - Further salted or keyed schemes can be registered later as additive (minor) changes; a salted scheme would add its own optional `salt` field, which is also additive.
4. **One verification entry point.** `verify_digest(obj, digest, *, key_resolver=None)` is the only function that checks digests. It dispatches on the scheme. For a keyed scheme without a resolver, or when the resolver cannot supply the key, it raises the typed `DigestKeyUnavailable`; it never reports success. No other code computes and compares digests itself. HMAC uses the stdlib `hmac` module (no new runtime dependency). **Return contract (revision 7):** `verify_digest` returns `None` on a match and raises otherwise (`DigestMismatch`, `UnknownDigestScheme`, `DigestKeyUnavailable`, `NonIJsonValueError`); it never returns a boolean, so a forgotten check cannot read as success. The key question is settled before any content is hashed. **Resolver failures never echo (revision 21, S-N91, option A; revision 30, P1-21 finding C3a):** when the key resolver raises or returns something other than `bytes`, the `DigestKeyUnavailable` message names the failure kind only, never the `key_id`, `key_version` or `provider_hint` (revision 30 reverses the revision 21 reading that the message names the `key_id`: a key id can itself be sensitive, and a pasted key in it would be echoed); the resolver's exception text, arguments and class name are never put in the message (a key manager client can raise with a key path, a token or key bytes, and generic error handlers log the message). The resolver's exception is chained (`raise ... from exc`), so an operator who logs the chain still finds the reason; the chain is the resolver's own responsibility. Rejected: dropping the chain (`from None`; loses the reason for operators); keeping `repr(exc)` (echoes secrets). **Key length (revision 30, P1-21 finding m1):** a key for `hmac-sha256-jcs/v1` has at least 32 bytes (the HMAC-SHA-256 output size), in `compute_digest` and for the key a resolver returns; a shorter key raises `WeakDigestKeyError`, a class that derives from both `ValueError` and `DigestKeyUnavailable`, whose message says `at least 32 bytes` and names the scheme, never key material or the key id. On the verify side it is raised before any content is hashed, so a weak key is never a `DigestMismatch`.
5. **The digest domain (accepted in revision 3).** The digest covers the entity's canonical JSON (`mode="json"`, by alias) with (a) the `content_digest` field removed, (b) `schema_version` removed, and (c) fields whose value is `null` omitted. Lists and empty lists are kept. Removing `schema_version` and nulls keeps the digest stable when a later minor version adds optional fields, so an `(id, version)` keeps one digest across schema upgrades (ADR 0009). **ConfigSnapshot domain (P-17, user decision):** every `TestProfileRef` inside a ConfigSnapshot contributes only `{id, version}` to the snapshot digest; its `content_digest` is excluded. The profile digest is recorded separately, in `TestProfileRef.content_digest`, for internal runs. A shared export can therefore drop or key the profile digest and the recipient can still verify the snapshot digest, and the snapshot digest cannot be used to confirm a guessed profile. **Evaluator domain (revision 11, N20 decided by the owner, option A):** the Evaluator's own `content_digest` domain also excludes `test_profile.content_digest` (an entity-specific exclusion at that one path, `evaluator.evaluator_digest_domain(doc)`), so that both the embedded evaluator's digest and the snapshot digest survive dropping or keying the profile digest; the evaluator digest therefore no longer proves which profile content was used, while `test_profile.id` and `version` still pin the profile version and the reference's own digest (internal data) and the TestProfile's verified digest pin its content. The profile digest itself is checked against the resolved profile where one is present (`test_ref_digest_must_match_resolved_entity_in_bundle`).
   **Depth (revision 7).** The generic domain is defined on the JSON document alone, so a verifier in any language can compute it without our models: (a) and (b) remove `content_digest` and `schema_version` **at the top level only**; (c) removes every object member whose value is `null` **at every depth**, including inside user `metadata`; `null` elements of arrays are kept (positions matter). Removing `schema_version` by key name at every depth would also delete user metadata keys of that name, so deeper exclusions are declared per entity at paths named by its schema: P-17 (above), the Evaluator's `test_profile.content_digest` (revision 11, N20, above) and, new in revision 7, the `schema_version` of every entity embedded in a ConfigSnapshot (Evaluator, Persona, MetricDefinitions, MetricBindings, Rubric), so the snapshot digest stays stable across schema upgrades as the reason above intends (implemented in P1-12, test `test_snapshot_digest_ignores_embedded_schema_version`). Embedded `content_digest` values stay in the domain, because they pin the exact versions used. **PricingCatalog domain (revision 15, N47 decided by the owner, option A):** the catalog uses the generic domain with no entity-specific exclusion. Its entries are value objects (ADR 0014 Decision 11) with no `schema_version`, `created_at` or `metadata` of their own, so the digest covers the catalog's own fields and every field of every entry (price, billing rules, conditions, validity, aliases, provenance, entry identifier), and it stays stable across schema upgrades without a nested exclusion. Before revision 15 qa's reading embedded entries as entities, whose nested `schema_version` would have changed the catalog digest across schema versions (api-surface 23.3 N47). "The digest covers prices and rules only" in the owner's decision is read as "no per-entry entity fields"; provenance and the identifier stay inside the digest, because altering them under one `(id, version)` must be detected (detail D4, api-surface 23.6). Documented consequence: inside `metadata` a member with value `null` and an absent member have the same digest. pydantic's `exclude_none` is not a substitute for (c), because it keeps nulls inside dict values (verified on pydantic 2.14.1).
6. **Where each scheme may be used (user decision 2).**
   - **Internal** (snapshots, runs, internal RunBundles, ExportBundle with `purpose=internal`): `TestProfileRef.content_digest` is required and uses `sha256-jcs/v1` (user decision OQ5).
   - **Shared** (ExportBundle with `purpose ∈ {shared_export, benchmark}`): every `TestProfileRef.content_digest`, and the digest of any other profile holding personal data, is either **dropped** (absent) or **keyed** (`hmac-sha256-jcs/v1`, key not in the export). A plain digest there is a validation error.
   - **Sealed payloads**: the `plaintext_digest` of a sealed profile is dropped or keyed under the same rule (ADR 0015).
   - The known limitation remains for internal data: a plain digest of a low-entropy profile (for example a 10-digit phone number plus a date of birth) can be brute-forced offline by anyone who holds an internal snapshot. `SCHEMA_POLICY.md` must state this, and must state that shared exports never carry such a plain digest.
7. **Portable exports** that must carry the profile itself use `SealedPayload` (ADR 0015), only in an explicit ExportBundle.
8. **Where the rules of Decisions 6 and 7 are checked (revision 22, P1-14, B9, B16).** A `RunBundle` is purpose-neutral: it verifies a `TestProfileRef` digest against an embedded `TestProfile` of the same `(id, version)` when both digests can be compared (`RefDigestMismatchError`), and accepts a plain, keyed or absent reference digest. The purpose rules belong to the `ExportBundle`: `internal` requires a plain digest on every snapshot's `TestProfileRef` (`snapshot.check_internal_snapshot`; absent or keyed is `[profile_digest]`) and may embed `TestProfile` entities in `RunBundle.test_profiles`; `shared_export` and `benchmark` reject a present digest whose scheme is not `hmac-sha256-jcs/v1` (`[profile_digest]`, naming the reference, never the digest value; A-30) and any embedded `TestProfile` in the clear (`[profile]`): such an export carries a profile only as a sealed `test_profile` payload whose subject is a `TestProfileRef` of a snapshot of the export. The snapshot and Evaluator digests exclude the profile reference digest (P-17, N20), so the recipient still verifies them after the drop (`test_shared_export_snapshot_digest_verifies_after_profile_digest_dropped`).
8. A transport `user_id` (possibly a phone number) never enters a snapshot or export. It lives only in a privacy-marked `Run.caller_external_id` (ADR 0016, P-43).
9. **Profile values in free text are placeholders (P-16, user decision).** Evaluator instructions and ScriptedTurn text refer to test-profile values only through placeholders of the form `{{profile.<field>}}` (for example `{{profile.name}}`, `{{profile.dob}}`), where `<field>` is a TestProfile field name; a placeholder naming no TestProfile field is rejected. Placeholders are stored unresolved in the Evaluator and the snapshot and are filled at run time from the referenced profile; the resolved text is never written into a snapshot. Any other `{{...}}` text is ordinary text, and placeholder-like text inside observed data (turn text, tool arguments) is data and is never resolved (A-02). A pure lint `lint_profile_values_in_free_text(snapshot, profile) -> list[IngestWarning]` warns (code `profile_value_in_free_text`, with the path but never the value) when free text in the snapshot contains a literal value equal to a field of the referenced profile. **Limitation (stated in `SCHEMA_POLICY.md`):** the lint can only find values of the profile it is given; personal data typed into free text that is not in any profile (for example a real person's name used as an example) cannot be detected and remains the author's responsibility.
9a. **Exact grammar and matching (revision 8, batch 2 item 10; `docs/phase1/api-surface.md` section 19.4).**
   - **Placeholder.** Exactly `{{profile.` + FIELD + `}}`, with FIELD matching `[a-z][a-z0-9_]*` and no white space inside, matched left to right without overlap. FIELD must be a `profile_placeholder_fields()` name, otherwise the text is rejected and the message names FIELD. (Revision 14, owner decision on the placeholder message: inside a model that hides its input, which every model holding such text now is, the message gives the field location and the rule ("unknown profile placeholder field", with the known fields) and not the FIELD the user typed, because it is part of the user's text; ADR 0007 Decision 8 (c). Outside a hiding model it still names FIELD.)
   - **Malformed, rejected** (the message gives the well-formed spelling): any `{{`, optional white space, `profile` in any letter case, optional white space, `.` that does not start a well-formed placeholder. Examples: `{{ profile.name }}`, `{{Profile.name}}`, `{{profile.}}`, `{{profile.name}`, and nested paths such as `{{profile.name.first}}`, since no profile field is structured.
   - **Ordinary text.** Everything else, for example `{{customer}}`, `{{ profile }}`, `{{}}`, `{profile.name}`. The grammar is ASCII and no Unicode normalization is applied to find placeholders.
   - **Where.** Profile placeholders may appear in four places:
     - `Evaluator.instructions` and `ScriptedTurn.text` (P-16);
     - `Evaluator.expected_outcome` and every string value at any depth of `ExpectedToolCall.arguments` (E7, decided by the owner in revision 9).
     The same grammar, unknown-field rule, malformed-placeholder rule and `test_profile` requirement apply in all four. Object keys, numbers, booleans and nulls inside `arguments` are never placeholder-checked, so a numeric argument cannot hold a profile value; that is the stated limitation of E7. At run time the expected outcome is resolved before it fills the reserved prompt variable `expected_outcome` (ADR 0013 Decision 2), and expected arguments are resolved before they are compared with the observed `ToolCallEvent.arguments` (ADR 0010 Decision 8). The resolved text is never written into a snapshot or a result. Placeholder-like text inside observed data stays data (A-02).
   - **A profile is required.** An Evaluator containing any profile placeholder must reference a `test_profile`, because otherwise nothing could fill it.
   - **Lint matching** (`find_literal_profile_values`, which `lint_profile_values_in_free_text` builds on):
     - Every string leaf of the JSON-mode dump is compared with every non-empty profile data value, after folding both sides: NFC, `str.casefold()`, NFC, every decimal digit (general category Nd) mapped to its ASCII digit, and every run of white space collapsed to one space. The stored text is never changed.
     - A hit needs token bounds. Where the value's first (last) code point is a letter, mark or digit (categories L, M, N), the code point before (after) it must be absent or outside L, M and N.
     - There is no length threshold, so no field is skipped. Token bounds keep a short value from matching inside words, IDs and digests.
     - One hit is reported per (path, field), sorted by path and then field in UTF-16 code-unit order, without the value.
     - Folding catches values retyped in another case, in native digits (an account number in Devanagari digits) or with other spacing. The fold uses the running Python's Unicode database, so hits may differ for very new characters. This is acceptable for a warning.
     - `SCHEMA_POLICY.md` adds two limitations: another format of the same value (a date written differently) and a part of a value (a first name alone) are not found.

## Rejected alternatives
- **Embed the TestProfile in the snapshot.** It copies PII into every run, bundle and export, and makes deletion on retention expiry impossible without rewriting immutable snapshots.
- **Reference by ID only (no digest), everywhere.** If the profile is edited in place, or a different store holds a different profile under the same ID, an internal snapshot cannot detect it, so reproducibility is unverifiable. (In shared exports the digest may be dropped because the recipient has no profile to compare it with.)
- **A bare hex string digest.** The algorithm cannot be changed later without ambiguity, and there is nowhere to put a key reference.
- **Python `json.dumps(sort_keys=True)` as the canonical form.** Its float formatting, Unicode escaping and separators are Python-specific, so a TypeScript or Go verifier would compute different bytes. JCS is a standard with cross-language implementations.
- **Salted/keyed digest for internal snapshots in 0.0.1.** Rejected by the user (OQ5). The registry keeps it available as an additive change.
- **Plain digests in shared exports.** Anyone holding the export could confirm a guessed profile offline; for low-entropy identity data that is a disclosure (user decision 2).
- **A salt stored next to the digest in the export.** A salt that travels with the digest slows brute force only by the cost of one extra input; the guess space stays small. A key kept out of the export removes the offline attack.
- **Accept unknown schemes and skip verification.** An attacker could downgrade integrity checking by writing `"scheme": "none"`.

## Consequences
- JCS requires I-JSON. Integers beyond 2^53 and non-finite floats cannot be digested. Digested entities must not contain them, and the `rfc8785` library raises if they do.
- Floats inside digested entities (pass-rule range bounds, confidences) are serialized with the ECMAScript shortest round-trip form. Python `float.__repr__` matches it for finite values, and the golden test pins this.
- Free-text fields embedded in the snapshot (Evaluator `instructions` and `expected_outcome`, ScriptedTurn text, string values of expected tool-call arguments) can still contain PII that a user typed instead of a placeholder. The `x-pii` walk cannot see it; the Decision 9 lint catches it only for values of the referenced profile.
- Producing a shared export means rewriting digests (drop or key), so an export is a transformation, not a copy, of internal data. The export builder is Phase 2+; Phase 1 provides the validators.
- Phase 2 can index internal snapshots by `content_digest.value` to deduplicate them.

## Decided items (revision 11)
- **N20. The embedded Evaluator's digest and the profile digest. Decided by the owner (revision 11): option A.** Found by qa while writing the batch 3 tests (`docs/phase1/api-surface.md` section 22.3): the snapshot domain excluded `evaluator.test_profile.content_digest`, but the embedded Evaluator's own digest still covered it and stayed inside the snapshot domain, so dropping or keying the profile digest broke the evaluator's own check and, through it, the snapshot digest. The Evaluator's domain now excludes `test_profile.content_digest` as well (Decision 5). Rejected: (B) moving the profile reference from the Evaluator to the snapshot, which changes the accepted Evaluator shape and still leaves a library Evaluator carrying the plain digest; (C) allowing only keyed profile digests in shared exports, which removes the drop option of user decision 2. Consequence: an internal and a shared copy of one Evaluator `(id, version)` have equal digests while their JSON differs only in that path; the bundle seam compares versioned records by digest (ADR 0009 Decision 7), so they are not two contents. Test: I20a.
- **N26. `PricingCatalogRef.digest` renamed `content_digest`. Decided by the owner (revision 11).** Decision 1. The bundle seam and every reader now find a reference's digest under one name. Test: I16 (`test_pricing_catalog_ref_digest_verified`, which qa updates for the new name).
