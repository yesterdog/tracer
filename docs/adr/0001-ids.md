## Context
Every entity carries an `id`. IDs are used as primary keys (Phase 2, Postgres and SQLite), in logs, in exported bundles, and in references between entities (for example `RunVerdict.checks[].binding_id`). They must index well, sort roughly by creation time, be readable in logs, and make it hard to put an ID of the wrong kind into a field. External systems (Pipecat, Langfuse, VoicEra, providers) bring their own identifiers, often bare UUIDv4 values or opaque strings. Those must never be taken as our identity.

## Decision
1. **Value.** Every ID is a UUIDv7 (RFC 9562). In Python it is stored natively as `uuid.UUID`. The typed ID class exposes the `uuid.UUID` as the attribute `.uuid` (revision 7); it is neither a `str` nor a `uuid.UUID` subclass, and it never equals its wire string.
2. **Wire form.** `<prefix>_<uuid>`: a lowercase prefix, an underscore, then the canonical lowercase hyphenated UUID text. The version nibble must be `7` and the variant bits must be `10xx`. JSON, logs and exports use only this form.
3. **Typed per kind.** Each entity kind has its own ID type and its own JSON Schema `pattern` (for example `^run_[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`). A `run_` ID in an `evl_` field is rejected by both pydantic and JSON Schema.
4. **Prefix registry (complete; accepted in revision 3).** Every entity, meaning everything that has its own identity and is referenced by ID or stored on its own, has exactly one prefix:

   **Confusable pairs in the frozen table (corrected in revision 7).** Two prefixes are *confusable* when their Levenshtein distance is 1 or one is an anagram of the other (the same letters in a different order). The frozen 0.0.1 table contains exactly five confusable pairs: four one-edit pairs, `run`/`rub`, `exc`/`exp`, `dts`/`dti` and `agt`/`art`, and one anagram pair, `tsc`/`cst`. Revisions 3-6 named only the first three. `agt`/`art` (both original) and `tsc`/`cst` (`tsc` was introduced in revision 3 to replace `trn`) were missed. All five stay as frozen, because typed IDs reject a swapped prefix in pydantic and in JSON Schema, so the pairs harm only log readability. `test_frozen_registry_confusable_pairs_are_the_known_five` pins exactly this set, so no sixth pair can enter.

   **Rule for new prefixes (P-03, stated precisely in revision 7):** a prefix added after the freeze must be 2-6 lowercase ASCII letters (`^[a-z]{2,6}$`), must not already be registered, and must not be confusable with any registered prefix: Levenshtein distance >= 2 from each, and not an anagram of any. `validate_new_prefix()` enforces this against the frozen table, and `test_new_prefixes_not_confusable` tests it.
5. **Freezing at the gate (accepted in revision 3).** The registry is one constant (`ID_PREFIXES` in `tracer_evalschema.ids`). Its patterns appear in the generated JSON Schema, so `schema.lock` covers them. `test_prefix_registry_frozen_matches_adr` compares the constant with a literal copy of the table above. At the Phase 1 gate (P1-21) the table is declared frozen. After that: adding a prefix is an additive schema change with an amendment to this ADR; removing, renaming or reassigning a prefix is never allowed, across any version, because stored IDs and external logs keep the old meaning.
6. **Generator.** A monotonic UUIDv7 generator: 48-bit Unix ms timestamp plus a counter/random tail, using the RFC 9562 monotonicity method. IDs from one process are strictly increasing, even inside one millisecond. Citation (P-01): RFC 9562 section 5.7 for the v7 bit layout and section 6.2 ("Monotonicity and Counters") for the monotonic counter method.
7. **External identifiers.** Bare UUIDs, v4 UUIDs and foreign strings never become our IDs. `from_external(id_type, *, system, kind, value) -> (TypedId, ExternalRef)` (signature fixed in revision 7; revisions 3-6 wrote `from_external(kind, system, value)`, which used `kind` both for the minted entity kind and for `ExternalRef.kind`) mints a fresh v7 ID of `id_type` on every call and returns the `ExternalRef{system, kind, value}` (value stored verbatim) that the caller records on the owning entity (for example `Run.external_refs[]`). It is pure: it neither looks anything up nor stores anything. The external value is stored only as data. **Idempotent re-import (P-02):** Phase 2 adds a unique index on `(entity kind, ExternalRef.system, ExternalRef.kind, ExternalRef.value)`, and importers look up an existing entity by that key before minting a new ID, so a re-imported external call is stored once.

## Rejected alternatives
- **UUIDv4.** Random values spread inserts across the whole B-tree, which fragments indexes and degrades them over time, and the ID carries no time order. v7 keeps index locality and gives a natural sort key.
- **Bare UUID on the wire (no prefix).** Logs and support tickets become ambiguous, and nothing stops an ID of the wrong kind from being stored. The prefix makes IDs self-describing and lets JSON Schema reject the wrong kind.
- **Stored as text in the database.** Uses 36+ bytes instead of 16, indexes more slowly, and allows case and format variants. The native `uuid` type is canonical by construction.
- **ULID / KSUID / Snowflake.** Not an IETF standard, and not supported natively by Postgres `uuid` or the Python stdlib (3.14 adds `uuid.uuid7`). Snowflake needs a coordinated worker ID. UUIDv7 gives the same time-ordering benefit and is a standard.
- **Adopting external IDs as our IDs.** External IDs collide across systems, may be v4 or non-UUID, and could be changed by a third party. Our identity would then depend on a provider, which breaks agent-agnosticism.
- **Deterministic name-based IDs (v5/v8) from external IDs.** Rejected by the user's v7-only decision. Idempotent re-import is handled by a uniqueness rule on `ExternalRef` instead (P-02).
- **Uppercase or mixed case allowed.** Two spellings of one identity break byte-identical exports and string comparison in logs.
- **IDs on value objects (Money, ContentDigest, ...).** A monetary amount or a digest has no identity: two equal amounts are the same value. An ID and a creation time on them would invite references to things that have no lifecycle, and would make equal values compare unequal.
- **Keeping `trn` for Transcript.** It differs from `turn` by one letter and both appear in the same log lines and evidence references.
- **(Revision 15) Keeping `PriceEntry` as an entity with prefix `pce`.** An entry never exists outside one catalog version, and as an embedded entity it carried `schema_version`, `created_at` and `metadata` into the catalog's digest domain (N47, ADR 0014).
- **(Revision 16, N61) `entry_id` on the opaque-ID allowlist.** It would widen the I12 principle (opaque `*_id` values are assigned outside tracer) to keys assigned by the author of a versioned record; `entry_key` names a catalog-scoped key without bending the rule.

## Consequences
- Phase 2 stores `uuid` natively. The prefix is implied by the column, so it is never stored.
- A v7 ID reveals its creation time to the millisecond. A shared export therefore reveals when a run was created. That is acceptable because exports already carry timestamps; the privacy work (ADR 0016) does not rely on hiding time.
- Monotonicity holds within one process only. Ordering across processes is by timestamp, with ties within the same millisecond.
- The registry is a Phase 2 dependency: table names and foreign keys follow it.

## Decided items (formerly [Proposed]; all decided by the user in revision 5)
- **P-01. RFC 9562 citation. Decided by the user (revision 5): accepted as recommended.** Decision: cite section 5.7 for the v7 layout and section 6.2 ("Monotonicity and Counters") for the generator; SCOPE P1-04a currently cites only 5.7. Reason: 5.7 defines the bit layout but not the monotonic counter method, so a reader following the citation cannot check the generator. Had it been decided otherwise: the citation stays 5.7 only; the generator and tests do not change.
- **P-02. Idempotent re-import. Decided by the user (revision 5): accepted as recommended.** Decision: Phase 2 adds a unique index on `(entity kind, ExternalRef.system, ExternalRef.kind, ExternalRef.value)` and importers look up an existing entity before minting. Reason: v7-only IDs mean a re-import mints a new ID, so without a uniqueness rule the same external call is stored twice and counted twice in benchmarks. Had it been decided otherwise: re-imports create duplicates, and deduplication becomes a query-time concern for every consumer.
- **P-03. Existing near-identical prefixes. Decided by the user (revision 5): accepted as recommended.** (Revision 7 correction: the frozen table has five confusable pairs, not three; see Decision 4. The user's decision, keep the existing pairs and apply the rule to future prefixes, covers all five.) Decision: keep `run`/`rub`, `exc`/`exp` and `dts`/`dti` as frozen in SCOPE (typed rejection already catches swaps), and adopt the rule "a new prefix is at least two edits from every existing prefix and is not an anagram of one" for all future additions, enforced by `test_new_prefixes_not_confusable`. Reason: these pairs are one edit apart, the same weakness that motivated the `trn` -> `tsc` change, but renaming them was not requested. Had it been decided otherwise (rename them): the registry table, patterns and `test_prefix_registry_frozen_matches_adr` change before the gate; nothing else does.
