# ADR 0017: Text storage, bidi controls and `display_safe()`

Revision 7: batch 1 items 14-17 resolved by schema-architect (marker table, `HumanLabel` edge cases, `BidiFlaggedText`, conformance result: the fallback P1-04e is triggered); rejecting variation selectors and tag characters in labels is escalated to the user for confirmation (E2). Open [Proposed] items: none.
- Date: 2026-10-22 (revision 5: P-48..P-50 folded into Decisions 2, 4 and 5)

## Context
The schema stores untrusted text: caller speech transcribed by STT, agent output, telemetry attributes, tool arguments, provider language labels. Unicode bidirectional controls can make displayed text differ from stored text (for example an account number `1234<RLO>9876` shown as `1234 6789`), and isolate characters can break out of a container (PDI breakout). Indic text legitimately depends on invisible characters: ZWJ and ZWNJ select half-forms, Malayalam chillu and conjunct shapes. Removing them corrupts the language. Normalization (NFC/NFD) changes code points, and therefore WER/CER results and digests. Proving that `display_safe()` works needs an independent implementation of the Unicode Bidirectional Algorithm (UBA, UAX #9) to compute the visual order.

## Decision
1. **`VerbatimText`** (free text: turn text, segment text, raw payloads, raw language labels). It is stored code-point-for-code-point as received. No normalization, no stripping. NFC and NFD forms are distinct values. Lone surrogates are rejected (they cannot be encoded as UTF-8). (Revision 20, N82 decided, auto-approved; ADR 0014 Decision 12c step 0.) The type keeps rejecting them; an importer never raises on source text, so before storing such text it applies the one public replacement `text.replace_lone_surrogates` (each code point in U+D800..U+DFFF becomes U+FFFD, one for one, nothing else changed), treats the text as unparseable and records the ingest warning `text_not_valid_unicode`.
2. **`contains_bidi_controls`** is computed at ingestion from the text and verified on load. A stored flag that disagrees is rejected. The reusable form is the value object `BidiFlaggedText{text: VerbatimText, contains_bidi_controls: bool}` (revision 7): computed when omitted, verified when supplied, always serialized. Turn and Segment reuse its validator. **Character set (P-48):** exactly U+202A-U+202E and U+2066-U+2069 (the explicit embedding, override and isolate controls); LRM, RLM and ALM do not set it, so the flag stays a signal instead of firing on ordinary right-to-left text.
3. **`display_safe(text) -> str`** is the one shared rendering function:
   - It wraps the whole text in FSI (U+2068) ... PDI (U+2069), so the text cannot affect surrounding content.
   - It replaces each U+202A-U+202E and U+2066-U+2069 inside the text with a visible marker from an exported marker table (for example `[RLO]`), so the controls are both visible and inert. This also prevents a PDI inside the text from closing the outer isolate early.
   - It leaves LRM (U+200E), RLM (U+200F) and ALM (U+061C) unchanged in free text.
   - It never mutates its input. The marker table is exported as JSON and must match the function.
3a. **Marker table (revision 7).** Markers are the Unicode abbreviations in brackets: U+202A `[LRE]`, U+202B `[RLE]`, U+202C `[PDF]`, U+202D `[LRO]`, U+202E `[RLO]`, U+2066 `[LRI]`, U+2067 `[RLI]`, U+2068 `[FSI]`, U+2069 `[PDI]`. The table is the read-only `text.MARKER_TABLE`, and `text.marker_table_json()` returns `{"wrapper": {"open": "U+2068", "close": "U+2069"}, "markers": {"U+202A": "[LRE]", ...}}`, shipped as the generated package file `data/bidi_markers.json` (no `_meta`, never edited by hand; `test_marker_table_json_matches_function` is its drift check).
4. **`HumanLabel`** (names, labels, accent, display names) rejects U+202A-U+202E, U+2066-U+2069, LRM, RLM, ALM, ZWSP (U+200B), WORD JOINER (U+2060), BOM (U+FEFF), and C0/C1 control characters. It accepts ZWJ (U+200D) and ZWNJ (U+200C). **Wider denylist (P-50):** `HumanLabel` also rejects every other Default_Ignorable_Code_Point character (for example U+2061-U+2064, U+180E, U+3164 and the Hangul fillers), so two labels cannot look identical while differing; ZWJ and ZWNJ remain the only accepted default-ignorables. **Precisely (revision 7):** the Default_Ignorable_Code_Point set is that of Unicode 16.0.0 (DerivedCoreProperties.txt), and it includes the variation selectors (U+FE00-FE0F, U+E0100-E01EF, U+180B-180D, U+180F) and the tag characters (U+E0020-E007F). Labels therefore cannot carry emoji presentation selectors or flag tag sequences; no need for emoji labels has been stated (confirmation escalated to the user as E2). Also rejected: all of general category Cc (C0, DEL U+007F, C1), U+2028 and U+2029, the empty string, and a label that begins or ends with white space (`str.isspace()`); a label is never trimmed. Tests: `test_human_label_rejects_variation_selectors_and_tag_characters`, `test_human_label_rejects_del_separators_empty_and_edge_whitespace`.
5. **`MachineKey`** (keys, provider/model identifiers, enum-like open values) is ASCII only, pattern `^[A-Za-z0-9][A-Za-z0-9._:/@+-]{0,255}$` (P-49), so case-sensitive provider model names with `/`, `:`, `.`, `@` and `-` fit. Our own metric keys use the stricter lowercase snake_case `MetricKey`.
6. ZWJ and ZWNJ are preserved in every text type.

## Rejected alternatives
- **Strip bidi controls on ingestion.** It changes the evidence. A spoofing attempt in an agent's output is itself a finding (a safety evaluation), and stripping hides it. Stripping also alters stored text relative to the source, which breaks the no-fabrication and verbatim rules.
- **NFC-normalize on ingestion.** It changes code points relative to what the STT or agent produced. Normalization belongs in WER/CER pipelines (indic-linguistics), where it is explicit and versioned.
- **Isolation only (no visible markers).** An RLO inside the isolate still reorders the text itself, so `1234<RLO>9876` would still display as `1234 6789`. Both mechanisms are needed (Q13).
- **Visible markers only (no isolation).** Neutral or RTL text inside can still interact with surrounding UI text in the bidi algorithm.
- **Escaping as `‮` text.** It makes ordinary RTL/Indic content unreadable when it contains marks, and it is worse for reviewers than a named marker.
- **Reject bidi controls in free text.** Real STT and LLM output may contain them, and rejecting would break ingestion (core rule).
- **Allow LRM/RLM in labels.** Labels are short identifiers shown in tables. Marks there are almost never needed and enable look-alike labels (OQ3).
- **Testing `display_safe()` by string comparison only, without a UBA reference.** It proves which characters were inserted, not what a renderer shows; the account-number and PDI-breakout properties are about visual order.
- **Trusting the reference without a conformance run.** An implementation that mishandles isolates would make the isolate tests pass or fail for the wrong reason.
- **PyICU as the required reference.** It has no wheels and builds against the runner's system ICU, so the UBA version is set by the runner, not by `uv.lock`, and the required matrix would depend on a system library.

## Consequences
- Every UI, CLI and report must render untrusted text through `display_safe()`. Bypassing it is a security bug.
- WER/CER normalization is a separate, documented step. Stored text is never the normalized text.
- Because JSON encoding varies (`\u` escapes vs raw UTF-8), "byte-for-byte" means code-point-for-code-point after JSON decoding. JCS fixes the bytes for digests.
- The license scan must distinguish the two named exceptions (hypothesis, pathspec; python-bidi was the third until 2026-10-22) from blockers; any other MPL, LGPL or GPL package still fails it.

## Decided items (formerly [Proposed]; all decided by the user in revision 5)
- **P-48. Character set of `contains_bidi_controls`. Decided by the user (revision 5): accepted as recommended.** Decision: exactly U+202A-U+202E and U+2066-U+2069 (the explicit embedding, override and isolate controls). Reason: these are the characters that can reorder or escape; including LRM/RLM/ALM would flag ordinary right-to-left and mixed-direction text constantly and make the flag useless as a signal. Had it been decided otherwise (include marks): the flag fires on routine text, and `test_bidi_flag_computed` changes its expected values.
- **P-49. `MachineKey` charset. Decided by the user (revision 5): accepted as recommended.** Decision: `^[A-Za-z0-9][A-Za-z0-9._:/@+-]{0,255}$`, plus a stricter lowercase snake_case `MetricKey` for our own keys. Reason: provider model names need `/`, `:`, `.`, `@`, `-` and case (model IDs are case-sensitive), while our own keys benefit from one spelling. Had it been decided otherwise: the chosen pattern replaces this; model names outside it must be stored in a VerbatimText field instead. Test (binding): `test_machine_key_charset_allows_model_names` (for example `org/Model-3.1:latest@2024`).
- **P-50. Wider invisible-character denylist for labels. Decided by the user (revision 5): accepted as recommended.** Decision: `HumanLabel` rejects every Default_Ignorable_Code_Point character except ZWJ and ZWNJ (and variation selectors if emoji labels are wanted), adding for example U+2061-U+2064, U+180E, U+3164 and the Hangul fillers to what SCOPE lists. Reason: the SCOPE list leaves invisible characters that allow two labels to look identical while differing. Had it been decided otherwise: the SCOPE list stays, and look-alike labels remain possible through the unlisted characters. Test (binding): `test_human_label_rejects_default_ignorables`.
