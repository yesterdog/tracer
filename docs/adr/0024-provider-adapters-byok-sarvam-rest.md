## Context
The framework is BYOK: every provider call uses the user's own key (ADR 0007). Phase 3 makes the first such call: Sarvam speech-to-text over REST, for the recorded-call scoring of ADR 0023. The two base-case recordings are 254.6 s and 437.2 s long, mono, 24 kHz, 16-bit PCM WAV, and they hold real people's speech. The facts below come from the Sarvam documentation retrieved on 2026-10-25 and from the 47 calls captured on 2026-10-23 (`packages/evalschema/tests/fixtures/real/sarvam-2026-10-23/`, `tools/capture/SARVAM_OBSERVATIONS.md`):
- `POST https://api.sarvam.ai/speech-to-text`, multipart form data, key in the `api-subscription-key` header; no API version anywhere; the docs default model is `saaras:v4`, and the response does not echo the model.
- The REST page is "For quick responses under 30 seconds" and sends longer audio to the Batch API (F1); what REST does above 30 s is unverified (no capture sent more than 12 s).
- A forced `language_code` is echoed, not detected; `unknown` returns a detected tag and, when speech was detected, `language_probability` (F2). Silence returns an empty transcript with a non-null tag and no probability.
- Timestamps, when requested, are phrase level; there is no word timing, no diarization on REST, no per-word confidence, no usage, no cost and no audio duration in the response (F10).
- Errors are `{"error": {"message", "code", "request_id"}}`; validation failures were 400, not the documented 422; 429 and 5xx were never observed, and no response carried `Retry-After` or rate-limit headers.
- Pricing is ₹0.49 per minute for real-time and batch STT, in INR only; rounding and a minimum charge per request are not stated (F8). Schema 0.0.1 prices in USD only (ADR 0014).

## Decision
Machine-read by `test_adr0024_rules_are_tested`, in the format of ADR 0021 and ADR 0022: every numbered rule of this section and every invariant cites at least one test name in backticks. Since the Phase 3 gate (P3-G) every name that rules 1 to 17 and invariants I1 to I9 cite is a test the tree defines, and the test's set of allowed undefined names is empty (revision 50, BL-263). The Phase 4 rules A1 to A9 are in their own section below and follow the citation rule stated there.

1. **The adapter boundary.** `tracer-evalcore` defines an `SttEngine` protocol (chunks in, a typed STT result or a typed failure out) and never imports a network module (`socket`, `ssl`, `http`, `urllib`, `httpx`). Provider adapters live in `tracer-evalproviders`; Sarvam is the only one in Phase 3. Provider names, URLs, form fields, error codes and language maps belong to the adapter and never enter `tracer-evalschema` or `tracer-evalcore`. `tracer-cli` selects the engine (`--stt sarvam`, or `--stt fake:<dir>`, which replays recorded responses offline). Rejected: one package with the HTTP client next to the scorers (the pure core could then open sockets); the vendor SDK (`sarvamai` declares no licence, F1). Trade-off: three packages to release and audit. Tests: `test_evalcore_imports_no_network_module`, `test_evalcore_runtime_imports_whitelist`, `test_evalproviders_runtime_imports_whitelist`, `test_cli_runtime_imports_whitelist`, `test_evalschema_does_not_import_phase3_packages`.
2. **The HTTP client (Q2; F11).** httpx in the bounded range `httpx>=0.28.1,<1`, tested at its lower bound (SCOPE Decisions D3), with its licence closure reviewed (P3-02). The adapter takes an injectable `httpx` transport; production uses the default transport, tests an `httpx.MockTransport`. Calls are sequential: one request in flight per run. Rejected: `urllib` (multipart by hand; the certificate store of uv's standalone Python on macOS unverified); `requests` (no mock transport). Trade-off: httpx has had no release since 2024-12 (watch row BL-190). Tests: `test_phase3_requires_dist_bounded_ranges`, `test_license_policy_lists_phase3_closures`.
3. **A fixed endpoint: no URL override, no redirect, TLS verified.** The base URL is the constant `https://api.sarvam.ai` and the path `/speech-to-text`; no argument, environment variable, configuration file or CLI flag changes them, and tests inject a transport, never a URL. Redirects are not followed (a redirect is an unexpected response, rule 10), so the key header is never sent to another host, and certificate verification cannot be turned off. The one `httpx.Client` is built with `trust_env=False` (batch G, audit F3): the client reads no `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` or `NO_PROXY` (any case), no `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE` or `CURL_CA_BUNDLE`, and no `.netrc`, so no variable of the environment can route the audio and the key through a middlebox or swap the trusted roots; the default transport still verifies TLS against the bundled roots. No public parameter names a proxy, a certificate or `trust_env`. Every request, every retry included, carries exactly one `Accept-Encoding: identity` header (audit F10); a server that compresses anyway is still decoded and still bounded by the size cap of rule 8. Rejected: a base-URL setting for proxies or tests (it is the one setting that would send the key anywhere); a `--proxy` option or honouring the proxy environment (a proxy is a host the key and the audio travel through, so it needs its own audited design: which schemes, whether the proxy sees plaintext, how it is recorded). Trade-off (reversed by batch G; the earlier text said a user behind a corporate proxy relies on the proxy environment httpx reads): proxies and extra CA files are NOT honoured in Phase 3, so a user behind a corporate proxy or a TLS-inspecting middlebox cannot make a real send until an explicit, audited setting exists (BACKLOG BL-237). Tests: `test_sarvam_base_url_not_overridable`, `test_audit_f3_client_never_reads_the_proxy_or_certificate_environment`, `test_audit_f3_source_passes_trust_env_false_to_the_http_client`, `test_audit_f3_default_transport_still_verifies_tls_against_the_bundled_roots`, `test_audit_f10_every_attempt_asks_for_an_uncompressed_reply`.
4. **BYOK at run time.** The key is read when the command runs, from the environment variable `SARVAM_API_KEY` or, with `--env-file <path>`, from that file, which is read for that one variable only: no other line is parsed into a value, nothing is exported into the process environment, and no error message quotes a line of the file. A missing or empty key stops the command before any request. The env file (batch G, audit F9) is opened read-only and non-blocking, so a FIFO cannot hang the command, and then judged by `fstat`: anything that is not a regular file (a directory, a FIFO, a device) is refused with the reason `env_file_not_regular`, a file over `ENV_FILE_MAX_BYTES` = 65,536 bytes with `env_file_too_large` (at most one byte over the cap is read; a file of exactly the cap is read), and any other failure keeps `env_file_unreadable`; a symbolic link to a regular file is followed and read. A file with any group or other permission bit earns exactly one `EnvFileModeWarning` (a `UserWarning` holding the mode and nothing else) before the content is parsed; the command prints it as one stderr line, `warning: the env file can be read by other users (mode 0o644); run chmod 600 on it` with the actual mode, and a warning never refuses the run. The key from the environment never warns. The errors keep the reason only: no path, no line, no file name. The key is never stored: the Project records `ProviderConfigRef{provider: sarvam, model: <model>, config_ref: env:SARVAM_API_KEY}` (ADR 0007 Decision 1), a name, never a value, and never the env-file path. Rejected: a `--api-key` flag (shell history and process lists show it); keyring support in Phase 3 (a second code path before the first is audited). Rejected (batch G): a callback argument for the mode warning (it would change the public signature of `load_api_key`); refusing a group-readable file (a warning tells the user without breaking a working setup). Trade-off: the user must export the variable or name the file each run. Tests: `test_env_file_reads_only_named_variable`, `test_missing_key_refuses_before_any_request`, `test_audit_f9_the_cap_is_64_kib`, `test_audit_f9_a_fifo_is_refused_at_once_and_never_blocks`, `test_audit_f9_a_directory_is_refused`, `test_audit_f9_a_file_other_users_can_read_earns_a_warning_that_holds_no_secret`, `test_audit_f9_a_readable_env_file_earns_exactly_one_non_secret_warning_on_stderr`.
5. **The key never leaves the request header.** The adapter holds the key in a redacting wrapper whose `str`, `repr` and formatting give a fixed placeholder; the clear value is read only to build the `api-subscription-key` header of one request. No exception the adapter raises holds the key, the request or its headers: an httpx error is translated into a typed adapter error raised `from None` (no `__cause__` or `__context__` that keeps the httpx request), with the HTTP status, the Sarvam `error.code` and the request id only. The key appears in no log record at any level (the `httpx` and `httpcore` loggers included), in no call-log line (rule 15), in no record of the bundle, in the store and in the report. The command's `Environment.environ` and `EngineRequest.environ` (the mapping the key is read from) are left out of the `repr` of their dataclasses (batch G, audit F8), so an assertion failure or a log line that prints either object cannot show the key. Rejected: relying on httpx not to log headers (a library change could start); masking only part of the key (a prefix narrows a guess). Trade-off: debugging a request means reading the call log, not the headers. Tests: `test_key_never_in_exception_str_repr_or_chain`, `test_key_never_in_logs_at_debug`, `test_key_never_in_call_log_store_or_report`, `test_audit_f8_environ_is_not_in_the_repr_of_the_environment_or_the_request`.
6. **The request (Q4, Q15, Q21; BL-162).** Each chunk is one request with exactly these form fields: `file` (the chunk as a WAV file), `language_code=unknown`, `model=<model>` and `with_timestamps=true`; nothing else is sent. The model is always sent explicitly (the docs default `saaras:v4` is the adapter's default value, never left to the server), and it is recorded on the Transcript and on every UsageRecord as requested, with a metadata note that the response does not echo it. The language map is mr only: the configured language must be mr, which is sent as `unknown` so the engine observes the language (ADR 0023 rule 14); any other configured language is refused before any request (BL-162), and a forced code is never sent in the base case. Audio is sent at its native rate (24 kHz for the base case), never resampled; whether Sarvam accepts it is checked on the first chunk of the first real send (P3-30), and a refusal stops that run. Rejected: forcing `mr-IN` (echoed, not observed, F2); omitting `model` (a run could not be priced or attributed, Q15); resampling in pure Python (quality risk, BL-187). Trade-off: if the engine detects another language on a chunk, the result is not scored (ADR 0023 rule 14). Tests: `test_sarvam_request_sends_unknown_language_and_explicit_model`, `test_sarvam_request_never_sends_forced_code_in_base_case`, `test_sarvam_configured_language_other_than_mr_refused`.
7. **Chunking (Q3, Q18; F1).** The audio is cut on the client into consecutive chunks of at most `max_chunk_ms`, an adapter parameter whose documented default is 25,000 ms: a technical margin under the docs' 30 s guidance, not a rubric value and not a measured limit. Each window of at most `max_chunk_ms` that does not reach the end of the audio is cut inside its last `search_ms` (default 5,000 ms, also a technical value): the window holds `rate * max_chunk_ms // 1000` samples; the candidate frames are the whole 20 ms frames (`rate * 20 // 1000` samples each, counted from the window start) that lie entirely inside its last `search_ms`, and parameters that leave no such frame are a typed `ChunkerParameterError`, never a silent fixed cut (batch A contract, SCOPE Decisions D8); the cut frame is the one with the lowest energy (the exact integer sum of squared samples over all channels), ties going to the latest frame, and the cut falls at the frame's middle sample. The remainder up to the end of the audio is the last chunk; audio no longer than `max_chunk_ms` is one chunk. Chunks cover every sample exactly once, in order, and are written as WAV files with the input's format, so the same input gives byte-identical chunks. The chunk plan is recorded in `Transcript.metadata["tracer.chunk_plan"]` as the document `tracer.chunk_plan/1`, which holds integers only: the parameters, the rate, the channels and the sample range of each chunk, so every duration can be recomputed exactly from its frames and the rate. The chunker's `exact_seconds(frames, rate)` returns a `Decimal` only when the quotient has a finite decimal expansion, else `None`; it is never rounded and never a float. Stereo input is refused unless the caller passes `accept_provider_downmix=True` (default `False`); with it the chunks keep their channels unchanged and Sarvam merges them (docs); Tracer never computes a downmix. Input with three or more channels is always refused. Rejected: the Batch API (its upload and start REST paths are not documented and its SDK declares no licence; BL-179); fixed cuts every 25 s (words cut in half more often); a silence detector with a threshold (a number nobody measured). Trade-off: chunk boundaries can split a word; ADR 0023 rule 10 marks spans near a boundary, and P3-31 measures the effect. Tests: `test_chunker_is_deterministic`, `test_chunker_covers_every_sample_once`, `test_chunker_never_exceeds_max_chunk_ms`, `test_chunker_cuts_at_lowest_energy_frame`, `test_chunker_short_audio_is_one_chunk`, `test_chunker_stereo_is_not_downmixed_silently`.
8. **Response validation and the size cap.** The adapter reads at most 1,048,576 bytes of a response body (a technical cap; a 25 s transcript is a few kilobytes) and stops reading beyond it with a typed error. A 200 response must be a JSON object, read with the strict I-JSON rules of the schema, with `request_id` a string, `transcript` a string, `language_code` a string or null, `language_probability` absent or a number in [0, 1], and `timestamps` absent or an object of three arrays of equal length (`words` strings, `start_time_seconds` and `end_time_seconds` finite non-negative numbers, each start at most its end). Numbers are read from their JSON text as decimals, never through a float. Unknown members are kept out of every record. A body that fails any of these is a typed error and is not retried. Rejected: trusting the documented shape (the docs and the captures already differ on 400 against 422). Trade-off: a new member Sarvam adds is ignored until the adapter maps it. Tests: `test_sarvam_response_models_parse_all_captures`, `test_sarvam_response_rejects_wrong_types_and_oversize_body`.
9. **Timeouts, retries and `Retry-After`.** Timeouts are 10 s to connect and to get a pooled connection, and 60 s to write and to read (technical defaults, not measured; R1 records the real latencies). A chunk gets at most 4 attempts. Retried: HTTP 429, any 5xx, and transport errors (connect, read and write errors and the timeouts). The waits before the second, third and fourth attempts are 1 s, 2 s and 4 s, with no jitter, so a test can predict them; one run sends one request at a time, so there is no herd to spread. A `Retry-After` header on a 429 or 503, as delay-seconds or as an HTTP date measured against the response `Date`, is honoured: the wait is the larger of the backoff and the header, never less than the header asks; a value above 30 s ends the attempts for that chunk with a typed rate-limit error rather than waiting longer than the bound, and an unparseable value is ignored. No other 4xx is retried. A retried attempt is a new request; whether a failed attempt was billed is unverified, so it makes no UsageRecord, and the call log keeps every attempt. Rejected: unbounded retries (a run could spend without limit); retrying 400 or 403 (the same request fails again); random jitter (non-deterministic tests). Trade-off: a long Sarvam outage fails the run quickly instead of waiting. Tests: `test_sarvam_retries_429_and_503_then_succeeds`, `test_sarvam_gives_up_after_bounded_retries`, `test_sarvam_does_not_retry_400_403`, `test_sarvam_honours_bounded_retry_after`.
10. **The error taxonomy (from the 2026-10-23 captures).** The adapter decides on the HTTP status and on `error.code`, never on the message text, which can echo input. Every error carries the chunk index, the HTTP status (or the transport error kind), the `error.code` when it is a short machine key (else `unrecognised`) and the request id; never the message, the body, the key or the audio.

   | Error | When | Captures | Retried |
   |---|---|---|---|
   | `SttAuthError` | 401 or 403, or `error.code=invalid_api_key_error` | `err_bad_key` | no; the run stops before the next chunk |
   | `SttRequestRejected` | 400, 422 or any other 4xx except 429, for example `invalid_request_error` | `err_invalid_language_code`, `err_underscore_language_code`, `err_no_file`, `err_not_audio`, `err_empty_file` | no |
   | `SttRateLimited` | 429 after the last attempt, or a `Retry-After` above the bound | none (never observed) | yes, within rule 9 |
   | `SttServerError` | 5xx after the last attempt | none (never observed) | yes, within rule 9 |
   | `SttTransportError` | connect, read or write error or timeout after the last attempt | none | yes, within rule 9 |
   | `SttResponseInvalid` | a 200 body that fails rule 8, a body over the cap, a non-JSON content type, a 1xx or 3xx status | none | no |

   The class names are the recommendation; the batch B contract written by qa pins the final spelling. Rejected: matching message text (it changes and can echo input); one generic error (the CLI could not tell a bad key from an outage). Trade-off: a new Sarvam error code maps by its status until the table is extended. Tests: `test_sarvam_error_taxonomy_matches_captures`, `test_sarvam_does_not_retry_400_403`.
11. **All or nothing (Q14).** A run's STT transcript exists only if every chunk succeeded. When any chunk fails after its attempts, the adapter returns a typed failure and no Transcript, no Turn and no Segment is built from the chunks that succeeded; the pipeline then records the failure as ADR 0004 Decision 10 states (`missing_input` `["transcript"]`, a Run `IngestWarning`, a non-zero exit). The UsageRecords of the chunks that succeeded are kept, because that usage happened (rule 13). Rejected: a partial transcript (its missing chunks would read as deletions in the export, ADR 0023); `error` (the input never existed). Trade-off: one failed chunk discards the paid text of the others. Tests: `test_sarvam_partial_chunk_failure_yields_no_transcript`, `test_stt_failure_is_missing_input_with_warning_and_nonzero_exit`.
12. **Mapping to records (Q16; P3-09).** One Transcript: `source=our_stt`, `provider=sarvam`, `model` as requested, `timeline_origin` the audio artifact, no `provider_call_ref` (it took several calls), and `detected_language` only when every non-empty chunk returned the same tag (ADR 0023 rule 14). One Turn per non-empty chunk, in chunk order: `role=unknown`, `source=our_stt`, `text` the transcript verbatim, `language` from the returned code through `normalize_language_label` (the raw label kept when it does not normalise, ADR 0005), `language_probability` copied into `Turn.metadata` as a canonical decimal string when present, and Segments from the phrase timestamps, offset by the chunk's start. Times follow the F3 floor rule of the Phase 1 mapper (`seconds_to_ms_floor`), computed from the exact chunk start (its first sample divided by the rate) plus the decimal seconds of the response; timing is `audio_alignment` from those Segments, or `none` when the response has no timestamps; a phrase that ends after its chunk's exact duration is not mapped to a Segment for that chunk (its Turn gets timing `none`) and the Run records an `IngestWarning`, so no time is moved or invented. A chunk whose transcript is empty or white space only makes no Turn, and the transcript metadata counts it and lists its index; the non-null tag the engine returns for silence is not a detection and is not recorded as one (captures `stt_silence_unknown`, `stt_silence_forced_hi`). Rejected: a Turn with empty text (it would read as a statement that nothing was said in a known language); clamping out-of-range phrase times (a fabricated time). Trade-off: a chunk of pure silence leaves no trace in the turns, only in the metadata. Tests: `test_stt_transcript_maps_one_turn_per_nonempty_chunk`, `test_empty_chunk_makes_no_turn_and_is_counted`, `test_stt_turn_language_is_observed_from_unknown_request`, `test_stt_segments_offset_by_chunk_start`, `test_detected_language_set_only_when_all_chunks_agree`, `test_stt_phrase_time_outside_chunk_gives_no_segment_and_a_warning`.
13. **Usage (Q19; ADR 0014).** Each successful chunk gives one UsageRecord: `domain=evaluation`, `stage=stt`, `provider=sarvam`, `model` as requested, `provider_call_ref` the response `request_id` (`ExternalRef{system: sarvam, kind: request_id, value}`), `source=measured`, `raw` null, and the quantities `audio_input_seconds` and `requests` 1. `audio_input_seconds` is the chunk's duration, frames divided by rate. That quotient has no finite decimal expansion for most chunks at 24 kHz (1/24000 does not terminate), and a `DecimalString` holds at most 18 fractional digits (ADR 0014 Decision 1), so the value is the quotient rounded half to even to 18 fractional digits, in canonical form. The rounding is stated, never hidden: every such UsageRecord carries `metadata["tracer.audio_seconds_rounding"]`, the short machine key `half_even_18` when rounding changed the value and `exact` when the quotient fits in 18 fractional digits; the exact frame count and rate stay in the chunk plan (rule 7). The rounding error is below 10^-18 s per chunk, far below any billing unit. `occurred_at` is the instant of the response's HTTP `Date` header, the source's own statement; it is absent when the header is missing or does not parse, and never the time of the run, the ingest or the local clock. The billable seconds are unknown (Sarvam's rounding and minimum are unstated, F8); the record states what was sent, from exact frame counts. The usage of our STT is evaluation usage and never makes the input kind `usage` available (ADR 0004 Decision 2). Rejected: the local clock for `occurred_at` (a time the source did not state, ADR 0014 Decision 8); the response body in `raw` (it holds call text, which is personal data). Trade-off: a missing `Date` header leaves the price date to the catalog rules. Tests: `test_usage_record_per_chunk_measured_seconds_exact`, `test_usage_audio_seconds_rounded_half_even_18_digits_and_stated`, `test_usage_raw_never_holds_transcript_text`.
14. **Cost (F8; ADR 0014).** Without a user-supplied USD pricing catalog, every chunk's CostRecord is `not_available` with `na_reason=no_price_for_model` and its usage record listed, and the CostSummary has no total: never an amount of 0. With a user catalog (a file the user writes, whose entries carry a `note` naming the source of each USD price and the billing rules), cost is computed by the evalschema pricing functions, and an entry with `billing: "unknown"` gives `billing_rules_missing`. Tracer never enters the INR price into a catalog, never converts INR to USD and never derives a USD price. Rejected: converting INR at a rate (no FX in 0.0.1, ADR 0014 Decision 4); an estimate from the audio length (an unearned number). Trade-off: by default the CLI shows usage and `not_available`. Tests: `test_cost_not_available_without_usd_catalog`, `test_cost_computed_with_user_usd_catalog`, `test_cost_never_zero_when_unpriced`, `test_inr_price_never_converted`.
15. **The call log.** Every attempt writes two JSON lines to a local call log inside the required `--out` directory (Q17), file mode 0600: one before the request is sent, flushed before sending, and one after the response or the error. A line holds only: the UTC timestamp, `before` or `after`, the chunk index, the attempt number, the bytes sent, the chunk's audio seconds (a decimal string), the HTTP status or the transport error kind, the elapsed milliseconds and the request id. It holds no transcript text, no error message, no header, no key and no file path. `CallLog.open` creates a missing output directory with mode 0700 whatever the umask (parents with the default mode; an existing directory keeps its mode), and the log is opened with `O_NOFOLLOW` (batch G, audit F7): a symbolic link in place of `sarvam_call_log.jsonl`, also a dangling one, is refused with an `OSError` before anything is written through it, by `CallLog.open` and by the constructor alike; the command turns that error into exit 4 (`output_unavailable`) before any request. An existing regular log with a looser mode is still tightened to 0600. Report HTML, store files and call logs are git-ignored, and the extended guard refuses them when staged (P3-34); the usage recovery file of rule 16 is git-ignored by a narrow pattern but not guarded (it holds usage and request ids, no call text). Rejected: logging response bodies (call text); logging only after a send (a crash mid-request would leave no trace of a billable call); following a link for the call log (a planted link would redirect the command's own appends; the env file of rule 4 may be a link because it is only read). Trade-off: two lines per attempt; POSIX only (modes, `O_NOFOLLOW`). Tests: `test_call_log_has_no_text_no_key`, `test_call_log_written_before_and_after_each_send`, `test_guard_rejects_staged_report_store_and_call_log`, `test_audit_f7_call_log_directory_is_private_whatever_the_umask`, `test_audit_f7_a_symbolic_link_in_place_of_the_log_is_refused`, `test_audit_f7_a_dangling_link_is_refused_and_creates_nothing`, `test_audit_f7_a_linked_call_log_is_refused_by_the_command_before_any_request`, `test_audit_f2_gitignore_lists_the_recovery_file`.
16. **The dry run, and the gates before a send.** `tracer score --dry-run` reads the inputs, builds the chunk plan and prints the number of chunks, the audio seconds and the number of calls, a cost only when the user supplied a USD price, the attempts per chunk and (batch G) the cap line `max chunks: <N> (the plan has <n>: within the cap)`, or `max chunks: not set` when no `--max-chunks` was given; it reads no key, reads no env file, creates and probes no output directory and opens no connection. It applies the same refusals as a real run (a plan over the ceiling, an export over the alignment cap, the consent gate) and prints them as the same exit-4 lines. Batch G (audit F2, F4, F5) puts every refusal that depends on the inputs, the plan or the output side before the first byte is sent: (a) **a chunk ceiling** (F4): `--max-chunks N` refuses a plan of more than N chunks (`max_chunks_exceeded`, exit 4, no engine built); it is required for a real `--stt sarvam` run, with no default, and at most `MAX_SARVAM_CHUNKS` = 200 (a technical bound, about 83 minutes at the 25 s window, not a measured value; raising it is a source change); with `--stt sarvam` a window `--max-chunk-ms` above 30,000 ms (the docs' REST guidance) is a usage error. The ceiling counts chunks, not requests: a chunk can take up to 4 attempts and a retried request may be billed again (BL-228, BL-239). The cap refuses a plan, it never truncates one, so a single-chunk first send needs an input of one chunk. (b) **a consent gate** (F5): `--stt sarvam` is refused unless `--consent obtained` (`consent_not_obtained`, exit 4, in a real run and a dry run, before any file is read); `--consent obtained` needs `--consent-reference TEXT` (1 to 200 characters, no edge white space, no character of category Cc, Cf, Cs, Co, Cn, Zl or Zp, any script otherwise) and `--consent-recorded-at INSTANT` (RFC 3339, stored in UTC, refused when later than the run: `consent_recorded_at_after_run`; since batch I, re-audit R5, every instant option, this one, `--retention keep-until:` and `delete-after:` and `--priced-at`, is parsed by one strict pattern on every Python version: hour 00 to 23, minute and second 00 to 59, offset hour 00 to 23 and offset minute 00 to 59, so `T24:00:00Z`, which Python 3.14 reads as the next day, and `+05:60` are usage errors); both go on the `ConsentRecord` of the three privacy markers (the artifact and both transcripts) and nowhere else: never printed, never in the report, the call log or a request. A replay (`--stt fake:<dir>`) sends nothing and is never gated. (c) **the output side first** (F2): a `?` in the output path is refused (`output_path_invalid`); the output location is probed without creating anything; the engine factory then reads the key and opens the call log (so a missing key still leaves no directory behind); an engine's optional `preflight(plan)` may refuse (the replay engine checks its directory there); then the store is opened (when the command creates `--out`, the leaf directory is 0700 and the parents it creates follow the umask; `tracer.sqlite` created and migrated) and only then can `transcribe` send. Any failure up to that point is exit 4 with nothing sent. Since batch I (re-audit R6) a link in place of `<out>/tracer.sqlite` (to a file, to a directory, or dangling) is refused before the engine factory with `error: output_unavailable (store_file_is_a_link)`, exit 4, and the store open refuses a link as well (an `OSError`, exit 4), so the link target is never written; a link at `--out` itself and links at SQLite's side files are not checked (BL-246). Since batch I (re-audit R3), after the store is open and before the first send, an existing `--out` with any group or other permission bit earns exactly one stderr line, `warning: the output directory is accessible to group or other users (mode 0755)` with its real mode and no path; the warning never refuses, never changes the mode and never changes the exit code. For `--stt sarvam` an export of more than `ALIGN_MAX_TOKENS` (10,000) tokens is refused before the send (`export_tokens_above_alignment_cap`, counted by `tracer_evalcore.scoring.export_token_count`); the speech side can only be known after the send and is stored and reported as not scored (exit 2). (d) **after the send** nothing re-sends audio: a failed store write, a failed report write or a pipeline failure is exit 1 with `error: unexpected failure (<class>)`; the report is still written when a run exists, and the paid usage is kept in `<out>/usage-recovery-<UTC>.json` (`tracer.usage_recovery/1`: usage, cost records, cost summaries and catalogs only; no call text, no key, no path, no exception message; created exclusively with mode 0600, never overwritten, only when at least one chunk was answered), announced on stdout as `usage recovery: <path>`, or as `usage recovery: not written` when the file cannot be created (since batch I, re-audit R2: the writer's own failure, of any class, never replaces the original error and never leaves the command). Since batch I (re-audit R1) the paid usage survives any end of the send: an engine that declares `streams_usage` (the Sarvam engine does; the protocol is `tracer_evalcore.stt.UsageStreamingSttEngine`, and `SttEngine` is unchanged) receives an `on_usage` callback and hands out the usage record of each answered chunk before the next request is built, the same records, with the same ids, that its outcome carries. The command catches `BaseException` around the pipeline and around the store write: when it holds usage it writes the recovery file (`failed_step` `pipeline` with empty cost lists, or `store` with the bundle's cost lists), prints the stdout line, and raises the same exception again. So an exception of the transport, a call-log `OSError`, a failure of the alignment and a `KeyboardInterrupt` (Ctrl-C) all keep the usage of the chunks answered so far; a plain exception then ends in exit 1 as above, while a `KeyboardInterrupt` leaves the command uncaught, with no exit code of its own and no report. With no chunk answered no file is written and nothing is printed. A reply whose `after` call-log line could not be written is not counted (the reply is dropped unread, so the file agrees with the call log). An exception raised by `on_usage` stops the send. No command reads the recovery file in Phase 3. Rejected: an estimate from the INR price (rule 14); a default ceiling (a number that decides what leaves the machine, ADR 0016 Decision 2); requiring `--max-chunks` in the dry run (the dry run is how a user learns the chunk count); opening the store before the engine factory (a missing key would leave a directory behind, against three existing tests); a seventh exit code for a failure after the send (the stdout lines carry the difference); deleting what the command created when the engine refuses (a deletion in the user's directory on an error path); (batch I) catching a `KeyboardInterrupt` in `main` with an exit code 130 (the stdout line already says where the usage is, and the six exit codes stay the contract), computing the cost inside the exception handler (a second way to fail while keeping the first; the cost is derivable from the usage and the user's price file), refusing an `--out` with group or other bits (a warning tells the user without breaking a working setup), and forcing the parent directories to 0700 (the parents may be the user's own existing directories). Trade-off: the user must state a ceiling and the consent details on every real run; a store the probe cannot judge (a corrupt database) is found after the key was read and the call log was opened, still before any request (Ambiguity 8); the recovery file is outside the store and outside deletion and retention (BL-240). Tests: `test_dry_run_sends_nothing_and_prints_plan`, `test_audit_f4_the_dry_run_prints_the_cap_check`, `test_audit_f4_sarvam_needs_an_explicit_ceiling`, `test_audit_f4_a_plan_over_the_ceiling_is_refused_before_any_engine_or_request`, `test_audit_f5_sarvam_is_refused_unless_consent_is_obtained`, `test_audit_f5_the_reference_is_never_printed_or_reported_only_stored`, `test_audit_f2_the_store_is_open_and_the_directory_exists_before_the_engine_is_called`, `test_audit_f2_the_export_is_checked_against_the_alignment_cap_before_the_send`, `test_audit_f2_a_store_failure_after_the_send_keeps_the_usage_and_writes_the_report`, `test_audit_f2_a_missing_key_still_leaves_no_directory_behind`, `test_r1_a_ctrl_c_on_chunk_2_keeps_the_usage_of_chunk_1_and_is_raised_again`, `test_r1_an_exception_of_the_transport_on_chunk_2_keeps_the_usage_of_chunk_1`, `test_r1_a_call_log_error_before_chunk_2_keeps_the_usage_of_chunk_1`, `test_r1_a_ctrl_c_while_the_store_is_written_keeps_the_usage_and_is_raised_again`, `test_each_record_is_handed_out_before_the_next_chunk_is_sent`, `test_r2_a_recovery_file_that_cannot_be_created_is_said_in_the_pipeline_path`, `test_r3_an_existing_out_with_group_or_other_bits_earns_exactly_one_warning`, `test_r3_only_the_leaf_is_forced_to_0700_the_parents_follow_the_umask`, `test_r5_the_pattern_refuses_an_hour_24_and_the_other_time_ranges_on_every_python`, `test_r6_a_link_in_place_of_the_store_is_refused_before_the_engine`, `test_r6_the_store_itself_refuses_a_link_so_a_late_planted_one_is_caught`.
17. **No network in tests.** Unit tests of the three Phase 3 packages (`tracer-evalcore`, `tracer-evalproviders`, `tracer-cli`) never open a socket: the test configuration of each of them patches `socket.connect` (and the async equivalents httpx uses) to fail (revision 43, batch F ambiguity 4; the earlier text said every package), and the Sarvam tests replay the 2026-10-23 captures or scripted bodies through `httpx.MockTransport`. A real send is a separate, owner-gated step (P3-30), never a test. One exemption (revision 49, Phase 3 gate condition C3, decision log "PHASE 3 BATCH J IMPLEMENTED", lead decision): a test that carries the `postgres` marker may connect to a loopback address only (`127.0.0.1`, `::1`, `localhost`), because the CLI store parity test `test_pipeline_bundle_stores_on_both_backends` (task P3-21: the same run bundle stored through `tracer_cli.store` on SQLite and on Postgres) needs a database server; such tests are deselected in the default run and run only in the Postgres legs (local and hosted). Every unmarked test keeps the full guard, loopback included, and a `postgres`-marked test still cannot reach any other host. `tracer-evalschema` and `tracer-evaldb` are not guarded: neither holds a provider adapter or a key, and the Postgres tests of `tracer-evaldb` need a socket to reach their test server (a later guard that allows only that server is BL-221). Rejected: recorded HTTP cassettes that fall back to the network (a missing cassette would send the key); guarding all five packages (the evaldb Postgres parity tests would fail, or the guard would need a per-test exception that weakens it); for the exemption: moving the parity test into `packages/evaldb/tests` (it must test the CLI path, and `tracer_evaldb` stays imported only by `tracer_cli.store`), removing the guard from the whole cli test directory (loses this rule's coverage), and exempting every socket for `postgres`-marked tests (an external host would become reachable). Trade-off: a `postgres`-marked test may talk to a local database server, and the exemption is by marker, so a later `postgres`-marked test in these packages is also loopback-only and must not need more (BL-267); real-API drift is caught by the owner-gated runs only, dated by their retrieval dates; a socket opened by an evalschema or evaldb unit test would go unnoticed until BL-221. Tests: `test_unit_tests_open_no_socket`, `test_cli_fake_stt_runs_offline`.

## Phase 4 amendment: TTS and LLM adapters, several BYOK variables, per-channel STT, 8 kHz and mu-law
Amended 2026-10-27 (ADR index revision 51; Phase 4 batch D, named spec change S-D1, auto-approved; BL-289), without changing rule 17 of the Phase 3 block: the no-network guard of rule 17 extends to `tracer-evalsim` (ADR 0026 rule 23), where tests carrying the `loopback` marker run in the default suite under an adversarial loopback-only guard (only `localhost` or a literal loopback address, a loopback-only bind, no UDP and no Unix socket); unmarked tests keep the full guard, and a test confines the marker to the declared evalsim modules. Rejected: deselecting them by default like the `postgres` tests, reusing the `integration` marker, in-memory transports only, mocking websockets. Read rule 17's "a `postgres`-marked test still cannot reach any other host", and the same claim for `loopback`-marked tests, as holding for the socket paths each guard patches: `socket.gethostbyname*`, UDP `sendto` without `connect`, the direct `_socket` module and subprocesses are not patched by the Phase 3 guard (BL-289), and a marked test can reach any listener on the loopback interface (BL-290).
Revision 50, 2026-10-27, Phase 4 batch 0, task P4-00d (`docs/phase4/SCOPE.md` F8, Q10, Q13, Q17 and the rows P4-08 to P4-12; auto-approved, SCOPE Decisions D1). The simulated caller (ADR 0026) needs speech synthesis for the caller, an LLM for the LLM caller, and speech-to-text of one channel of a stereo recording that may be 8 kHz G.711. Rules 1 to 17 above keep their numbers and meaning; the rules of this section are labelled A1 to A9 so that the rule numbering of the Decision, which `test_adr0024_rules_are_tested` pins, is unchanged. Machine-read: each rule A1 to A9 and each invariant IA1 to IA4 cites at least one test name in backticks; a cited name that no test defines yet must be one that the task table of `docs/phase4/SCOPE.md` (section A) names, and that set shrinks to empty by the gate P4-G (`test_adr0024_rules_are_tested`, extended by qa in Phase 4).

A1. **TTS and LLM engines follow this ADR (P4-03, P4-08, P4-09).** The Sarvam TTS adapter and the Sarvam chat v2 adapter live in `tracer-evalproviders` behind the `TtsEngine` and `LlmEngine` protocols of `tracer-evalcore` (ADR 0026 rule 4). Rules 1 to 5, 8 to 10 and 15 to 17 apply to them as they apply to STT: no network module in the core; httpx with an injected transport; a fixed endpoint with no URL override, no redirect, TLS verified and `trust_env=False`; the key read at run time and redacted; strict reply validation with a size cap; at most 4 attempts with the backoff and the bounded `Retry-After` of rule 9; the error taxonomy of rule 10 with provider-neutral names (`Tts...`, `Llm...`); the call log; no socket in tests. Rejected: the vendor SDK (`sarvamai` declares no licence). Trade-off: three adapters to keep in step with one set of rules. Tests: `test_sarvam_tts_base_url_not_overridable`, `test_sarvam_tts_retry_taxonomy_matches_stt_rules`, `test_tts_llm_errors_hold_facts_only_and_no_chain`, `test_engines_stream_usage_before_next_request`.

A2. **The TTS request (P4-08; F8).** `POST https://api.sarvam.ai/text-to-speech` with exactly the fields `text`, `language_code`, `speaker`, `model`, `pace`, `speech_sample_rate` and `output_audio_codec`, nothing else. `model` and `speaker` are always sent and have no default in code (Q10; unlike the STT adapter's documented model default of rule 6, the caller's voice is a choice the user must make); `language_code` is `mr-IN` only, and any other language is refused before the send (BL-162, BL-278); `speech_sample_rate` equals the dialect rate of the call (ADR 0027), so nothing is resampled; `output_audio_codec` is `linear16`, or `mulaw` for the telephony dialect. A text above 2,500 characters (the documented limit for `bulbul:v3`) is refused before the send. A 200 reply must be a JSON object with a string `request_id` and an `audios` array of exactly one base64 string; the decoded bytes are capped (a named constant fixed by P4-08 from the cap on text length and the rate, stated in the CHANGELOG) and must be audio of the requested rate, one channel and the requested codec, else `TtsResponseInvalid`; which container the documented reply uses for each codec (the reviewer read "base64 WAV") is not verified and is fixed by P4-08 from the documentation and the first owner-gated reply. Rejected: the server's default model or speaker (a voice nobody chose); resampling a reply at another rate. Trade-off: a voice catalogue change at Sarvam shows up as a refused request, never a silently different voice. Tests: `test_sarvam_tts_sends_explicit_model_speaker_language_rate`, `test_sarvam_tts_refuses_non_mr_and_over_2500_chars_before_send`, `test_sarvam_tts_response_rejects_wrong_shape_and_oversize`.

A3. **The LLM request (P4-09; F8; ADR 0028).** `POST https://api.sarvam.ai/v2/chat/completions` with an explicit `model` (no default), a required `max_tokens`, the `messages` built by the prompt builder of ADR 0028, `seed` when the profile gives one, `reasoning_effort` when the profile gives one, and no `tools` and no streaming. A 200 reply must hold exactly one choice whose message content is a string, a `usage` object with integer `prompt_tokens` and `completion_tokens`, and a string id; the reply text is capped in bytes before decoding; anything else is `LlmResponseInvalid`. The seed is recorded and never claimed to make replies repeatable (the documentation says output is not guaranteed identical even at `0`). Rejected: an OpenAI-compatible client library (one more closure; compatibility not verified). Trade-off: a model rename at Sarvam is a refused request until the user names the new model. Tests: `test_sarvam_llm_model_and_max_tokens_required`, `test_sarvam_llm_response_rejects_wrong_shape_and_oversize`, `test_sarvam_llm_seed_recorded_never_claimed_deterministic`.

A4. **Several BYOK variables (ADR 0007 Decision 1).** Each provider adapter fixes the name of the one environment variable its key is read from, as a constant; Sarvam's STT, TTS and LLM adapters all read `SARVAM_API_KEY` (one key, three roles, F8), and each records `ProviderConfigRef{provider: sarvam, model: <model>, config_ref: env:SARVAM_API_KEY}` for its own model. A run reads exactly the variables of the real engines it selected, each at step 6 of ADR 0026 rule 14 and each with the checks of rule 4 (`--env-file` is read for exactly those names, no other line is parsed); a missing or empty variable for any selected real engine refuses the run before any request and before any socket. Every key is held in its own redacting wrapper, and the canary tests cover every provider and every output channel (exception, repr, logs at DEBUG, call log, store, report, recovery file, TTS cache names). Telephony variables are named by ADR 0029 at P4-40. Rejected: one generic variable for every provider (a key would be sent to the wrong provider); reading every variable that ends in `_API_KEY` (keys the run does not need would enter the process). Trade-off: a user with several providers exports several variables. Tests: `test_key_canaries_never_in_any_output_channel`, `test_key_never_in_store_and_report_outputs`, `test_refusals_happen_before_any_key_read_or_connect`.

A5. **Per-channel STT with the declared role (Q13; P4-10).** For a simulated run the STT input is channel 1 (the agent) of the stereo recording, taken sample for sample (a copy of one channel's samples, never a downmix and never a mix with channel 0). The chunk plan `tracer.chunk_plan/2` (integers only, like `tracer.chunk_plan/1`, plus the channel index and the segment rule) cuts at agent-activity segments: a segment is a maximal run of agent frames holding any non-zero sample, joined across gaps shorter than `wait_for_agent_silence_ms` (ADR 0026 rule 10), from the first sample of its first active frame to the last sample of its last active frame on the recording timeline; each segment is one chunk, and a segment longer than `max_chunk_ms` is cut inside by rule 7. Every Turn gets `role` from the declared channel map (`agent`), never inferred, `source=our_stt`, and otherwise the mapping of rule 12 with times offset by the chunk's start. Our STT never runs on channel 0 by default (the caller's text is known, ADR 0027 rule 5). Recorded mono input keeps rules 7 and 12 exactly (role `unknown`, `tracer.chunk_plan/1`). Rejected: fixed 25 s cuts on the agent channel (they cut agent replies in the middle); sending the stereo file with `accept_provider_downmix` (the caller's audio would be transcribed into the agent's turns). Trade-off: a pause shorter than the silence value inside one reply keeps the reply in one chunk; a longer pause splits it. Tests: `test_stt_agent_channel_turns_have_role_agent_from_declared_map`, `test_activity_chunk_plan_is_deterministic_and_covers_agent_audio`, `test_phase3_mono_mapping_unchanged`, `test_stt_never_runs_on_caller_channel_by_default`.

A6. **8 kHz and mu-law input.** A `twilio-media-stream/1` call carries G.711 mu-law at 8,000 Hz. The recorder decodes it with the pure ITU-T G.711 table to 16-bit PCM at 8,000 Hz (ADR 0027 rule 4), and the STT chunk is that 16-bit 8 kHz PCM in a WAV file: never resampled (BL-187), never the raw mu-law bytes. Whether Sarvam STT accepts 8 kHz is not verified: until an owner-gated check on the first real telephony-dialect call records the answer in the decision log, a real `--stt sarvam` request on an 8 kHz chunk is refused before the send, and fake engines are used in tests (BL-293). Rejected: upsampling to 16 kHz in pure Python (it invents samples and hides what was heard); sending mu-law bytes (codec support not verified). Trade-off: until the check, a telephony-dialect run has no `our_stt` transcript from Sarvam, so its agreement results are `missing_input` (`transcript`). Tests: `test_g711_mulaw_alaw_decode_matches_itu_table`, `test_recorder_refuses_rate_mismatch_never_resamples`.

A7. **Usage and cost of TTS and LLM (P4-12; ADR 0014).** Each answered request makes one UsageRecord with `domain=evaluation`, the model as requested, `provider_call_ref` the reply's request id and `occurred_at` from the reply's `Date` header (as rule 13): TTS, `stage=sim_caller_tts`, `source=measured`, quantities `input_characters` (the code points of the text sent, a count we made, since Sarvam's billing unit is not verified) and `requests` 1; LLM, `stage=sim_caller_llm`, `source=provider_reported`, quantities `input_tokens` (the reported prompt tokens minus any reported cached tokens), `cache_read_input_tokens` (only when the reply reports cached tokens), `output_tokens` and `requests` 1. A TTS cache hit makes no request and no record. A failed attempt makes no record (rule 9). Without a user USD catalog every cost is `not_available` (`no_price_for_model`), never 0; TTS and LLM prices are not verified and no INR price is converted (rule 14). Rejected: an estimate from a price page. Trade-off: the user sees counts, not money, by default. Tests: `test_sim_usage_records_per_request_with_stages`, `test_sim_cost_not_available_without_usd_catalog`, `test_sarvam_llm_usage_maps_tokens_exactly`.

A8. **One call log for a simulated run (rule 15; P4-12).** `tracer simulate` writes `sim_call_log.jsonl` in `--out` with the file rules of rule 15 (mode 0600, the directory 0700, `O_NOFOLLOW`): two lines per attempt of every engine (before the send, flushed, and after), with the stage, the attempt number, the bytes, characters or audio seconds sent, the HTTP status or transport error kind, the elapsed milliseconds and the request id, and lines for the call's connect and end (the end reason and counts). It holds no text, no number, no URL, no header and no key. Rejected: one log per engine (the order of TTS, LLM and STT requests within a call would be lost). Trade-off: a mixed log needs the stage field to read. Tests: `test_sim_call_log_has_no_text_no_number_no_key`, `test_sim_call_log_written_before_and_after_each_request`.

A9. **The content-addressed TTS cache (P4-11; Q11).** Synthesised audio is cached under `--out/tts-cache/`, keyed by the SHA-256 of the canonical JSON of exactly `{provider, model, speaker, language_code, sample_rate_hz, codec, pace, text}`; the file name is the lower-case hexadecimal key (no text in any name), the directory is 0700, files 0600, and every open uses `O_NOFOLLOW`, so a link is refused. A hit makes no request and no UsageRecord, and is validated like a reply before use (an invalid entry is a refusal, never repaired or re-fetched silently). The cache and the call log are git-ignored and refused by the guard when staged. Rejected: a cache keyed by text only (a voice change would replay the old voice); a cache outside `--out` (Tracer writes only inside the user's output directory). Trade-off: the cache grows with every distinct line; deleting it is the user's. Tests: `test_tts_cache_hit_sends_nothing_and_records_no_usage`, `test_tts_cache_key_covers_every_parameter`, `test_tts_cache_refuses_links_and_is_private`, `test_guard_rejects_staged_sim_outputs_and_allowlist`.

## Terms of service: owner gates
Stated as facts read from the terms; this is not legal advice, and the project does not decide these questions.
- **10.5(a)** forbids using "any content, data, output ... received or derived from the Offerings, to directly or indirectly develop, train, test, fine-tune or otherwise improve any machine learning algorithm or artificial intelligence system ... except as expressly permitted by us in writing". Using Sarvam's transcript to judge a voice agent's transcript can be read as testing an artificial intelligence system; whether it is barred cannot be determined here. Gate (BL-188): before the first real send the owner records either written permission from Sarvam or an explicit risk acceptance.
- **17.5**: Sarvam may train on Inputs "subject to your consent, which you may decline or withdraw". Real helpline audio could become training data unless the owner declines; how to decline is unverified. Gate (BL-189): the owner records the opt-out status, and how it was done, before the first real send.
- **10.2** concerns audio Output (speech synthesis, dubbing); STT returns text and the input audio is the owner's, so it does not appear to apply (unverified reading). **8.2**: processing and storage happen in India. **15.2**: retention is at Sarvam's discretion.
- These gates, the callers' consent status, `flag_min_confidence` and the review budget are asked one at a time in chat (P3-29), and the security audit (P3-28) must pass, before the first real send (P3-30). No code checks the terms gates; the run book does, and the decision log records the answers. Since batch G the callers' consent is also checked by code: `--stt sarvam` is refused unless `--consent obtained` with a reference and an instant (rule 16); the code checks that a statement was given, not that it is true.

## Run book for a real send (P3-30)
Preconditions from the security audit P3-28 (2026-10-26, decision log "PHASE 3 SECURITY AUDIT P3-28"; verdict: conditional GO), checked by the lead before every real send. They are procedure, not numbered rules. Batch G (revision 45) turned part of them into code checks (rules 3, 4, 15 and 16); each such step stays in the run book, and the step says what the code now enforces and what is still the lead's to check.
- Run the dry run first with exactly the arguments of the real send, `--max-chunks` included, and check the planned chunks, audio seconds, calls and the `max chunks:` line. Code: the dry run applies the ceiling, the export cap and the consent gate; it does not require `--max-chunks` (it prints `max chunks: not set` and exits 0 where the real run exits 64), so the lead checks that the line shows the value of the real send.
- `--max-chunks` is the chunk count the dry run printed for that clip, never higher. Code: required for `--stt sarvam`, at most 200, a plan over it is refused; it counts chunks, not requests (up to 4 attempts per chunk, BL-228, BL-239), so the lead still reads the call log after the send.
- Do not press Ctrl-C during the send. Code: since batch I a Ctrl-C keeps the usage of the chunks answered so far in `usage-recovery-<UTC>.json` (rule 16 (d)); still avoid it, because the run then has no store row and no report, and the chunk in flight may be billed without a record (BL-228).
- `--out` is a directory outside the repository, created beforehand with mode 0700 (`chmod 700`), and its path holds no `?`. Code: a `?` is refused (`output_path_invalid`); the location is probed and the store is opened before the send; when the command creates `--out`, the leaf directory is 0700 and the parent directories it creates follow the umask, and an existing `--out` that group or other users can reach earns one warning on stderr with its mode (since batch I; the run goes on, so the lead stops on the warning and runs `chmod 700`); a link in place of `tracer.sqlite` is refused (`store_file_is_a_link`). Still the lead's: that `--out` is outside the repository (the guard and the `.gitignore` lines are the second line of defence).
- `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `SSL_CERT_FILE` and `SSL_CERT_DIR` are unset. Code: the adapter ignores all of them (`trust_env=False`, audit F3, rule 3); the step stays as good practice for `curl` and other tools run in the same shell. A machine that needs a proxy cannot make a real send in Phase 3 (BL-237).
- The key comes from `SARVAM_API_KEY` or from an `--env-file` with mode 0600; it is never typed on the command line. Code: the env file must be a regular file of at most 64 KiB, and a group- or world-readable file prints a warning (rule 4); a warning does not stop the run, so the lead stops on it and runs `chmod 600`.
- The export of each clip is well under `ALIGN_MAX_TOKENS` (10,000 tokens). Code: an export over the cap is refused before the send (rule 16); the STT side can only be known after the send (stored and reported as not scored, exit 2), which is why "well under" stays the step.
- Send the clip with the fewest chunks first, alone, and check its result (24 kHz accepted, mr detected) before the other clip; never both at once. The ceiling refuses a plan, it does not truncate it: a one-chunk first send needs an input of one chunk.
- The real command carries `--consent obtained --consent-reference "<pointer to the consent record>" --consent-recorded-at <instant>`; for the base case the reference names the owner statement of 2026-10-25 (BACKLOG BL-213), and the instant is one the decision log records for that statement (if the log holds only the date, the lead records which instant was used and why: never a guess presented as fact). For the base case the owner accepted (2026-10-27) the instant 2026-10-25T00:00:00+05:30, midnight of the statement's date, as a date-only value (BL-213, BL-259). Record the consent source in the decision log before the send. Code: `--stt sarvam` is refused without these (rule 16); the code checks that a statement was given, not that it is true.
- Afterwards log counts only (chunks, detections per tag, usage, status), never text, and reconcile the call log with the Sarvam dashboard (BL-228). If the command printed `usage recovery: <path>` (exit 1 after the send), keep that file with the run's output, reconcile it as well, and never re-run the send to recover the result; delete it by hand with `--out` when the retention ends (BL-240).

## Ambiguities resolved
- **Ambiguity 1. Numbers the SCOPE does not give.** `search_ms` (5,000 ms), the attempt count (4), the backoff (1, 2, 4 s), the `Retry-After` bound (30 s), the timeouts (10 s and 60 s) and the body cap (1 MiB) are not in the SCOPE. **Recommendation:** these technical defaults, documented as such (not measured, not rubric values), pinned by the batch B tests and changed only with a CHANGELOG entry; `search_ms` and `max_chunk_ms` are recorded in the chunk plan because they change the output. Rejected: leaving them to the implementation (untestable).
- **Ambiguity 2. Cost reason without a catalog.** `compute_cost` needs a catalog with at least one entry. **Recommendation:** without a user catalog the pipeline writes `not_available` with `no_price_for_model` itself (the reason `compute_cost` gives when no quantity is priced), linking the usage records (ADR 0014 Decision 12, N67).
- **Ambiguity 3. Stereo.** P3-05 refuses stereo unless an explicit downmix is requested and says Sarvam merges channels. **Recommendation:** the opt-in accepts Sarvam's merge, and Tracer sends the stereo chunks unchanged (rule 7); it never computes a downmix. The flag name is the CLI contract's.
- **Ambiguity 4. Phrase times outside the chunk.** **Recommendation:** no Segment for that chunk and a Run `IngestWarning` (rule 12), rather than clamping or refusing the run; the test `test_stt_phrase_time_outside_chunk_gives_no_segment_and_a_warning` was added to the P3-09 row (SCOPE Decisions D7).
- **Ambiguity 5. Failed attempts and usage.** **Recommendation:** no UsageRecord for a failed attempt (billing unverified, rule 9); the call log keeps the attempt, and R1 asks whether Sarvam bills failures.
- **Ambiguity 7. Seconds that do not terminate (batch A, decision log "PHASE 3 BATCH A ... DELIVERED" item 2; SCOPE Decisions D8).** The earlier text said the usage seconds were the exact quotient, which cannot hold at 24 kHz. **Recommendation, accepted:** rule 13 (half-even rounding to 18 digits, stated in the record's metadata, exact frames kept in `tracer.chunk_plan/1`). Rejected: a float (inexact and banned in the cost path, ADR 0014 Decision 15a); truncation (biased downwards); dropping the quantity (the usage happened); adding a millisecond unit (a schema change, D5).
- **Ambiguity 6. Error class names.** **Recommendation:** the provider-neutral names of rule 10 (`Stt...`), so a second adapter reuses them; qa's batch B contract pins the spelling.
- **Ambiguity 8. The engine factory before the store (batch G, contract ambiguity 2; SCOPE Decisions D13).** The audit asked that the store be opened and the directory created before the engine is called. **Recommendation, accepted:** the output location is probed before the factory, the factory (key, call log) runs next, then the optional `preflight(plan)`, and the store is opened before `transcribe`, the first call that can send; so a missing key still leaves no directory behind (three existing tests pin that). Rejected: opening the store first and tolerating an empty directory after a missing key (changes three tests; the audit asked to protect the paid send, not to move the key check). What it loses: a store the probe cannot judge (a corrupt database) is found after the key was read and the call log was opened, still before any request.

## Consequences
- Any later provider adapter (a second STT engine, BL-173; a judge) follows rules 1 to 5 and 15 to 17: injected transport, fixed endpoint, key from the environment at run time, redaction, call log, no network in tests.
- Long audio costs one request per chunk; the dry run shows the count before any send, and a real Sarvam run states its own ceiling (`--max-chunks`, at most 200 chunks, rule 16).
- A user behind a corporate proxy or a TLS-inspecting middlebox cannot make a real send in Phase 3 (rule 3, BL-237).
- A Sarvam API change shows up as a typed error or a validation failure on the next real run, never as a silently different record.
- The owner gates must be answered before the first real send; until then only the offline fake runs.
- Every real send follows the run book above (audit P3-28); a failed precondition stops the send.
- Sarvam training use (terms 17.5): for the two test clips the owner decided not to opt out (2026-10-27: "This is test data, it is okay to send to sarvam."), an owner-accepted choice for test data only. Before any real-caller (production) audio is sent, training use, retention and audio storage are decided again (BL-212, BL-266).
- (Revision 47.) A later engine that wants its paid usage kept when a send is cut short declares `streams_usage` and takes `on_usage`; an engine of the older protocol is still called as before, and keeps its usage only once `transcribe` has returned.
