## Context
The framework is BYOK: every provider call uses the user's own key (ADR 0007). Phase 3 makes the first such call: Sarvam speech-to-text over REST, for the recorded-call scoring of ADR 0023. The two base-case recordings are 254.6 s and 437.2 s long, mono, 24 kHz, 16-bit PCM WAV, and they hold real people's speech. The facts below come from the Sarvam documentation retrieved on 2026-10-25 and from the 47 calls captured on 2026-10-23 (`packages/evalschema/tests/fixtures/real/sarvam-2026-10-23/`, `tools/capture/SARVAM_OBSERVATIONS.md`):
- `POST https://api.sarvam.ai/speech-to-text`, multipart form data, key in the `api-subscription-key` header; no API version anywhere; the docs default model is `saaras:v4`, and the response does not echo the model.
- The REST page is "For quick responses under 30 seconds" and sends longer audio to the Batch API (F1); what REST does above 30 s is unverified (no capture sent more than 12 s).
- A forced `language_code` is echoed, not detected; `unknown` returns a detected tag and, when speech was detected, `language_probability` (F2). Silence returns an empty transcript with a non-null tag and no probability.
- Timestamps, when requested, are phrase level; there is no word timing, no diarization on REST, no per-word confidence, no usage, no cost and no audio duration in the response (F10).
- Errors are `{"error": {"message", "code", "request_id"}}`; validation failures were 400, not the documented 422; 429 and 5xx were never observed, and no response carried `Retry-After` or rate-limit headers.
- Pricing is ₹0.49 per minute for real-time and batch STT, in INR only; rounding and a minimum charge per request are not stated (F8). Schema 0.0.1 prices in USD only (ADR 0014).

1. **The adapter boundary.** `tracer-evalcore` defines an `SttEngine` protocol (chunks in, a typed STT result or a typed failure out) and never imports a network module (`socket`, `ssl`, `http`, `urllib`, `httpx`). Provider adapters live in `tracer-evalproviders`; Sarvam is the only one in Phase 3. Provider names, URLs, form fields, error codes and language maps belong to the adapter and never enter `tracer-evalschema` or `tracer-evalcore`. `tracer-cli` selects the engine (`--stt sarvam`, or `--stt fake:<dir>`, which replays recorded responses offline). Rejected: one package with the HTTP client next to the scorers (the pure core could then open sockets); the vendor SDK (`sarvamai` declares no licence, F1). Trade-off: three packages to release and audit. Tests: `test_evalcore_imports_no_network_module`, `test_evalcore_runtime_imports_whitelist`, `test_evalproviders_runtime_imports_whitelist`, `test_cli_runtime_imports_whitelist`, `test_evalschema_does_not_import_phase3_packages`.
2. **The HTTP client (Q2; F11).** httpx in the bounded range `httpx>=0.28.1,<1`, tested at its lower bound (SCOPE Decisions D3), with its licence closure reviewed (P3-02). The adapter takes an injectable `httpx` transport; production uses the default transport, tests an `httpx.MockTransport`. Calls are sequential: one request in flight per run. Rejected: `urllib` (multipart by hand; the certificate store of uv's standalone Python on macOS unverified); `requests` (no mock transport). Trade-off: httpx has had no release since 2024-12 (watch row BL-190). Tests: `test_phase3_requires_dist_bounded_ranges`, `test_license_policy_lists_phase3_closures`.
3. **A fixed endpoint: no URL override, no redirect, TLS verified.** The base URL is the constant `https://api.sarvam.ai` and the path `/speech-to-text`; no argument, environment variable, configuration file or CLI flag changes them, and tests inject a transport, never a URL. Redirects are not followed (a redirect is an unexpected response, rule 10), so the key header is never sent to another host, and certificate verification cannot be turned off. Rejected: a base-URL setting for proxies or tests (it is the one setting that would send the key anywhere). Trade-off: a user behind a corporate proxy needs the proxy environment that httpx reads, not a Tracer setting. Tests: `test_sarvam_base_url_not_overridable`.
4. **BYOK at run time.** The key is read when the command runs, from the environment variable `SARVAM_API_KEY` or, with `--env-file <path>`, from that file, which is read for that one variable only: no other line is parsed into a value, nothing is exported into the process environment, and no error message quotes a line of the file. A missing or empty key stops the command before any request. The key is never stored: the Project records `ProviderConfigRef{provider: sarvam, model: <model>, config_ref: env:SARVAM_API_KEY}` (ADR 0007 Decision 1), a name, never a value, and never the env-file path. Rejected: a `--api-key` flag (shell history and process lists show it); keyring support in Phase 3 (a second code path before the first is audited). Trade-off: the user must export the variable or name the file each run. Tests: `test_env_file_reads_only_named_variable`, `test_missing_key_refuses_before_any_request`.
5. **The key never leaves the request header.** The adapter holds the key in a redacting wrapper whose `str`, `repr` and formatting give a fixed placeholder; the clear value is read only to build the `api-subscription-key` header of one request. No exception the adapter raises holds the key, the request or its headers: an httpx error is translated into a typed adapter error raised `from None` (no `__cause__` or `__context__` that keeps the httpx request), with the HTTP status, the Sarvam `error.code` and the request id only. The key appears in no log record at any level (the `httpx` and `httpcore` loggers included), in no call-log line (rule 15), in no record of the bundle, in the store and in the report. Rejected: relying on httpx not to log headers (a library change could start); masking only part of the key (a prefix narrows a guess). Trade-off: debugging a request means reading the call log, not the headers. Tests: `test_key_never_in_exception_str_repr_or_chain`, `test_key_never_in_logs_at_debug`, `test_key_never_in_call_log_store_or_report`.
6. **The request (Q4, Q15, Q21; BL-162).** Each chunk is one request with exactly these form fields: `file` (the chunk as a WAV file), `language_code=unknown`, `model=<model>` and `with_timestamps=true`; nothing else is sent. The model is always sent explicitly (the docs default `saaras:v4` is the adapter's default value, never left to the server), and it is recorded on the Transcript and on every UsageRecord as requested, with a metadata note that the response does not echo it. The language map is mr only: the configured language must be mr, which is sent as `unknown` so the engine observes the language (ADR 0023 rule 14); any other configured language is refused before any request (BL-162), and a forced code is never sent in the base case. Audio is sent at its native rate (24 kHz for the base case), never resampled; whether Sarvam accepts it is checked on the first chunk of the first real send (P3-30), and a refusal stops that run. Rejected: forcing `mr-IN` (echoed, not observed, F2); omitting `model` (a run could not be priced or attributed, Q15); resampling in pure Python (quality risk, BL-187). Trade-off: if the engine detects another language on a chunk, the result is not scored (ADR 0023 rule 14). Tests: `test_sarvam_request_sends_unknown_language_and_explicit_model`, `test_sarvam_request_never_sends_forced_code_in_base_case`, `test_sarvam_configured_language_other_than_mr_refused`.
7. **Chunking (Q3, Q18; F1).** The audio is cut on the client into consecutive chunks of at most `max_chunk_ms`, an adapter parameter whose documented default is 25,000 ms: a technical margin under the docs' 30 s guidance, not a rubric value and not a measured limit. Each window of at most `max_chunk_ms` that does not reach the end of the audio is cut inside its last `search_ms` (default 5,000 ms, also a technical value): the window holds `rate * max_chunk_ms // 1000` samples; the candidate frames are the whole 20 ms frames (`rate * 20 // 1000` samples each, counted from the window start) that lie entirely inside its last `search_ms`, and parameters that leave no such frame are a typed `ChunkerParameterError`, never a silent fixed cut (batch A contract, SCOPE Decisions D8); the cut frame is the one with the lowest energy (the exact integer sum of squared samples over all channels), ties going to the latest frame, and the cut falls at the frame's middle sample. The remainder up to the end of the audio is the last chunk; audio no longer than `max_chunk_ms` is one chunk. Chunks cover every sample exactly once, in order, and are written as WAV files with the input's format, so the same input gives byte-identical chunks. The chunk plan is recorded in `Transcript.metadata["tracer.chunk_plan"]` as the document `tracer.chunk_plan/1`, which holds integers only: the parameters, the rate, the channels and the sample range of each chunk, so every duration can be recomputed exactly from its frames and the rate. The chunker's `exact_seconds(frames, rate)` returns a `Decimal` only when the quotient has a finite decimal expansion, else `None`; it is never rounded and never a float. Stereo input is refused unless the caller passes `accept_provider_downmix=True` (default `False`); with it the chunks keep their channels unchanged and Sarvam merges them (docs); Tracer never computes a downmix. Input with three or more channels is always refused. Rejected: the Batch API (its upload and start REST paths are not documented and its SDK declares no licence; BL-179); fixed cuts every 25 s (words cut in half more often); a silence detector with a threshold (a number nobody measured). Trade-off: chunk boundaries can split a word; ADR 0023 rule 10 marks spans near a boundary, and P3-31 measures the effect. Tests: `test_chunker_is_deterministic`, `test_chunker_covers_every_sample_once`, `test_chunker_never_exceeds_max_chunk_ms`, `test_chunker_cuts_at_lowest_energy_frame`, `test_chunker_short_audio_is_one_chunk`, `test_chunker_stereo_is_not_downmixed_silently`.
8. **Response validation and the size cap.** The adapter reads at most 1,048,576 bytes of a response body (a technical cap; a 25 s transcript is a few kilobytes) and stops reading beyond it with a typed error. A 200 response must be a JSON object, read with the strict I-JSON rules of the schema, with `request_id` a string, `transcript` a string, `language_code` a string or null, `language_probability` absent or a number in [0, 1], and `timestamps` absent or an object of three arrays of equal length (`words` strings, `start_time_seconds` and `end_time_seconds` finite non-negative numbers, each start at most its end). Numbers are read from their JSON text as decimals, never through a float. Unknown members are kept out of every record. A body that fails any of these is a typed error and is not retried. Rejected: trusting the documented shape (the docs and the captures already differ on 400 against 422). Trade-off: a new member Sarvam adds is ignored until the adapter maps it. Tests: `test_sarvam_response_models_parse_all_captures`, `test_sarvam_response_rejects_wrong_types_and_oversize_body`.
9. **Timeouts, retries and `Retry-After`.** Timeouts are 10 s to connect and to get a pooled connection, and 60 s to write and to read (technical defaults, not measured; R1 records the real latencies). A chunk gets at most 4 attempts. Retried: HTTP 429, any 5xx, and transport errors (connect, read and write errors and the timeouts). The waits before the second, third and fourth attempts are 1 s, 2 s and 4 s, with no jitter, so a test can predict them; one run sends one request at a time, so there is no herd to spread. A `Retry-After` header on a 429 or 503, as delay-seconds or as an HTTP date measured against the response `Date`, is honoured: the wait is the larger of the backoff and the header, never less than the header asks; a value above 30 s ends the attempts for that chunk with a typed rate-limit error rather than waiting longer than the bound, and an unparseable value is ignored. No other 4xx is retried. A retried attempt is a new request; whether a failed attempt was billed is unverified, so it makes no UsageRecord, and the call log keeps every attempt. Rejected: unbounded retries (a run could spend without limit); retrying 400 or 403 (the same request fails again); random jitter (non-deterministic tests). Trade-off: a long Sarvam outage fails the run quickly instead of waiting. Tests: `test_sarvam_retries_429_and_503_then_succeeds`, `test_sarvam_gives_up_after_bounded_retries`, `test_sarvam_does_not_retry_400_403`, `test_sarvam_honours_bounded_retry_after`.
10. **The error taxonomy (from the 2026-10-23 captures).** The adapter decides on the HTTP status and on `error.code`, never on the message text, which can echo input. Every error carries the chunk index, the HTTP status (or the transport error kind), the `error.code` when it is a short machine key (else `unrecognised`) and the request id; never the message, the body, the key or the audio.

   | Error | When | Captures | Retried |
   |---|---|---|---|
   | `SttAuthError` | 401 or 403, or `error.code=invalid_api_key_error` | `err_bad_key` | no; the run stops before the next chunk |
   | `SttRequestRejected` | 400, 422 or any other 4xx except 429, for example `invalid_request_error` | `err_invalid_language_code`, `err_underscore_language_code`, `err_no_file`, `err_not_audio`, `err_empty_file` | no |
   | `SttRateLimited` | 429 after the last attempt, or a `Retry-After` above the bound | none (never observed) | yes, within rule 9 |
   | `SttServerError` | 5xx after the last attempt | none (never observed) | yes, within rule 9 |
   | `SttTransportError` | connect, read or write error or timeout after the last attempt | none | yes, within rule 9 |
   | `SttResponseInvalid` | a 200 body that fails rule 8, a body over the cap, a non-JSON content type, a 1xx or 3xx status | none | no |

   The class names are the recommendation; the batch B contract written by qa pins the final spelling. Rejected: matching message text (it changes and can echo input); one generic error (the CLI could not tell a bad key from an outage). Trade-off: a new Sarvam error code maps by its status until the table is extended. Tests: `test_sarvam_error_taxonomy_matches_captures`, `test_sarvam_does_not_retry_400_403`.
11. **All or nothing (Q14).** A run's STT transcript exists only if every chunk succeeded. When any chunk fails after its attempts, the adapter returns a typed failure and no Transcript, no Turn and no Segment is built from the chunks that succeeded; the pipeline then records the failure as ADR 0004 Decision 10 states (`missing_input` `["transcript"]`, a Run `IngestWarning`, a non-zero exit). The UsageRecords of the chunks that succeeded are kept, because that usage happened (rule 13). Rejected: a partial transcript (its missing chunks would read as deletions in the export, ADR 0023); `error` (the input never existed). Trade-off: one failed chunk discards the paid text of the others. Tests: `test_sarvam_partial_chunk_failure_yields_no_transcript`, `test_stt_failure_is_missing_input_with_warning_and_nonzero_exit`.
12. **Mapping to records (Q16; P3-09).** One Transcript: `source=our_stt`, `provider=sarvam`, `model` as requested, `timeline_origin` the audio artifact, no `provider_call_ref` (it took several calls), and `detected_language` only when every non-empty chunk returned the same tag (ADR 0023 rule 14). One Turn per non-empty chunk, in chunk order: `role=unknown`, `source=our_stt`, `text` the transcript verbatim, `language` from the returned code through `normalize_language_label` (the raw label kept when it does not normalise, ADR 0005), `language_probability` copied into `Turn.metadata` as a canonical decimal string when present, and Segments from the phrase timestamps, offset by the chunk's start. Times follow the F3 floor rule of the Phase 1 mapper (`seconds_to_ms_floor`), computed from the exact chunk start (its first sample divided by the rate) plus the decimal seconds of the response; timing is `audio_alignment` from those Segments, or `none` when the response has no timestamps; a phrase that ends after its chunk's exact duration is not mapped to a Segment for that chunk (its Turn gets timing `none`) and the Run records an `IngestWarning`, so no time is moved or invented. A chunk whose transcript is empty or white space only makes no Turn, and the transcript metadata counts it and lists its index; the non-null tag the engine returns for silence is not a detection and is not recorded as one (captures `stt_silence_unknown`, `stt_silence_forced_hi`). Rejected: a Turn with empty text (it would read as a statement that nothing was said in a known language); clamping out-of-range phrase times (a fabricated time). Trade-off: a chunk of pure silence leaves no trace in the turns, only in the metadata. Tests: `test_stt_transcript_maps_one_turn_per_nonempty_chunk`, `test_empty_chunk_makes_no_turn_and_is_counted`, `test_stt_turn_language_is_observed_from_unknown_request`, `test_stt_segments_offset_by_chunk_start`, `test_detected_language_set_only_when_all_chunks_agree`, `test_stt_phrase_time_outside_chunk_gives_no_segment_and_a_warning`.
13. **Usage (Q19; ADR 0014).** Each successful chunk gives one UsageRecord: `domain=evaluation`, `stage=stt`, `provider=sarvam`, `model` as requested, `provider_call_ref` the response `request_id` (`ExternalRef{system: sarvam, kind: request_id, value}`), `source=measured`, `raw` null, and the quantities `audio_input_seconds` and `requests` 1. `audio_input_seconds` is the chunk's duration, frames divided by rate. That quotient has no finite decimal expansion for most chunks at 24 kHz (1/24000 does not terminate), and a `DecimalString` holds at most 18 fractional digits (ADR 0014 Decision 1), so the value is the quotient rounded half to even to 18 fractional digits, in canonical form. The rounding is stated, never hidden: every such UsageRecord carries `metadata["tracer.audio_seconds_rounding"]`, the short machine key `half_even_18` when rounding changed the value and `exact` when the quotient fits in 18 fractional digits; the exact frame count and rate stay in the chunk plan (rule 7). The rounding error is below 10^-18 s per chunk, far below any billing unit. `occurred_at` is the instant of the response's HTTP `Date` header, the source's own statement; it is absent when the header is missing or does not parse, and never the time of the run, the ingest or the local clock. The billable seconds are unknown (Sarvam's rounding and minimum are unstated, F8); the record states what was sent, from exact frame counts. The usage of our STT is evaluation usage and never makes the input kind `usage` available (ADR 0004 Decision 2). Rejected: the local clock for `occurred_at` (a time the source did not state, ADR 0014 Decision 8); the response body in `raw` (it holds call text, which is personal data). Trade-off: a missing `Date` header leaves the price date to the catalog rules. Tests: `test_usage_record_per_chunk_measured_seconds_exact`, `test_usage_audio_seconds_rounded_half_even_18_digits_and_stated`, `test_usage_raw_never_holds_transcript_text`.
14. **Cost (F8; ADR 0014).** Without a user-supplied USD pricing catalog, every chunk's CostRecord is `not_available` with `na_reason=no_price_for_model` and its usage record listed, and the CostSummary has no total: never an amount of 0. With a user catalog (a file the user writes, whose entries carry a `note` naming the source of each USD price and the billing rules), cost is computed by the evalschema pricing functions, and an entry with `billing: "unknown"` gives `billing_rules_missing`. Tracer never enters the INR price into a catalog, never converts INR to USD and never derives a USD price. Rejected: converting INR at a rate (no FX in 0.0.1, ADR 0014 Decision 4); an estimate from the audio length (an unearned number). Trade-off: by default the CLI shows usage and `not_available`. Tests: `test_cost_not_available_without_usd_catalog`, `test_cost_computed_with_user_usd_catalog`, `test_cost_never_zero_when_unpriced`, `test_inr_price_never_converted`.
15. **The call log.** Every attempt writes two JSON lines to a local call log inside the required `--out` directory (Q17), file mode 0600: one before the request is sent, flushed before sending, and one after the response or the error. A line holds only: the UTC timestamp, `before` or `after`, the chunk index, the attempt number, the bytes sent, the chunk's audio seconds (a decimal string), the HTTP status or the transport error kind, the elapsed milliseconds and the request id. It holds no transcript text, no error message, no header, no key and no file path. Report HTML, store files and call logs are git-ignored, and the extended guard refuses them when staged (P3-34). Rejected: logging response bodies (call text); logging only after a send (a crash mid-request would leave no trace of a billable call). Trade-off: two lines per attempt. Tests: `test_call_log_has_no_text_no_key`, `test_call_log_written_before_and_after_each_send`, `test_guard_rejects_staged_report_store_and_call_log`.
16. **The dry run.** `tracer score --dry-run` reads the inputs, builds the chunk plan and prints the number of chunks, the audio seconds and the number of calls, and a cost only when the user supplied a USD price; it reads no key and opens no connection. Rejected: an estimate from the INR price (rule 14). Trade-off: none. Tests: `test_dry_run_sends_nothing_and_prints_plan`.
17. **No network in tests.** Unit tests of the three Phase 3 packages (`tracer-evalcore`, `tracer-evalproviders`, `tracer-cli`) never open a socket: the test configuration of each of them patches `socket.connect` (and the async equivalents httpx uses) to fail (revision 43, batch F ambiguity 4; the earlier text said every package), and the Sarvam tests replay the 2026-10-23 captures or scripted bodies through `httpx.MockTransport`. A real send is a separate, owner-gated step (P3-30), never a test. `tracer-evalschema` and `tracer-evaldb` are not guarded: neither holds a provider adapter or a key, and the Postgres tests of `tracer-evaldb` need a socket to reach their test server (a later guard that allows only that server is BL-221). Rejected: recorded HTTP cassettes that fall back to the network (a missing cassette would send the key); guarding all five packages (the evaldb Postgres parity tests would fail, or the guard would need a per-test exception that weakens it). Trade-off: real-API drift is caught by the owner-gated runs only, dated by their retrieval dates; a socket opened by an evalschema or evaldb unit test would go unnoticed until BL-221. Tests: `test_unit_tests_open_no_socket`, `test_cli_fake_stt_runs_offline`.

## Terms of service: owner gates
Stated as facts read from the terms; this is not legal advice, and the project does not decide these questions.
- **10.5(a)** forbids using "any content, data, output ... received or derived from the Offerings, to directly or indirectly develop, train, test, fine-tune or otherwise improve any machine learning algorithm or artificial intelligence system ... except as expressly permitted by us in writing". Using Sarvam's transcript to judge a voice agent's transcript can be read as testing an artificial intelligence system; whether it is barred cannot be determined here. Gate (BL-188): before the first real send the owner records either written permission from Sarvam or an explicit risk acceptance.
- **17.5**: Sarvam may train on Inputs "subject to your consent, which you may decline or withdraw". Real helpline audio could become training data unless the owner declines; how to decline is unverified. Gate (BL-189): the owner records the opt-out status, and how it was done, before the first real send.
- **10.2** concerns audio Output (speech synthesis, dubbing); STT returns text and the input audio is the owner's, so it does not appear to apply (unverified reading). **8.2**: processing and storage happen in India. **15.2**: retention is at Sarvam's discretion.
- These gates, the callers' consent status, `flag_min_confidence` and the review budget are asked one at a time in chat (P3-29), and the security audit (P3-28) must pass, before the first real send (P3-30). No code checks the gates; the run book does, and the decision log records the answers.

## Run book for a real send (P3-30)
Preconditions from the security audit P3-28 (2026-10-26, decision log "PHASE 3 SECURITY AUDIT P3-28"), checked by the lead before every real send. They are procedure, not numbered rules; where a precondition becomes code (batch G: `trust_env=False`, a chunk cap, the consent gate), the code check is added on top and the step stays in the run book.
- Run the dry run first with exactly the arguments of the real send, and check the planned chunks, audio seconds and calls.
- `--out` is a directory outside the repository, created beforehand with mode 0700 (`chmod 700`), and its path holds no `?`.
- `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `SSL_CERT_FILE` and `SSL_CERT_DIR` are unset until the adapter ignores the environment (`trust_env=False`, audit F3); otherwise audio and key could be routed through a middlebox.
- The key comes from `SARVAM_API_KEY` or from an `--env-file` with mode 0600; it is never typed on the command line.
- The export of each clip is well under `ALIGN_MAX_TOKENS` (10,000 tokens), so the run cannot fail after the paid transcription.
- Send the clip with the fewest chunks first, alone, and check its result (24 kHz accepted, mr detected) before the other clip; never both at once.
- Record the consent source ("owner statement 2026-10-25", BACKLOG BL-213) in the decision log before the send.
- Afterwards log counts only (chunks, detections per tag, usage, status), never text, and reconcile the call log with the Sarvam dashboard (BL-228).

## Ambiguities resolved
- **Ambiguity 1. Numbers the SCOPE does not give.** `search_ms` (5,000 ms), the attempt count (4), the backoff (1, 2, 4 s), the `Retry-After` bound (30 s), the timeouts (10 s and 60 s) and the body cap (1 MiB) are not in the SCOPE. **Recommendation:** these technical defaults, documented as such (not measured, not rubric values), pinned by the batch B tests and changed only with a CHANGELOG entry; `search_ms` and `max_chunk_ms` are recorded in the chunk plan because they change the output. Rejected: leaving them to the implementation (untestable).
- **Ambiguity 2. Cost reason without a catalog.** `compute_cost` needs a catalog with at least one entry. **Recommendation:** without a user catalog the pipeline writes `not_available` with `no_price_for_model` itself (the reason `compute_cost` gives when no quantity is priced), linking the usage records (ADR 0014 Decision 12, N67).
- **Ambiguity 3. Stereo.** P3-05 refuses stereo unless an explicit downmix is requested and says Sarvam merges channels. **Recommendation:** the opt-in accepts Sarvam's merge, and Tracer sends the stereo chunks unchanged (rule 7); it never computes a downmix. The flag name is the CLI contract's.
- **Ambiguity 4. Phrase times outside the chunk.** **Recommendation:** no Segment for that chunk and a Run `IngestWarning` (rule 12), rather than clamping or refusing the run; the test `test_stt_phrase_time_outside_chunk_gives_no_segment_and_a_warning` was added to the P3-09 row (SCOPE Decisions D7).
- **Ambiguity 5. Failed attempts and usage.** **Recommendation:** no UsageRecord for a failed attempt (billing unverified, rule 9); the call log keeps the attempt, and R1 asks whether Sarvam bills failures.
- **Ambiguity 7. Seconds that do not terminate (batch A, decision log "PHASE 3 BATCH A ... DELIVERED" item 2; SCOPE Decisions D8).** The earlier text said the usage seconds were the exact quotient, which cannot hold at 24 kHz. **Recommendation, accepted:** rule 13 (half-even rounding to 18 digits, stated in the record's metadata, exact frames kept in `tracer.chunk_plan/1`). Rejected: a float (inexact and banned in the cost path, ADR 0014 Decision 15a); truncation (biased downwards); dropping the quantity (the usage happened); adding a millisecond unit (a schema change, D5).
- **Ambiguity 6. Error class names.** **Recommendation:** the provider-neutral names of rule 10 (`Stt...`), so a second adapter reuses them; qa's batch B contract pins the spelling.

## Consequences
- Any later provider adapter (a second STT engine, BL-173; a judge) follows rules 1 to 5 and 15 to 17: injected transport, fixed endpoint, key from the environment at run time, redaction, call log, no network in tests.
- Long audio costs one request per chunk; the dry run shows the count before any send.
- A Sarvam API change shows up as a typed error or a validation failure on the next real run, never as a silently different record.
- The owner gates must be answered before the first real send; until then only the offline fake runs.
- Every real send follows the run book above (audit P3-28); a failed precondition stops the send.

## Invariants (testable)
- I1. The pure core opens no network and imports no network module; adapters hold every provider detail. Tests: `test_evalcore_imports_no_network_module`, `test_evalschema_does_not_import_phase3_packages`.
- I2. The endpoint cannot be overridden and the request sends exactly the four fields, with `language_code=unknown` and an explicit model. Tests: `test_sarvam_base_url_not_overridable`, `test_sarvam_request_sends_unknown_language_and_explicit_model`, `test_sarvam_request_never_sends_forced_code_in_base_case`.
- I3. The key is read at run time only, refused when missing, and appears in no exception, log, call log, record, store or report. Tests: `test_missing_key_refuses_before_any_request`, `test_env_file_reads_only_named_variable`, `test_key_never_in_exception_str_repr_or_chain`, `test_key_never_in_logs_at_debug`, `test_key_never_in_call_log_store_or_report`.
- I4. Chunks are deterministic, cover every sample once and never exceed `max_chunk_ms`. Tests: `test_chunker_is_deterministic`, `test_chunker_covers_every_sample_once`, `test_chunker_never_exceeds_max_chunk_ms`.
- I5. Retries are bounded and deterministic, honour `Retry-After` within its bound, never repeat a 400 or 403, and errors follow the taxonomy. Tests: `test_sarvam_retries_429_and_503_then_succeeds`, `test_sarvam_gives_up_after_bounded_retries`, `test_sarvam_does_not_retry_400_403`, `test_sarvam_honours_bounded_retry_after`, `test_sarvam_error_taxonomy_matches_captures`.
- I6. The transcript is all or nothing, and empty chunks make no Turn. Tests: `test_sarvam_partial_chunk_failure_yields_no_transcript`, `test_empty_chunk_makes_no_turn_and_is_counted`.
- I7. Usage is measured per chunk from exact frame counts, with any rounding to 18 fractional digits stated, and no text; cost is `not_available` without a USD catalog, never 0, and INR is never converted. Tests: `test_usage_record_per_chunk_measured_seconds_exact`, `test_usage_audio_seconds_rounded_half_even_18_digits_and_stated`, `test_usage_raw_never_holds_transcript_text`, `test_cost_not_available_without_usd_catalog`, `test_cost_never_zero_when_unpriced`, `test_inr_price_never_converted`.
- I8. The call log holds no text and no key and is written before and after each send; the unit tests of the three Phase 3 packages open no socket. Tests: `test_call_log_has_no_text_no_key`, `test_call_log_written_before_and_after_each_send`, `test_unit_tests_open_no_socket`.
- I9. Every numbered rule and every invariant cites a test. Test: `test_adr0024_rules_are_tested`.
