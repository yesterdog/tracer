# ADR 0021: Store schema version and migration policy

## Context
The stored documents are evalschema 0.0.1 documents, and a reader requires an exact version match while the schema is `0.0.x` (ADR 0008 Decision 2). The digest domain excludes `schema_version` and null members (ADR 0006 Decision 5), so a content-preserving schema upgrade can keep every content digest. `(id, version)` is immutable (ADR 0009 Decision 2), and records of fact are never edited. Alembic manages the DDL; SQLite changes most constraints only by recreating a table (batch mode), which can drop triggers or `STRICT` and, with foreign keys on, cascade-delete child rows.

## Decision
Machine-read by `test_adr0021_policy_rules_are_tested`: every numbered rule cites at least one existing test name.

1. **One schema version per database.** A store holds documents of exactly one evalschema version. `tracer_meta` records it (`schema_version`) and the evaldb version of the last migration (`evaldb_version`), in one row. Every entity table pins `schema_version` with a CHECK whose literal is written into the DDL of the revision that created it (`= '0.0.1'` for revision `0001`). A document of another version cannot be inserted. Tests: `test_tracer_meta_records_schema_version`, `test_schema_version_check_pinned_to_0_0_1`, `test_mixed_schema_versions_in_one_database_rejected`.
2. **The pin of the stored data.** `tracer-evaldb` depends on `tracer-evalschema==0.0.1` exactly; the other runtime dependencies are bounded ranges tested at their lower bounds (ADR 0019 Decision 1). evaldb never changes evalschema. Tests: `test_evaldb_requires_dist_bounded_ranges`, `test_evalschema_unchanged_since_phase1_gate`.
3. **`open_store` never migrates.** `open_store(engine)` checks, before any read or write: the Alembic revision is the head this evaldb ships (an empty database or an older revision is `StoreNotMigrated`; a revision this evaldb does not know is `StoreRevisionUnknown`); then `tracer_meta.schema_version` against the installed `SCHEMA_VERSION` (newer is `StoreSchemaVersionTooNew`, older is `StoreSchemaVersionMismatch`, ADR 0008 Decision 2). It never upgrades, downgrades or repairs a database by itself. Tests: `test_open_store_refuses_unmigrated_database`, `test_open_store_never_auto_migrates`, `test_open_store_newer_schema_version_raises_too_new`, `test_open_store_older_schema_version_raises_mismatch`.
4. **Migrations are explicit and programmatic.** `upgrade(engine, revision="head")` and `downgrade(engine, revision, *, allow_data_loss=False)` are the API; a CLI command calls them. The migration environment takes the engine from the caller; `alembic.ini` holds no database URL and no credential. Tests: `test_programmatic_upgrade_api`, `test_alembic_ini_holds_no_database_url`.
5. **Hand-written revisions; autogenerate as a drift check only (Q29).** Each revision is written and reviewed by hand. At head, Alembic's `compare_metadata` between the migrated database and `MetaData` is empty on both backends, and CI runs `alembic check` against a fresh SQLite database. Test: `test_alembic_head_matches_metadata_exactly`.
6. **Migrations ship with the package.** The revisions live in `tracer_evaldb/migrations` and ship in the wheel; the wheel holds no test. Tests: `test_migrations_ship_in_wheel`, `test_evaldb_wheel_contains_migrations_and_no_tests`.
7. **SQLite: foreign keys off during a migration (Q28).** A migration on SQLite sets `PRAGMA foreign_keys=OFF` outside a transaction, runs its revision steps (batch mode, `render_as_batch=True`) in a transaction, runs `PRAGMA foreign_key_check` (any row reported fails the migration and rolls it back), then sets `PRAGMA foreign_keys=ON`. A batch table recreate therefore never cascades into child rows, and it re-creates `STRICT`, `WITHOUT ROWID` and the immutability triggers of the table. Tests: `test_sqlite_batch_migration_preserves_child_rows`, `test_sqlite_batch_migration_preserves_strict_and_triggers`.
8. **Postgres migrations are transactional.** Each revision runs in one transaction; a failing step leaves the database at the previous revision. Test: `test_postgres_migration_is_transactional`.
9. **Rewriting rows inside a migration.** The immutability triggers refuse every UPDATE (ADR 0020 Decision 7). A data migration that must change stored rows drops the triggers of the tables it rewrites, rewrites them and creates the triggers again, all inside the revision's transaction, so no committed state lacks a trigger; on SQLite a table whose CHECK literal changes is recreated by batch mode, which re-creates its triggers (rule 7). Tests: `test_immutability_triggers_exist_after_migrations`, `test_fake_data_migration_rewrites_schema_version_and_preserves_digests`.
10. **A schema version move is a data migration.** Moving a store from 0.0.1 to a later version `V` is one revision that, in one transaction: reads every `doc` through the strict loader; calls the pure evalschema upgrade step for its entity (ADR 0008 Decision 5); validates the result with the models of `V`; writes the new `doc`, `doc_sha256` and projections; rewrites the `schema_version` column and its CHECK literal; and sets `tracer_meta.schema_version` to `V`. A content-preserving upgrade only rewrites `schema_version`, so every content digest is unchanged (it is outside the digest domain). Test: `test_fake_data_migration_rewrites_schema_version_and_preserves_digests`.
11. **A digest-changing upgrade of digested content is refused.** If the upgraded document of a versioned entity, or of a `ConfigSnapshot`, has a different `content_digest` (or a recomputed digest that differs), the migration raises a typed error and rolls back, because it would change the content of an immutable `(id, version)` or of a snapshot that runs cite. Such a schema change needs its own owner-level decision when it arises. Test: `test_digest_changing_upgrade_of_versioned_entity_refused`.
12. **Downgrades are byte-exact or refused.** Every data migration has a downgrade that restores every stored byte (`doc`, `doc_sha256`, projections, `tracer_meta`) exactly, or raises the typed `IrreversibleMigration` before changing anything. Test: `test_fake_data_migration_downgrade_restores_bytes_exactly`.
13. **Data loss needs an explicit flag.** A downgrade that would drop tables or columns holding rows refuses unless `allow_data_loss=True` is passed; downgrading an empty database needs no flag. Test: `test_downgrade_base_on_populated_db_requires_explicit_data_loss_flag`.
14. **Every revision passes the stairway.** On both backends, on an empty and on a populated database, each revision goes up, down and up again with the same schema and the same rows. Test: `test_migration_stairway_up_down_up`.
15. **The fake 0.0.2 migration is a test fixture.** The data migration that proves rules 10 to 12 is a test-only revision with a test-only upgrade step that rewrites `schema_version` to `0.0.2`; it is never shipped in the wheel and never registered in the package's migration chain. Tests: `test_fake_data_migration_rewrites_schema_version_and_preserves_digests`, `test_evaldb_wheel_contains_migrations_and_no_tests`.

## Ambiguities resolved
- **Ambiguity 1. Triggers against data migrations.** SCOPE requires both the immutability triggers and a data migration that rewrites `doc`. **Recommendation:** rule 9 (drop and recreate inside the transaction). Rejected: a migration-only session flag that the trigger reads (a second path around immutability that raw SQL could also set); copying every table to a new one (doubles the storage of a large store).
- **Ambiguity 2. Digested records of fact.** SCOPE names versioned entities only. **Recommendation:** rule 11 also covers `ConfigSnapshot`, the one digested record of fact, because runs cite its digest.
- **Ambiguity 3. A database newer than the installed evaldb.** **Recommendation:** an unknown Alembic revision is `StoreRevisionUnknown`, separate from the schema-version errors, so an operator sees which of the two is ahead (rule 3).
- **Ambiguity 4. What `evaldb_version` means.** **Recommendation:** the evaldb version that ran the last migration, written by migrations only; `open_store` does not compare it (the Alembic revision and `schema_version` decide), so a patch release of evaldb without a migration opens an existing store.
- **Ambiguity 5. The error names.** The names in rules 3 and 12 (`StoreNotMigrated`, `StoreRevisionUnknown`, `StoreSchemaVersionTooNew`, `StoreSchemaVersionMismatch`, `IrreversibleMigration`) are the recommendation; the Phase 2 API contract written by qa pins the final spelling, and none of them names a value or the URL.

## Rejected alternatives
- **Mixed schema versions per row (Q15).** It needs several model versions in one interpreter and makes every query version-aware.
- **Automatic migration on open (Q15).** A reader could change a shared database without an operator's decision, and a downgrade could not be planned.
- **Autogenerated migrations (Q29).** They miss triggers, CHECK literals and SQLite batch details, and would ship unreviewed DDL.
- **SQLite migrations with foreign keys on (Q28).** A batch-mode table recreate drops the old table, and `ON DELETE CASCADE` then deletes the child rows.
- **Rewriting digests during an upgrade.** It changes the content of an immutable `(id, version)` and breaks every reference that pinned it.

## Consequences
- Upgrading evalschema means a new evaldb release with a data migration; there is no in-place reading of older documents.
- A schema change that would change the content digests of stored versioned entities cannot be migrated in place; schema changes are designed around this (SCOPE section 5).
- An operator runs `upgrade` explicitly after installing a new evaldb; until then `open_store` refuses the database with a typed error.
