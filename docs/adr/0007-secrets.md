## Context
The framework is BYOK: every STT/TTS/LLM call uses the user's own keys. Schema objects are serialized into databases, bundles, exports, logs and fixtures. If any schema field can hold a credential, it eventually will, and it will leak through an export or a public fixture. Secrets also arrive unintentionally: inside `metadata`, endpoint URLs (`wss://host/?token=...`), presigned artifact URLs, telemetry attributes and tool arguments.

## Decision
1. **No secret-bearing fields.** No model has a field meant to hold a credential. Providers are referenced through `ProviderConfigRef{provider, model, config_ref}`. `config_ref` is an opaque reference (for example `env:SARVAM_API_KEY`, `keyring:...`, `vault:...`) that a runtime outside the schema resolves. **Shape (P-19):** a `MachineKey` of the form `<scheme>:<name>`; values containing `=` or matching known key prefixes (`sk-`, `AKIA`, ...) are rejected, so a pasted key cannot hide in an innocently named field. **Revision 30 (P1-21 finding m6, A6):** the name part after the first `:` is also checked with the high-entropy rule of Decision 5a (a run of 32 or more of `[A-Za-z0-9+/=_-]` with an upper-case letter, a lower-case letter and a digit, and 16 distinct characters), for every scheme (`env`, `vault`, `keyring` and any other); the known-prefix rule still covers the whole value, scheme included. One error type `config_ref_credential` and one message for both rules, nothing quoted. Upper-case and lower-case names (`env:OPENAI_API_KEY`, `keyring:tracer/sarvam`, `vault:secret/data/tracer/sarvam`) and mixed-case names under 32 characters stay valid. **Revision 8:** a `ProviderConfigRef` is used where tracer itself calls a provider with the user's key, and it is held by the Project: `Project.provider_configs` is unique per `(provider, model)`. A record that only names a model, for example a metric definition's judge (`ModelRef{provider, model}`, ADR 0010 Decision 1a) or an agent's declared stack, carries no `config_ref`. The run resolves such a model to the Project entry with the same pair. A missing entry is a configuration error before the run starts, never a guess.
2. **`extra="forbid"`** on every model. An unexpected `api_key` field is a validation error, not an ignored field.
3. **Secret-field walk.** A contract test walks every model and JSON Schema property name and fails on a denylist of credential names (`api_key`, `apikey`, `secret`, `password`, `passwd`, `private_key`, `access_token`, `refresh_token`, `auth_token`, `bearer`, `authorization`, `credential(s)`, `client_secret`). The denylist matches whole name components, so usage units such as `input_tokens` are not flagged.
4. **Keys for sealing and for keyed digests** are referenced by `KeyRef{key_id, key_version?, provider_hint?}` (ADR 0006, ADR 0015). A KeyRef never carries key material. **Revision 30 (P1-21 finding C3b; closes ADR 0015 S-N83):** `key_id` and `key_version` reject a credential-shaped value (`credentials.key_ref_looks_like_credential`): a Decision 5a known prefix anywhere (also after `/`, `:` or `_`), any `=` (A2), or a high-entropy run inside one segment of the value split at `/` and `:` (A5, so GCP KMS resource names, ARNs and URN-like ids stay valid). 32 or 40 hexadecimal digits in one letter case are names, not keys (A1: a 40-digit OpenPGP fingerprint). The error type is `key_ref_credential`, located at the field, with one message for every rejected value and no context: no part of the value is quoted. `provider_hint` has no credential rule (A8). The rule is a heuristic, code-only (no JSON Schema change).
5. **Metadata.** `EntityBase.metadata` is user-owned JSON. A value that looks like a secret (high-entropy token, known key prefixes) is **preserved and flagged**, never silently dropped or altered, because silent mutation is data loss and hides the problem. Redaction is a Phase 3 feature (A-03 is a known gap with an owner). **Where the flag lives (P-21):** a serialized `EntityBase.metadata_flags[]` of `MetadataFlag{path, reason}` value objects, computed at validation and verified on load like `contains_bidi_controls` (a stored list that disagrees with the computed one is rejected), so a recipient of an export can see that a value was flagged and a later redaction can be audited against it. **Revision 28 (2026-10-24, adversarial finding 1, auto-approved; qa batch 20):** `metadata` is an **I-JSON object** (RFC 7493; type `ijson.IJsonObject`): NaN, infinities, integers outside +-(2**53 - 1), lone surrogates in strings or keys, non-string keys and Python values that are not JSON are rejected, with an error that names the JSON Pointer of the member and never its value. Before, NaN was accepted and dumped as `null`, a silent change of user data that this decision forbids; finite floats stay valid. The flagging rule of 5a is unchanged. The models bound no depth of Python objects (a 5,000-deep dict passed to `model_validate` raises `RecursionError`); only the JSON-text loader bounds depth (256). No length limit on `metadata` in 0.0.1 (the loader's 256 MiB is the bound; revisited with the Phase 2 storage limits). See `SCHEMA_POLICY.md` sections 2.9 and 11.
5a. **The flagging rule, exactly (revision 7).** The rule decides which documents load (flags are verified), so it is part of the schema version: changing it is a schema change recorded in the CHANGELOG, and from 0.1.0 `upgrade()` recomputes the flags. It uses integer and pattern logic only, so any language computes the same list.
   - **Scope:** every JSON string at any depth of `metadata` (object member values and array elements). Keys, numbers, booleans and nulls are never flagged.
   - **Reason `known_credential_prefix`:** the string contains a match of one of these patterns, starting at the beginning of the string or after a character outside `[A-Za-z0-9]`: `sk-[A-Za-z0-9_-]{20,}`; `(sk|rk)_(live|test)_[A-Za-z0-9]{16,}`; `(AKIA|ASIA)[0-9A-Z]{16}`; `AIza[0-9A-Za-z_-]{35}`; `gh[pousr]_[A-Za-z0-9]{36,}`; `github_pat_[A-Za-z0-9_]{22,}`; `glpat-[A-Za-z0-9_-]{20,}`; `xox[abpors]-[A-Za-z0-9-]{10,}`; `hf_[A-Za-z0-9]{30,}`; `eyJ[A-Za-z0-9_-]{10,}\.eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]*` (JWT); `-----BEGIN [A-Z ]*PRIVATE KEY-----`. The same list is used by the `config_ref` check of Decision 1 (P-19). The patterns are our definition. Their match with each vendor's current key format is not verified.
   - **Reason `high_entropy_token`:** the string contains a maximal run of characters from `[A-Za-z0-9+/=_-]` of length >= 32 that holds at least one upper-case ASCII letter, one lower-case ASCII letter and one digit, and at least 16 distinct characters. Lower-case hex digests and our own IDs are not flagged; long CamelCase identifiers may be (a harmless false positive: the value is never changed).
   - **One flag per path:** if both reasons match, the reason is `known_credential_prefix`.
   - **Path syntax:** an RFC 6901 JSON Pointer from the entity document root (`/metadata/note`, `/metadata/nested/token`, `/metadata/items/0`), with `~` escaped as `~0` and `/` as `~1`.
   - **Order:** sorted by path, comparing UTF-16 code units (the order JCS uses for keys), so the serialized list and the digest are canonical.
   - **Load rule:** an omitted `metadata_flags` is computed. A supplied list must equal the computed list exactly (entries, reasons and order); anything else is a `ValidationError`. Test (golden for the rule): `test_metadata_flag_rule_golden`.
6. **URLs (P-20):** `AgentTarget` endpoints and `Artifact.uri` reject URLs with userinfo (`user:pass@`) and known credential query parameters (`token`, `key`, `api_key`, `X-Amz-Signature`, `X-Amz-Credential`, `sig`, `signature`). Presigned URLs are runtime-only and never stored. (Revision 9: the parameter list is widened, and a pattern rule is added, by P-60 in Decision 6b.) (Revision 12: the scheme set, `file:` URIs and fragments of `Artifact.uri` were decided by the owner, O5 option A; exact rules in Decision 6c.)
6a. **Exact URL rules (revision 8, batch 2 item 9).**
   - **ws and webrtc.** An absolute RFC 3986 URI, ASCII only, with no white space or control characters. The scheme is lowercase: `ws`/`wss` for ws, `http`/`https` for webrtc (the signalling endpoint). A host is required. Any userinfo (an `@` inside the authority, which ends at the first `/`, `?` or `#`) is rejected, while an `@` in the path is not userinfo. A fragment is rejected (RFC 6455 section 3 for ws; a signalling endpoint never uses one).
   - **sip.** `sip:`/`sips:` (lowercase) with a host. In SIP the user part is the address (`sip:1001@pbx`) and is allowed. A password, meaning a `:` in the userinfo before `@` (also percent-encoded as `%3A`), is rejected. Decision 6's "userinfo (user:pass@)" is read this way for SIP.
   - **Parameter names.** Checked in the query (ws, webrtc), and in SIP `;uri-parameters` and `?headers`. The text is split at `&` and `;`. A name is the text before the first `=`. It is percent-decoded as UTF-8 (a malformed escape or invalid UTF-8 rejects the URL), case-folded (`str.casefold()`), and compared as a whole name with the name set of Decision 6b (revision 9; in revision 8 the Decision 6 list), with `-` and `_` treated as equal (revision 10, N15; exact rule in 6b). So `Token`, `%74oken`, `X-AMZ-CREDENTIAL` and `x_amz_credential` are rejected, while `tokenizer` and `monkey` pass. Decoding comes before folding because that is the order a server applies.
6b. **Credential parameter names and credential patterns (P-60, decided by the owner in revision 9).** This applies to every URL that Decision 6 checks: the three endpoint classes now, and `Artifact.uri` at P1-10a.
   - **The name set, exactly 25 names** (revision 10; 23 in revision 9). They are stored already case-folded, in the spelling below, and exported as `tracer_evalschema.credentials.URL_CREDENTIAL_PARAMETER_NAMES` (a `frozenset[str]`):
     - from P-20 (7): `token`, `key`, `api_key`, `sig`, `signature`, `x-amz-signature`, `x-amz-credential`;
     - from the Decision 3 denylist (13): `apikey`, `access_token`, `auth_token`, `refresh_token`, `client_secret`, `password`, `passwd`, `secret`, `bearer`, `authorization`, `credential`, `credentials`, `private_key`;
     - cloud presign names (3): `x-amz-security-token`, `x-goog-signature`, `x-goog-credential`;
     - API-key header names that are also sent as query parameters (2, revision 10, N15 decided by the owner): `x-api-key`, `x-goog-api-key`.
     No two of the 25 names are equal under the comparison below, so the set has no redundant entry.
   - **Name matching (revision 10, N15 decided by the owner).** Names are taken from the query (ws, webrtc) and from SIP `;uri-parameters` and `?headers`, as in Decision 6a. Each name and each set entry is compared after these steps, in this order:
     1. percent-decode the name once as UTF-8 (a malformed escape or invalid UTF-8 rejects the URL);
     2. case-fold it with `str.casefold()`;
     3. replace every `-` (U+002D) with `_` (U+005F), one for one. The set entries go through the same step.
     The results must be equal as whole strings. Only U+002D and U+005F are equated. Other punctuation (`.`, a space, U+2010 HYPHEN, U+2011), a removed separator, a doubled separator and a longer or shorter name are different names. So `Access_Token`, `%61ccess_token`, `X-Goog-Signature`, `access-token`, `api-key`, `X_Api_Key`, `x_amz_signature`, `x-goog_api-key` and `%2D`/`%5F`-encoded separators are rejected. `access_token_ttl`, `access-token-ttl`, `access.token`, `accesstoken`, `api--key`, `x-api-keys`, `x-api-key-id`, `x-goog-api`, `apiKey1`, `tokens` and `keyboard` pass. Reason: servers and frameworks commonly treat the two separators as interchangeable in parameter and header names, so a name that differs only by separator carries the same credential. The two added names are needed because no separator folding maps `x-api-key` or `x-goog-api-key` to `api_key`.
   - **Coverage of presigned URLs.** AWS Signature Version 4 query authentication uses `X-Amz-Signature`, `X-Amz-Credential` and, with temporary credentials, `X-Amz-Security-Token`. Google Cloud Storage V4 signing uses `X-Goog-Signature` and `X-Goog-Credential`. The other presign forms we know carry `Signature` or `sig`: legacy S3 and GCS V2 query signing, CloudFront signed URLs, and Azure SAS. Each of those names is in the set. This list of provider forms comes from our knowledge of their documentation and was not re-checked against current provider documentation in revision 9.
   - **The pattern rule.** A URL is rejected if one of the Decision 5a `known_credential_prefix` patterns matches anywhere in it. The match uses the same left boundary as 5a: the start of the text, or after a character outside `[A-Za-z0-9]`. Two texts are searched: the URL as written, and the URL percent-decoded once as UTF-8 over its whole length. A malformed escape or invalid UTF-8 rejects the URL, as in 6a. "Anywhere" covers the authority (including a SIP user part and host labels), the path, query names and values, and SIP parameters and headers. Examples: `wss://h/ws/sk-...`, `sip:AKIA...@pbx`, `https://h/x?state=eyJ...eyJ...`.
   - **Not applied to URLs:** the `high_entropy_token` reason of 5a. Metadata keeps and flags a value, but a URL rule rejects the record, so a heuristic that matches ordinary opaque IDs (recording IDs, CDN paths) would block valid data. Only the named patterns, which are specific, reject. Known false positive: a path segment that happens to fit a pattern, such as a slug of `sk-` followed by 20 or more letters, digits, `_` or `-`, is rejected. Refusing is the safe failure, and the message names the rule, so the user can see why.
   - **Errors** name the rule and the URL part, for example "query parameter name `x-goog-signature`" (the name as found in the URL, not its folded form) or "credential pattern in the path". They never name the value (Decision 8).
   - JSON Schema cannot express the name set or the patterns. Both are code-only rules (api-surface 19.6 N12) and are recorded as such.
6c. **`Artifact.uri` (revision 12, O5 decided by the owner, option A).** In addition to Decisions 6, 6a (ASCII only, no white space or control characters, no userinfo, valid percent-escapes) and 6b (credential names in the query, credential patterns anywhere):
   - **Closed scheme set:** exactly `http`, `https`, `s3`, `gs`, `file`, lowercase as written. Every other scheme is rejected, including `ftp`, `data` (it would embed the recording itself in the record), `blob`, `ws`, `wss`, `sip`, and object-store schemes not in the set. Adding a scheme is an additive schema change (ADR 0003 Decision 4).
   - **`http`, `https`, `s3`, `gs`:** `<scheme>://` followed by a non-empty host (for `s3` and `gs` the bucket name). A relative reference (`recordings/1.wav`, `/data/1.wav`, `./1.wav`) and a network-path reference without a scheme (`//host/1.wav`) are rejected.
   - **`file`:** exactly `file:///` followed by an absolute path, so the authority is empty. Rejected: `file:/data/1.wav` (the RFC 8089 form without an authority: the owner's rule names `file:///`), `file://localhost/data/1.wav` (in any letter case), any other host (`file://server/share/1.wav`), a relative path (`file:data/1.wav`, `file://./1.wav`), and an empty path (`file:///`). Details fixed while applying O5, **confirmed by the owner in revision 13**: a `file:` URI has no query (`?` is rejected), and its path has no `.` or `..` segment (`file:///data/../1.wav`), because a path with dot segments is not a stated absolute location. The rule is syntactic: a Windows drive path in RFC 8089 form (`file:///C:/rec/1.wav`) is an absolute path and is accepted.
   - **Fragments:** a `#` anywhere is rejected for every scheme, including an empty fragment (`https://host/1.wav#`). A time range in a recording belongs in `EvidenceRef{kind: artifact_range}` (ADR 0012), not in the URI.
   - **Exports:** `file:` URIs are allowed in internal data and `internal` exports. A `shared_export` or `benchmark` ExportBundle holding an Artifact with a `file:` URI is rejected (P1-14): a local path is meaningless to a recipient and may contain a user name. The message names the artifact ID and the rule, never the path. (Revision 22: implemented as `[uri]` in `bundle.check_export_bundle`, for every artifact of every run bundle of the export.)
   - **Errors** name the rule and the URI part ("scheme not allowed", "fragment not allowed", "file URI must be file:/// with an absolute path"), never the value (Decision 8).
   - **Loopback hosts** in `http`/`https` URIs: Decision 6d (revision 13, O8).
   - The scheme set and the `file:` form can be stated as a JSON Schema pattern; the credential rules cannot (Decision 6b). Whether the pattern is emitted or listed in `KNOWN_SCHEMA_GAPS` follows the staff-reviewer's answer to N12/N38.
6d. **Loopback hosts in `http`/`https` artifact URIs (revision 13, O8 decided by the owner, option A).** The owner's `localhost` rule of Decision 6c concerns `file:` URIs. For `http` and `https`:
   - **Records and `internal` exports accept loopback hosts**, for example a local object store in a CLI or CI setup (`http://localhost:9000/bucket/1.wav`).
   - **`shared_export` and `benchmark` ExportBundles reject an Artifact whose `uri` has a loopback host** (P1-14), like `file:` URIs: the address means nothing to a recipient and names the producer's own machine. The message names the artifact ID and the rule, never the URI (Decision 8).
   - **What counts as a loopback host** (detail fixed while applying O8; api-surface 22.12 item D1). The host is compared after ASCII case-folding and the removal of one trailing dot, both as written and percent-decoded once (the two texts of Decision 6b). It is a loopback host if any of these holds:
     - it is `localhost` or a name ending in `.localhost` (RFC 6761 section 6.3);
     - the WHATWG URL Standard IPv4 parser maps it into `127.0.0.0/8` (RFC 1122 section 3.2.1.3), which covers `127.1`, `0x7f.0.0.1` and `2130706433`;
     - it is an IPv6 literal equal to `::1` or to an IPv4-mapped address in `::ffff:127.0.0.0/104` (RFC 4291 sections 2.5.3 and 2.5.5.2), in any textual spelling.
   - **The spellings, accepted by the owner in revision 14** (the list qa pinned in `test_artifact_uri_loopback_host_rules`). Loopback: the hexadecimal, octal, integer and short IPv4 forms that the WHATWG parser maps into 127.0.0.0/8 (`0x7f.0.0.1`, `0177.0.0.1`, `0x7f000001`, `2130706433`, `127.1`, `127.0.1`, `127.0.0.0x1`); one trailing dot (`localhost.`, `127.0.0.1.`); `localhost` and `*.localhost` in any letter case (`LocalHost.`, `a.b.LOCALHOST`); a host that is loopback after percent-decoding once (`%6Cocalhost`); `::1` in any spelling (`0:0:0:0:0:0:0:1`, the full form with leading zeros); IPv4-mapped addresses in any spelling (`::ffff:127.0.0.1`, `::ffff:7f00:1`, `::FFFF:127.255.255.254`, `0:0:0:0:0:ffff:7f00:1`). Not loopback: `localhost..` (two dots), `localhost.example`, `mylocalhost`, `localhostx`, `localhost.localdomain`, `127.0.0.1.example`, `127.0.0.256`, `127.0.0.1.1` and `127.0.0.1.0` (not an IPv4 address), `126.256.0.1`, `126.255.255.255`, `128.0.0.0`, `1.0.0.127`, `0.0.0.0`, `[::]`, `[::2]`, `[::1:0]`, `[1::1]`, `[fe80::1]`, the IPv4-compatible `[::127.0.0.1]`, `[::ffff:128.0.0.1]`, `10.0.0.0/8`, `192.168.0.0/16`, `169.254.0.0/16`, `host.docker.internal`, a loopback name in the path or query only, and every `s3`, `gs` and `file` URI. A zone identifier (`%` inside an IPv6 literal) is not loopback: it is not part of a URL host. Left to staff-reviewer by the owner: whether records must also accept the spellings beyond the ten that `test_artifact_uri_loopback_host_rules` accepts (the implementation accepts every syntactically valid one, because no rule rejects a loopback host on a record), and how `%2e%2e` and `//` inside a `file:` path are treated (the implementation compares segments as written: `%2e%2e` is not a dot segment and an empty segment is accepted).
   - The rule applies only to `http` and `https`: for `s3` and `gs` the authority is a bucket name. It does not cover the unspecified addresses (`0.0.0.0`, `[::]`), private or link-local ranges, or names such as `host.docker.internal`, because the owner's decision names loopback only; widening it would be a new owner decision.
   - Exposed as the pure function `artifact.is_loopback_uri(uri) -> bool`, so that P1-10a tests the definition and P1-14 uses it. (Revision 22: `bundle.check_export_bundle` uses it, `[uri]`.)
6e. **Price provenance URLs (revision 15, N50 decided by the owner, option A).** `PriceProvenance.url` (inside `PriceEntry`, ADR 0014 Decision 11) is a URL that Decision 6 checks: userinfo is rejected (Decision 6); the query parameter names are compared with the 25 names of Decision 6b, with the decoding, case-folding and `-`/`_` rule of Decisions 6a and 6b; and a Decision 5a credential pattern anywhere in the URL, as written or percent-decoded once, rejects it (Decision 6b). The error says which rule failed and in which URL part, and never the value. A pre-signed or tokenised price-page URL is therefore rejected, as it is for endpoints and artifacts. **Syntax (revision 16, N50 remainder decided by the owner, accepted as recommended):** the URL is an absolute RFC 3986 URI, ASCII only, with no white space or control characters, the lowercase scheme `http` or `https` and a host, as for the webrtc signalling endpoint in Decision 6a. Unlike Decisions 6a and 6c, a fragment is allowed, because price pages link to sections with anchors; the Decision 5a credential patterns are searched in the fragment too (as written and percent-decoded once). No loopback rule is added. Whether the parameter-name check also applies to `name=value` pairs inside a fragment, whether loopback or private hosts are accepted, and whether a user-supplied price's `note` may be empty, are open (N66). **Revision 17 (N66 decided, auto-approved under the owner's standing rule of 2026-10-23):** (a) **Fragment names.** The fragment of `provenance.url` is split at `&` and `;`, and each name (the text before the first `=`) goes through the name matching of Decision 6b (percent-decode once as UTF-8, `str.casefold()`, `-` equal to `_`) against the 25 names; a match rejects the URL, with an error that names the rule and the part ("credential parameter name in the fragment") and, because `PriceProvenance` hides its input (Decision 8 (c)), not the name. **Revision 18 (N70 decided, auto-approved, option A; qa finding 2):** every piece is a name, with or without `=`, exactly as in the query: the name is the text before the first `=`, or the whole piece when it has none, and it is compared whole. So `#token` and `#a=1&key` are rejected (`token`, `key` are credential names), while `#tokens=1`, `#token-pricing`, `#access_token_ttl=5`, `#audio-models` and `#a=1&b=2` are accepted (their names `tokens`, `token_pricing`, `access_token_ttl`, `audio_models`, `a`, `b` are not among the 25). A price page whose anchor is exactly a credential name must be stored without that anchor. ## Rejected alternatives
- **Encrypted secret fields in the schema.** Ciphertext in exports is still a liability (key-management coupling, offline attack). The schema's job is to describe evaluations, not to be a secret store. References keep the boundary clean.
- **`extra="ignore"`.** An `api_key` sent by mistake would be dropped without notice on one path and stored on another path that uses a raw dict. Rejecting it is explicit and safe.
- **Silently strip secret-looking metadata.** It destroys user data on a heuristic (false positives on hashes and IDs) and hides that a leak was attempted.
- **Store presigned artifact URLs.** They are bearer credentials until they expire, and they would end up in exports.

## Consequences
- Adapters must translate provider configuration into `ProviderConfigRef` and drop credentials before building schema objects.
- Phase 3 must add redaction for flagged metadata and for telemetry attributes before any shared export.
- The secret walk runs at the gate (P1-21).
