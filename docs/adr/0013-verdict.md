## Context
The verdict is the number people will read first. Two failure modes are common in evaluation tools. (1) Not-applicable checks are silently dropped, so "3/3 passed" is shown when two other required checks never ran. (2) Weights are mixed into the pass count, so a high weighted score hides a failed required check. Missing telemetry must lower confidence in a verdict, never turn it into a pass. The same trap exists inside a weighted score: a score computed only over the checks that ran can read 1.00 while a fifth of the weight was never measured.

## Decision
1. **`RunVerdict`** (entity `vrd`): `{required_total, passed, failed, not_applicable, errored, status, checks[], weighted_score?, weight_coverage?, weighted_excluded[]}`.
2. **`checks[]`** (value objects) hold one entry per required check: `{binding_id: mbd_ID, metric_ref, outcome: passed|failed|not_applicable|errored, result_id: res_ID}`. The evaluator's expected outcome is an ordinary required check; with the `equals_true` pass rule (ADR 0010) it is expressible as a boolean. Every check's binding is required in the snapshot's rubric, and every required binding has exactly one check.
   - **`metric_ref` (revision 8)** is a `MetricDefinitionRef{id, version, content_digest?}` (ADR 0009 Decision 4), equal to the `metric` of the check's binding. `key@version` is display text from `render_metric_ref()`, never stored or parsed.
   - **How the expected outcome is tied to its check (revision 8).** The judge receives the text through the reserved prompt variable `expected_outcome`, which the runner fills with `Evaluator.expected_outcome` verbatim, after resolving its profile placeholders (revision 9: E7 decided by the owner, ADR 0006 Decision 9a). An *expected-outcome check* is an enabled binding of the evaluator whose definition is `llm_judge`, boolean, `per_conversation`, `equals_true`, and lists `expected_outcome` in `prompt_variables`. The ConfigSnapshot (P1-12) requires at least one such check, and each one must be a required rubric item. A definition that uses the variable in another shape is an ordinary metric. The prompt variable is the actual data path, so the link is stated once, in the versioned definition, and no second field can disagree with it.
3. **Outcome derivation:** scored + passed -> `passed`; scored + not passed -> `failed`; not_applicable -> `not_applicable`; error -> `errored`. (Revision 11, `docs/phase1/api-surface.md` section 22.3 N37: a scored result with `passed=None` has no outcome and `outcome_of_result` rejects it rather than guessing one; it cannot occur for a required or weighted check, because those need a pass rule (Decision 7). Since a rubric has at least one required item, `required_total >= 1`. A result is matched to its binding through the binding's `metric` reference, which names one binding per evaluator; when the supplied results hold two results of one metric, the verdict check rejects instead of choosing one, N33.)
4. **Counts:** `required_total = passed + failed + not_applicable + errored`. Each count equals the tally of `checks[].outcome`.
5. **Headline:** `render_headline()` returns exactly `"{passed}/{required_total} required checks passed"`. The denominator includes not_applicable and errored checks. Weights never change the headline, and the headline never contains the weighted score.
6. **Status:**
   - `pass` iff `passed == required_total`
   - `fail` iff `failed > 0`
   - `inconclusive` iff `failed == 0` and `not_applicable + errored > 0`

   A stored status that disagrees with the counts is rejected.
7. **Rubric:** at least one required metric. Every required metric has a pass rule (ADR 0010). Weights live in the Rubric, are positive `DecimalString` values, and never affect counts or status. **Weights on non-required metrics (P-34)** are allowed; the weighted score may include them, the counts never do. **A weight requires a pass rule (user decision P-55, revision 6):** Rubric validation rejects a weight on a binding whose metric definition has no pass rule, because such a metric's scored results have `passed=None` (P-08) and cannot contribute to `Σ(w·passed)`. An informational metric (for example talk ratio) stays in the rubric unweighted.
   - **Weight values (revision 8).** A canonical `DecimalString` strictly greater than 0. Zero is rejected, because "contributes nothing" is already said by omitting the weight, and all-zero weights would make Σw = 0. An item without a weight is in neither sum of the weighted score or of the coverage, and never in `weighted_excluded[]`. Weights are relative, so there is no upper bound.
   - **`RubricItem{binding: MetricBindingRef, required: bool, weight?}` (revision 8).**
     - Items are non-empty, at least one is required, and no binding `id` appears twice at any version.
     - `validate_rubric(rubric, *, bindings, definitions)` resolves item -> binding -> definition and rejects, naming the binding or definition ID: an unresolved or other-version reference; bindings of more than one evaluator; two items resolving to one definition `id` or to two definitions with the same `key`; a required or weighted item without a pass rule; parameter errors (ADR 0010 Decision 4a).
     - It also rejects **an item whose binding is disabled** (`enabled=false`). A disabled binding writes no result, so as a required check it would make every run inconclusive, and as a weighted check it would keep the coverage below 1, both for a reason fixed when the rubric was written.
8. **Weighted score and coverage (user decision P-33, revision 5).**
   - The weighted checks are the rubric bindings that carry a weight (required or not). A weighted check is *scored* if its MetricResult is `scored` with `passed` true or false; not_applicable and errored weighted checks are excluded and listed in `weighted_excluded[]` (binding ID and outcome).
   - `weighted_score = Σ(w · passed) / Σ(w)` over the scored weighted checks, where `passed` is 1 or 0. It lies in [0,1].
   - `weight_coverage = Σ(w over scored weighted checks) / Σ(w over all weighted checks)`. It lies in (0,1] whenever a score exists.
   - **`weight_coverage` is required whenever `weighted_score` is present, and the two are stored together.** If no weighted check was scored (or the rubric has no weights), both are absent; there is never a score of 0 standing for "nothing measured".
   - Both are exact `Decimal` computations stored as `DecimalString`; a non-terminating quotient is rounded half-even at scale 18, the same rule as ADR 0014 (P-35).
   - **Rendering rule:** every report and rendering helper that shows the weighted score shows the weight coverage next to it, and never shows the score alone. The one shared helper is `render_weighted_score(verdict) -> str | None`, which returns `"weighted score {score} (weight coverage {coverage})"` with both values formatted to 2 decimal places (display only; the stored values are unchanged), or `None` when no score exists. Other renderers call it rather than formatting the score themselves.
   - Worked example (golden): three weighted checks with weights 5, 3 and 2; the weight-5 and weight-3 checks passed; the weight-2 check is not_applicable. `weighted_score = (5 + 3) / 8 = 1`, `weight_coverage = 8 / 10 = 0.8`, rendered `"weighted score 1.00 (weight coverage 0.80)"`, and `weighted_excluded` lists the weight-2 check.

8a. **Per-turn-share metrics in the verdict (P-58, revision 7).** A metric aggregated as `per_turn_share` is one check, however many turns it covers. Its outcome follows Decision 3 from its MetricResult: scored and `passed` true -> passed; scored and `passed` false -> failed (`passed` is the range pass rule applied to `per_turn.share`, ADR 0010 Decision 3a); `error` (including `judge_undetermined` with no counted turn) -> errored; `not_applicable` -> not_applicable. In the weighted score it contributes `w * passed` (1 or 0), never `w * share`, so partial credit cannot raise the score while the check fails; it is excluded and listed in `weighted_excluded[]` when not scored. Being required or weighted needs a pass rule (Decision 7, P-55); for these metrics that is the range on the share. Test: `test_weighted_score_uses_per_turn_passed_not_share`.

## Rejected alternatives
- **Denominator = checks that ran.** "2/2 passed" for a run where three required checks could not run overstates confidence. The user ruled this out (Q3).
- **not_applicable counts as pass.** It rewards missing telemetry: a black-box agent would pass tool-call checks it never exercised.
- **not_applicable counts as fail.** It punishes capability tier rather than behaviour, which breaks the core rule.
- **A weighted score as the headline.** A failed critical check can be outweighed. Weights express priorities among metrics, not whether the run met its requirements.
- **A weighted score without coverage.** 1.00 over 80% of the weight reads like 1.00 over everything. The coverage is what tells a reader how much of the rubric the score describes.
- **Counting not_applicable or errored weighted checks as 0 in the score.** It mixes "did not run" into "ran and failed", the error the headline rule exists to prevent.
- **A boolean verdict.** It cannot represent "nothing failed, but we could not check everything".
- **Status computed only, not stored.** Storing it with a consistency check lets readers in other languages use it without re-implementing the rule, while forged or stale values are still caught.

## Consequences
- With degraded tiers, many runs are `inconclusive`. T-DEG reports the inconclusive share per tier. That is the honest result.
- UIs must show the headline with the not_applicable and errored counts, not just the status, and must show the weighted score only through `render_weighted_score()` (score plus coverage).
- `SCHEMA_POLICY.md` states the formula, the coverage definition and the rendering rule.

## Decided items (formerly [Proposed]; decided by the user in revision 5)
- **P-33. Weighted-score formula. Decided by the user (revision 5): `Σ(w·passed)/Σ(w)` over scored checks, plus a required `weight_coverage` (scored weight / total weight) stored with the score; every report and rendering helper shows the coverage next to the score and never the score alone; the headline x/y is unchanged; the weighted score is absent if nothing was scored.** Folded into Decision 8. Tests: `test_weighted_score_excludes_errored`, `test_weighted_score_absent_when_all_excluded`, `test_weighted_score_range_0_1`, `test_weight_coverage_required_with_score`, `test_weight_coverage_is_scored_over_total_weight`, `test_weighted_score_5_3_2_with_na_is_1_coverage_0_8`, `test_render_weighted_score_shows_coverage`, `test_no_renderer_shows_weighted_score_without_coverage`, `test_headline_unchanged_by_weights`. Details fixed while applying the decision, **accepted by the user in revision 6**: coverage is absent together with the score; rounding is half-even at scale 18 (P-35); display uses 2 decimal places.
- **P-34. Weights on non-required metrics. Decided by the user (revision 5): accepted as recommended.** Allowed; the weighted score may include them, the counts never do (Decision 7). Had it been decided otherwise: weights would be allowed only on required metrics.
- **P-55. A weight on a metric without a pass rule. Decided by the user (revision 6): accepted.** A metric without a pass rule cannot carry a weight; Rubric validation rejects such weights (Decision 7). Reason: P-08 gives a scored result without a pass rule `passed=None`, so the P-33 formula has no defined contribution for it, and silently excluding it would lower `weight_coverage` on every run for a reason unrelated to the run. Rejected alternative: exclude it at scoring time with reason `no_pass_rule`, which keeps coverage below 1 permanently. Test (binding): `test_rubric_weight_requires_pass_rule`.
