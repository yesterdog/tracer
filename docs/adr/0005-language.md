## Context
The framework is Indic-first. Two different questions are involved:
1. Which languages may a user *configure* a test in (Persona, ScriptedTurn, Evaluator, DatasetItem)? Here we promise quality: native-speaker-reviewed fixtures and Indic-aware normalization.
2. Which language did a *provider or source report* (STT detected language, agent transcript language)? This is an observation. Rejecting it would discard real data and break ingestion.

Merging the two forces a bad choice: either the configured set accepts anything (losing the quality promise) or ingestion rejects real provider output (breaking the core rule).

## Decision
1. **`SupportedLanguage`** (configuration). Exactly nine languages (user decision 6): English `en`, Hindi `hi`, Marathi `mr`, Telugu `te`, Tamil `ta`, Kannada `kn`, Malayalam `ml`, Punjabi `pa` (Gurmukhi), Gujarati `gu`. The data lives in `languages.json`: default ISO 15924 script, allowed scripts (native only), native digit block, English and native names.
   - A region subtag is accepted and kept (`hi-IN` stays `hi-IN`; `en-US` is valid). **Regions (P-14, user decision):** only the regions in the vendored IANA subset, which in 0.0.1 are exactly `IN`, `US` and `GB` (Indian languages and English first). Any other region (for example `ta-LK`, `en-AU`) is rejected as a configured tag with a message that names the rejected region, lists the supported regions and says that adding a region is a data change to the vendored subset. The full region list is not vendored. Observed tags are unaffected (Decision 2): `ta-LK` and `en-AU` are valid observations.
   - A script subtag is accepted only if it is in the language's allowed native scripts (`pa-Guru-IN` is valid; `pa-Arab` is rejected; `hi-Latn` is rejected).
   - Rejected: extensions (`-u-`, `-t-`), variants (`-1901`), private use (`-x-`), and `und`, `mul`, `zxx`.
   - Canonical case: language lowercase, script title case, region uppercase (`HI-in` -> `hi-IN`). No other rewriting: a suppressed script is not removed and a region is not added.
   - Validation reads `languages.json` and the vendored IANA subtag subset only.
   - **Message precedence (revision 7).** A tag whose primary subtag is one of the eight configured non-English languages and whose region subtag is `EN` (any case) is rejected with the code-mix message `CODEMIX_UNSUPPORTED_MESSAGE` (Decision 5), and this takes precedence over the unsupported-region message. `en-EN` is not that alias and gets the ordinary region message. No other pair is treated as code-mix.
2. **`ObservedLanguageTag`** (observation; user decision 3). Validation is **syntax-only**: the value must be a well-formed BCP-47 tag (RFC 5646 section 2.1 ABNF). It is **never** checked against a registry and is **never rejected for being unknown, unregistered or unsupported**. `bn-IN`, `hi-Latn`, `und`, `zxx`, `hi-x-foo`, `xq-IN` are all valid observations. The same case canonicalization as Decision 1 applies (letter case only). The underscore form `hi_IN` is not well-formed and is rejected **by the type**; the importer handles it (Decision 3). **Syntax profile (P-12, user decision):** the RFC 5646 `langtag` production and private-use-only tags (`x-...`) are accepted; the primary language subtag must be 2-3 letters (optionally followed by extlang subtags). Primary subtags of 4-8 letters are rejected, so a language *name* such as `hindi` is never stored as a tag. Grandfathered tags are rejected: all 26 tags of the RFC 5646 section 2.1 `grandfathered` production (irregular, such as `i-klingon` and `en-GB-oed`, and regular, such as `zh-min-nan` and `art-lojban`), matched against that literal list from the grammar, which is still syntax-only (no registry lookup). **Matching (revision 7):** the whole tag is compared case-insensitively with each of the 26 literal tags (RFC 5646 section 2.1.1: tags are case-insensitive). A longer tag that only begins with one of them (for example `zh-min-nan-TW`, `art-lojban-x-a`) is an ordinary langtag and is judged by the grammar. **Extlangs:** a 2-3 letter primary subtag may be followed by at most three 3-letter extlang subtags, exactly the ABNF `extlang = 3ALPHA *2("-" 3ALPHA)`. Nothing is rejected at ingest: an importer facing such a label keeps it verbatim in the raw field, leaves the normalized tag empty (`None`) and adds a `language_label_unparseable` warning (Decision 3).
3. **The provider's raw label is kept (user decision 3).**
   - `Transcript.detected_language_raw: VerbatimText?` holds the label exactly as the provider sent it, code point for code point, whether or not it could be parsed. It is rendered only through `display_safe()` (ADR 0017).
   - `Transcript.detected_language: ObservedLanguageTag?` holds the normalized tag.
   - **Importers** (not the type) remove surrounding white space (E4, user decision; characters for which `str.isspace()` is true, at either end, like the currency labels of P-52), convert `_` to `-` to build the normalized tag, apply case canonicalization, and add an IngestWarning `language_label_normalized` with the raw value (one warning per label, even when both trimming and `_` replacement applied; its `raw` is the label as received, before trimming). If the label still is not well-formed after that, `detected_language` is `None`, the raw label is kept, and an IngestWarning `language_label_unparseable` is added. Importers never map names to tags by guessing; a documented provider-specific table (for example a provider's own list of labels) counts as a source derivation under ADR 0018 and must be cited in the mapping.
   - This resolves the revision 2 contradiction between the F3 check "bn_IN observed ok" and `test_observed_rejects_malformed["hi_IN"]`: the type stays strict, the importer normalizes. The F3 check is renamed `test_f3_bn_IN_label_normalized_raw_kept`.
   - **The pure helper and its warnings (revision 7).** `normalize_language_label(raw)` returns `(tag or None, [LanguageLabelWarning{code, raw}])` and `observe_language_label(raw)` returns `ObservedLanguage{tag, raw, warnings}` (value objects, ADR 0001 Decision 8). The importer converts each `LanguageLabelWarning` 1:1 into an `IngestWarning` (P1-10c) with the same code and raw. `language_label_normalized` is added iff the underscore replacement changed the label and the result is a well-formed tag; a label that is still not a tag gets only `language_label_unparseable`. A case-only difference adds no warning, because tags are case-insensitive and the raw label is kept anyway. **Trimming (E4, decided by the user) happens in the importer, not here:** the types (`SupportedLanguage`, `ObservedLanguageTag`) and the pure helpers never trim, so given a padded label the helper reports it as unparseable. The importer (P1-31 and later importers) trims surrounding white space first, calls the helper with the trimmed label, and records the label as received (untrimmed) in the raw field and in the warning's `raw`; a label that needed trimming gets `language_label_normalized`. An empty or whitespace-only label is unparseable (also after trimming). An absent label (`None`) gives no warning. **Revision 20 (N82 decided, auto-approved; closes the open P1-31 lone-surrogate item):** importers never raise on text content. A provider label holding a lone surrogate is treated as non-matching (no tag); the raw field and the warnings' `raw` hold it with each lone surrogate replaced by U+FFFD (`text.replace_lone_surrogates`), and the importer records the warning `text_not_valid_unicode` (as the cost importer does, ADR 0014 Decision 12c step 0). Which further language warning accompanies it is pinned by the P1-31 tests.
   - **Turn-level raw label (P-13):** `Turn.language_raw: VerbatimText?` holds a per-turn provider label verbatim, with the same importer rules (normalized into `Turn.language` when well-formed, otherwise `Turn.language=None` and a warning).
4. **`primary_language(tag)`** returns the primary language subtag. It is used to compare an observed tag with a supported one (`hi-IN` and `hi` share `hi`).
5. **No code-mix in 0.0.1.** There is no CodeMix type, no `code_mix` field and no `hi-en` alias. A `hi-en` value for a supported language is rejected with a message that says code-mix is unsupported. (In BCP-47 `hi-en` is not a language-pair tag: a two-letter second subtag is a region, so `hi-en` parses as Hindi with the unassigned region `EN`. As an *observed* tag it is therefore well-formed and, under syntax-only validation, recorded as `hi-EN` with the raw label kept; it is rejected only as a SupportedLanguage. Consumers must not read an observed `hi-EN` as code-mix.)
6. **Where each type is used.** `Persona.language`, `ScriptedTurn.language`, Evaluator and `DatasetItem.language` use `SupportedLanguage`. `Turn.language` and `Transcript.detected_language` use `ObservedLanguageTag`. Both are optional on observations; an absent value is `None`, never guessed.
   - **Lists of configured languages (revision 8, batch 2 item 12).** `MetricDefinition.languages` is non-empty and has no two entries with the same primary language, because coverage is decided by primary language (ADR 0004 Decision 6). An empty list is rejected rather than read as "none" or "all". `AgentTarget.languages` may be empty, meaning "no language declared" (never "all"). It rejects exact duplicates after case canonicalization, and no logic reads it. **Revision 9 (P-59, decided by the owner):** `MetricDefinition.languages` may instead be the single value `"language_independent"`, for metrics that do not depend on language. A language-dependent metric on input without an observed tag is `not_applicable` with `language_not_observed`. A configured language (Persona, ScriptedTurn, Evaluator, DatasetItem, AgentTarget) is never used in place of an observed tag. The exact rules and a worked example are in ADR 0004 Decision 6.
   - **Declared languages (revision 10, N14 decided by the owner).** A user may declare the language of an imported transcript that carries no transcript-level label: `Transcript.declared_language: LanguageDeclaration{language: SupportedLanguage without a script subtag, source: user_declared, declared_by, declared_at}`. It is a third kind of language value, beside configured (`SupportedLanguage`) and observed (`ObservedLanguageTag`). It is never stored in an observed field and never read as an observation. Metrics that are not script-sensitive may use it where no tag exists, and each such result records `language_source=declared`. Script-sensitive metrics never use it. The rules are in ADR 0004 Decision 6g.
7. **Script-sensitive metrics** on observed text whose script is not native for its language are `not_applicable` with `unsupported_script` (ADR 0004, data-driven through `MetricDefinition.script_sensitive`). A turn whose text mixes scripts is valid. Its text is stored verbatim, and no single-script assumption is enforced on observations.
8. **Excluded in 0.0.1:** Bengali, Urdu, Shahmukhi Punjabi, Odia, Assamese, and code-mix. They can be added later as a non-breaking minor change once data files, fixtures and native review exist. As observations they are always accepted (Decision 2).
9. **Language data (user decision 6).** `languages.json`, `iana_subtag_registry_subset.json` and `iso4217_active.json` were verified against directly downloaded raw sources (IANA registry File-Date 2026-09-17; Unicode 18.0.0 Blocks.txt and DerivedNumericType.txt; SIX ISO 4217 List One published 2026-09-17), as recorded in each file's `_meta.verification` and in `docs/languages.md`. Native names remain `needs_native_review` until a native speaker checks them. No separate ISO 15924 file is vendored: script subtags in the IANA subset are ISO 15924 codes, which is what `test_scripts_in_vendored_iso15924` checks. Because observed tags are syntax-only, the full IANA registry is not needed.
10. **T-DRIFT allowlist (accepted in revision 3).** `test_no_codemix_or_excluded_language_tokens` greps the package, fixtures, docs and agent files for code-mix and excluded-language tokens. Files that must name them in order to reject them are listed explicitly in the test, by path:

    - the negative-fixture directory for languages (P1-17 negatives) and the test modules that carry the negative parameters (`test_supported_rejects`, `test_excluded_languages_absent`, `test_hi_en_rejected_with_codemix_message`, A-22, A-23); without these the accepted negative tests could not exist
    - the module that defines the code-mix rejection message constant

## Rejected alternatives
- **One permissive tag type for everything.** The configured set would accept languages we have no normalization, fixtures or reviewers for, and results would carry an unearned quality promise.
- **One strict type for everything.** Real provider output (for example `bn-IN` from a multilingual STT, or romanized `hi-Latn`) would be rejected. This breaks the core rule and loses evidence of unwanted language switching, a metric we need.
- **Registry-checked observed tags.** A provider that reports a newly registered subtag, or a private-use subtag, would have its observation rejected or dropped because our vendored snapshot is older. The observation is evidence and must be kept as reported; whether we *support* the language is a separate question answered by `SupportedLanguage` and `unsupported_language`.
- **Normalizing `_` inside the type.** The stored tag would then silently differ from the source with no record of the change. Doing it in the importer keeps the raw label and a warning, so the normalization is auditable.
- **Dropping the raw label after normalization.** Language-switch metrics and audits need to know what the provider actually said; a label that could not be parsed would otherwise vanish.
- **Strip the region (`hi-IN` -> `hi`).** It loses information that matters for STT/TTS model choice and accent. Use `primary_language()` for comparison instead.
- **Full RFC 5646 canonicalization (suppress-script removal, deprecated-tag replacement).** It rewrites what the source reported. Comparison goes through `primary_language()`.
- **Allow romanized configured languages.** The user decided native script only (OQ2). Scripted references in romanized text would make WER/CER depend on transliteration conventions, which have no standard for these languages.
- **A `hi-en` alias for Hinglish.** It is not valid BCP-47 semantics, and code-mix is out of scope for 0.0.1 (Q2).
- **ISO 639 codes without BCP-47.** No script or region, so `pa-Guru` vs `pa-Arab` cannot be expressed.

## Consequences
- `languages.json` and the vendored IANA subset (with `File-Date`) are versioned data. Updating them is a schema data change recorded in the CHANGELOG.
- Observed tags can name languages and scripts we know nothing about; consumers must not assume an observed tag is in any list.
- Persona `accent` is a `HumanLabel`, not a language tag.
- `docs/languages.md` still carries a caveat that the files were transcribed from web-fetch output; the `_meta.verification` notes in the data files supersede it (direct downloads). indic-linguistics should update that caveat.
