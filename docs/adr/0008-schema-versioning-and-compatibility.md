## Context
`tracer-evalschema` is the source of truth. JSON Schema, OpenAPI, TypeScript types and DB tables are generated from it. Files written by one version will be read by others: CI artifacts, exports, benchmark bundles. Silently dropping fields that a reader does not understand corrupts data without anyone noticing. Generated artifacts must be reproducible so that reviewers see real changes only.

## Decision
1. **One version string.** `SCHEMA_VERSION` is a semver string. The first release is `0.0.1`. The package version equals `SCHEMA_VERSION`. Every entity carries `schema_version`; value objects inherit it from their entity (ADR 0001).
2. **Reader rules.**
   - A file with a newer version raises `SchemaVersionTooNew`. Fields are never silently dropped.
   - While the version is `0.0.x`, the reader requires an **exact match**. An older file raises `SchemaVersionMismatch`.
   - A malformed version (`"1"`, `"v0.0.1"`) raises `SchemaVersionInvalid`.
   - All errors are typed exceptions carrying the found and expected versions.
   - **`schema_version` is required on input** (no default). The only valid form is `MAJOR.MINOR.PATCH` with non-negative integers without leading zeros, compared numerically (`0.0.10` is newer than `0.0.2`). Pre-release and build suffixes, whitespace and non-strings are `SchemaVersionInvalid` (revision 7).
   - **Typed errors are not wrapped by pydantic (revision 7).** Pydantic v2 turns only `ValueError`, `AssertionError` and `PydanticCustomError` raised in validators into `ValidationError`. Every typed error of this package that derives from `TracerSchemaError` and not from `ValueError` (the version errors, the digest errors, `NonIJsonValueError`, the loader and bundle errors) therefore propagates as itself out of `model_validate`, `model_validate_json`, `TypeAdapter.validate_*` and the strict loader, including from nested models. Consequences: callers catch the typed class; the first typed error aborts validation and carries no pydantic `loc`, so each typed error names the offending value (and the path where known) in its message. `ConfusablePrefixError` and `DataFileError` are also `ValueError`s; they are raised by `validate_new_prefix()` and the data loaders, never inside model validation.
3. **Bundles are single-version.** Every entity in a RunBundle or ExportBundle has the same `schema_version`. A mixed bundle is rejected. (Revision 22, P1-14: each embedded record is checked by its own model first, so a record of a newer version raises `SchemaVersionTooNew` and an older one `SchemaVersionMismatch`, unwrapped; the seam over the dumped documents is the second line, `MixedSchemaVersionError`.)
4. **Change classes** during 0.0.x: every release bumps the patch and is treated as incompatible. Additive changes (new optional field, new enum member, new digest scheme, new ID prefix) and breaking changes (removing, renaming, retyping, tightening) are still classified in the CHANGELOG, and a breaking change needs a migration note. **The rule from 0.1.0 on (P-22):** between 0.1.0 and 1.0.0 a minor bump is breaking and a patch is additive; from 1.0.0 a reader accepts the same major with minor <= its own (missing optional fields become `None`), rejects a newer minor with `SchemaVersionTooNew`, and rejects another major unless it is upgraded through `upgrade()`.
5. **Frozen fixtures, per version (accepted in revision 3).**
   - Every released version `V` has a directory `tests/fixtures/frozen/<V>/` holding its golden fixtures. Once `V` is released, the directory is immutable: its file hashes are recorded and checked.
   - `test_frozen_fixtures_still_parse` asserts: (a) the fixtures of the current `SCHEMA_VERSION` parse with the strict loader; (b) for every older version without a registered upgrade step, each fixture raises `SchemaVersionMismatch` (not another error, and never a silent parse); (c) for every older version with a registered step, `upgrade(doc, from=V)` produces a document that parses under the current version and equals the stored upgraded twin in `tests/fixtures/frozen/<V>/upgraded/<current>/`.
   - `upgrade()` is a chain of pure, registered steps `V -> V+1`. A step is required for every release from 0.1.0 on. During 0.0.x a step is optional; without one, older files stay unreadable, which (b) checks explicitly.
   - The test iterates over versions in its body, not through an empty `parametrize`, so it never produces a skip when there are no older versions (gate item 2).
6. **Strict loading.** The loader rejects duplicate JSON object keys and enforces a nesting-depth limit with a typed error, never a `RecursionError`. Unknown fields are forbidden (`extra="forbid"`). (Revision 22, P1-14, S-N94, B12:) `loader.load_bundle(model, data, *, max_bytes=DEFAULT_MAX_BUNDLE_BYTES, max_depth=DEFAULT_MAX_DEPTH)` loads a `RunBundle` or an `ExportBundle` only (any other model is a `TypeError`, before the data is read); the UTF-8 byte length of `data` is compared with `max_bytes` before any parsing, and a larger input raises `BundleSizeError` (a `BundleError`) naming the two sizes and no content; `DEFAULT_MAX_BUNDLE_BYTES` is 256 MiB. `load_model` keeps no size limit.
7. **JSON Schema export.** Draft 2020-12, one file per entity plus the bundle, `$id = urn:tracer:evalschema:<version>:<entity>`. Output is byte-identical across runs. Files ship inside the wheel. `schema.lock` records the SHA-256 of each file, tied to `SCHEMA_VERSION`. Changing a schema file without bumping the version fails CI. (Revision 23, P1-15; api-surface section 26:)
   - **What is exported.** `tracer_evalschema.schema_export.render_schemas()` writes one file `<ClassName>.schema.json` per entity of `registry.entity_classes()` (the two bundles included); value objects travel under `$defs` of the entities that embed them. A file is `model_json_schema(mode="validation")` plus `"$schema": "https://json-schema.org/draft/2020-12/schema"` and the URN `$id` (`<entity>` is the class name), with every `required` array sorted, and nothing else. Every reference is local (`#/$defs/<Name>`); `const` and `discriminator` are never used (ADR 0003 Decision 6).
   - **Bytes.** `json.dumps(document, indent=2, sort_keys=True, ensure_ascii=True)` plus one LF: ASCII only, no machine path, interpreter or dependency version, and the same bytes on every supported Python (verified on 3.11 to 3.14). A root `.gitattributes` keeps the files LF on every checkout.
   - **Distribution.** The files and `schema.lock` are committed package data under `tracer_evalschema/schemas/` (`schema_directory()`), shipped byte for byte in the wheel and the sdist; nothing is generated at install time. (Revision 25, A25, superseding the sdist half of revision 24's A23:) neither archive carries tests. The sdist holds `src/tracer_evalschema/` (with `schemas/` and `data/`), `README.md`, `LICENSE`, `NOTICE` (also the `license-files` of the metadata), `pyproject.toml` and the files hatchling always adds (`PKG-INFO` and the `.gitignore` it applies), through `[tool.hatch.build.targets.sdist] only-include`; so it never carries `tests/fixtures/real` (captured provider responses), `tests/fixtures/private` (real call data, never committed), `tests/support` or the UAX #9 reference. The tests need the repository (those fixtures, `tests/support`, `scripts/`, `docs/`, the root `pyproject.toml` with the `private_fixtures` and `local_only` markers), so verification runs from the git checkout; shipping them with a skip marker was rejected because it hides failures behind skips. A wheel built from the unpacked sdist is identical to the wheel built from the checkout and passes `--check` when installed. The generator adds no runtime dependency (Decision 10); it hashes through `digest.sha256_hex`.
   - **The lock.** `schema.lock` is canonical JSON (same byte form) of exactly `algorithm` (`sha256`), `files` (file name -> lowercase hex SHA-256 of its bytes) and `schema_version` (`SCHEMA_VERSION`).
   - **Drift rules.** `python -m tracer_evalschema.schema_export --check` (a CI step, and `test_shipped_schemas_match_generated` in the suite) compares the directory with the generator: a changed, missing or foreign file, or a lock that is missing, not canonical or not the generated one, fails (exit 1, one tagged line per problem). The generator is the reference: editing a file together with its lock entry is still drift. The files are never edited by hand (Decision 9).
   - **Update procedure.** Change the model, run `uv run python -m tracer_evalschema.schema_export --write`, review the diff of `schemas/` (only real changes show, Context), and commit the files with the model change.
   - **Version-bump rule.** While a version is unreleased (0.0.1 until its release) the lock is simply regenerated. When a version `V` is released its lock is recorded as `tests/fixtures/frozen/<V>/schema.lock` (with the frozen fixtures of Decision 5) and is immutable: the check, given the recorded locks, reports `[released]` when the directory's lock under the same `SCHEMA_VERSION` differs from the recorded one. Any later schema change therefore bumps `SCHEMA_VERSION` and the package version, and adds the CHANGELOG entry (Decision 4), before `--write`.
8. **Validation and serialization schemas agree.** Pydantic's validation-mode and serialization-mode schemas must be identical. Pydantic and JSON Schema must both reject every invalid fixture. A divergence fails CI unless it is listed in `KNOWN_SCHEMA_GAPS` with an owner (only non-blocking mapping gaps may be listed, gate item 2). (Revision 23, P1-15; N12, N38, A12:) a rule that JSON Schema 2020-12 cannot state (cross-record, arithmetic, cryptographic, a property of a string's content, or a property of the JSON Schema language itself) is not a divergence of this kind: it is listed, with an owner, the documentation that states it and the differences it explains, in the separate register `CODE_ONLY_RULES` of the tests (`tests/_support_b8.py`), and the mutation tests keep that register exact in both directions. A rule that JSON Schema can state on a closed discriminator, a presence or an exact repeat is emitted (`if`/`then`, `uniqueItems`), never registered, with one exception (revision 24, A22, amending A13): `uniqueItems` is emitted only on arrays of strings (closed-set kinds, IDs, language tags, option names). On an array of objects no exported schema bounds the length, and a validator compares objects pairwise, so the keyword costs time quadratic in a length the document chooses (`jsonschema` 4.26 on the 4,000-turn A-05 bundle: about 4.2 s with it, 0.5 s without; 8,000 turns: 35.7 s against 0.8 s). There, and on the record lists of `RunBundle` and `ExportBundle` and `PricingCatalog.entries` in particular, uniqueness is a code-only rule (register row `CO-LONG-LIST-UNIQUENESS`, nature `mutation`, reason validator cost): the models reject a repeat in linear time, and a consumer that validates untrusted documents with the schema alone checks it itself, after applying the byte limit (Decision 6). The same holds (revision 25, A21 and A24) for `ConfigSnapshot.metric_definitions` and `ConfigSnapshot.metric_bindings`: the model rejects one definition or one binding embedded twice (the same `id` and `version`, whether the two entries are identical or not: references resolve by `(id, version)`, so a second entry under one key would otherwise be dropped silently; a `ValidationError` located at the list and the position of the repeat, whose message says `duplicate` and shows neither the record nor its digest), and no `uniqueItems` and no `maxItems` is emitted there; the exact repeat belongs to `CO-LONG-LIST-UNIQUENESS`, two different entries under one key are keyed uniqueness (next sentence). Uniqueness by key (record ID, unit, primary language) is code-only in any case (`CO-KEYED-UNIQUENESS`, A20). The schema is never stricter than the model: there is no register for that direction.
9. **Generated artifacts are never edited by hand.** Field docs and schemas are regenerated in CI, and any diff fails the build. (Revision 26, P1-20a:) the field docs are `docs/schema/*.md`, one page per entity plus `value-objects.md` and `README.md`, rendered by `scripts/generate_field_docs.py` from the shipped schema files only (after checking each file against `schema.lock`), so they say what the exported schemas say and nothing the models add; `--write` regenerates them, and `--check` (a step of the CI lint job, after the schema drift check) reports `[changed]`, `[missing]` and `[extra]` pages and exits 1. The policy text that the schemas cannot carry (the code-only rules, the limitations, what is not guaranteed) is the hand-written `packages/evalschema/SCHEMA_POLICY.md`; the release notes are `packages/evalschema/CHANGELOG.md` (I20).
10. **Runtime dependencies:** stdlib, pydantic (and its dependencies) and `rfc8785` only.

## Rejected alternatives
- **Tolerant reader (ignore unknown fields).** It silently loses data written by newer producers, which is the exact failure the user ruled out (Q5).
- **Accept older 0.0.x files with defaults.** Before 0.1 there is no compatibility promise. Partial acceptance would create untested upgrade paths. Exact match keeps behaviour predictable until a policy with migrations exists.
- **One shared frozen-fixture directory that is edited on every release.** Editing frozen fixtures removes the evidence that old files were ever readable; the test would always pass and prove nothing.
- **Frozen fixtures that must parse directly under every later version.** That contradicts exact-match reading during 0.0.x; the test would have to be weakened or skipped. An explicit mismatch error, or an explicit upgrade, keeps it strict.
- **Date-based or integer schema versions.** Change classes cannot be expressed. Semver is what downstream tools expect.
- **`$id` as an https URL.** No domain is owned (OQ1). A URL that does not resolve, or that someone else later controls, is worse than a URN. A URL alias can be added later.
- **Generate schemas at runtime only.** Consumers in other languages need static files, and reproducibility needs locked bytes.
- **Per-entity independent versions.** Entities cross-reference each other, so independent versions create a compatibility matrix nobody tests.

## Consequences
- During 0.0.x, every release makes all earlier files unreadable without an upgrade step. That is intended for a pre-release, and the frozen-fixture test makes it visible.
- From 0.1.0 every release must ship its upgrade step and upgraded twins.
- The `$id` URN uses the unregistered namespace identifier `tracer`. RFC 8141 expects registered NIDs, so the URN is a stable identifier but not a formally registered one. Accepted under OQ1.

## Decided items (formerly [Proposed]; all decided by the user in revision 5)
- **P-22. Compatibility after 0.0.x. Decided by the user (revision 5): accepted as recommended.** Decision: between 0.1.0 and 1.0.0 a minor bump is breaking and a patch is additive; from 1.0.0 a reader accepts the same major with minor <= its own (missing optional fields become `None`), rejects a newer minor with `SchemaVersionTooNew`, and rejects another major unless it is upgraded through `upgrade()`. Reason: SCOPE defines only 0.0.x; without a stated rule, the first 0.1.0 release would have to invent one under time pressure, and the frozen-fixture test (c) needs to know which versions must upgrade. Had it been decided otherwise: the chosen rule replaces this one, and only reader-rule tests for 0.1.0+ change; nothing in 0.0.1 changes.
