## Context
Metrics range from deterministic numbers (latency, WER, talk ratio) through ratings and enums to LLM-judged booleans (goal completion, expected outcome). The verdict needs every required metric to produce a pass/fail decision, so pass rules must be explicit and typed for every value type, including booleans, and every rule must state which direction is good. Some metrics are per turn (F5 `min_score` means "share of turns that pass"). Money must never be a metric unit (cost lives in ADR 0014). LLM judges need provenance for later calibration (MVP-2).

## Decision
1. **`MetricDefinition`** (versioned, ADR 0009): `key: MetricKey` (revision 8: our own keys use the stricter `MetricKey` of ADR 0017 Decision 5; revisions 3-7 said `MachineKey`), `kind` (deterministic|llm_judge|audio|latency), `value_type` (boolean|rating|enum|numeric), `scale` (for rating: integer min/max; for enum: the option list), `unit` (numeric only; a closed set of non-currency units, exactly `ms`, `count`, `ratio`, `percent`, `wer`, `cer` since revision 8), `requires[]` (ADR 0004), `languages[]`, `script_sensitive: bool` (required, no default; ADR 0004), `pass_rule?` (for `per_turn_share`: a `range` on the share, Decision 3a), `aggregation`, `parameters[]` (revision 8, Decision 4a), `implementation_ref`, `prompt_template`, `prompt_variables`, `judge_model_ref` (conditions in Decision 1a).
1a. **Field conditions (revision 8).** The exact list, with types, is `docs/phase1/api-surface.md` section 19.4.1.
   - **Kind.** `kind=llm_judge` requires `prompt_template` (non-empty `VerbatimText`), `prompt_variables` (unique `MetricKey` names, equal as a set to the `{{name}}` variables in the template; any other `{{` in a template is rejected) and `judge_model_ref: ModelRef{provider, model}`, and forbids `implementation_ref`. The other kinds require `implementation_ref` (a `MachineKey` `<namespace>:<name>` naming the scorer, for example `builtin:wer`) and forbid the three judge fields. A judge without prompt and model cannot be reproduced. A scorer name on a judge would name two computations for one value.
   - **`judge_model_ref` has no `config_ref`.** A definition is portable and digested, while a `config_ref` names one deployment's variable. The key is reached at run time through the Project's `provider_configs` entry with the same `(provider, model)` (ADR 0007 Decision 1).
   - **Scale.** `RatingScale{min: int, max: int}` (min < max) iff rating; `EnumScale{options: list[MetricKey]}` (non-empty, distinct) iff enum; absent otherwise.
   - **Unit.** Required iff numeric. Value domains: `ms` >= 0; `count` integers >= 0; `ratio` [0,1]; `percent` [0,100]; `wer` and `cer` >= 0 (error rates may exceed 1).
   - **Range bounds** lie within the value domain (the scale for rating, the unit's domain for numeric, [0,1] for the share), and the set of passing values must be non-empty (integers only for rating and `count`).
   - **Languages** take one of two forms (revision 9, P-59 decided by the owner). The first is the string `"language_independent"`, which requires `script_sensitive=false`. The second is a non-empty list with no two entries sharing a primary language (ADR 0004 Decision 6 matches by primary language). The field is required. ADR 0004 Decision 6 gives the applicability rules and the `language_not_observed` reason.
   - **Reserved prompt variable `expected_outcome`.** The runner fills it with the evaluator's expected outcome (ADR 0013 Decision 2).
2. **Pass rule** (user decision P-25, revision 5): a discriminated union on `kind` with exactly three kinds. Each kind states its own direction; there is no rule kind whose direction is implied.
   - `range{min?, max?, inclusive}` (value object `RangeRule`): numeric and rating only; at least one bound; `inclusive` applies to both bounds. The bounds are the direction: `range{max}` means lower is better (latency, WER: passes iff `value <= max`, or `<` when not inclusive); `range{min}` means higher is better (a judge score: passes iff `value >= min`, or `>`); both bounds mean a target band.
   - `equals_true` (value object `EqualsTrueRule`): boolean only. Passes iff the value is `true`. This is how required boolean checks such as goal completion and the evaluator's expected outcome get a pass rule.
   - `one_of{options[]}` (value object `OneOfRule`): enum only. `options` is a non-empty subset of the definition's enum options without duplicates. Passes iff the value is in `options`.
   A rule whose kind does not fit the definition's `value_type` is rejected. A rule with no direction is rejected: an unknown kind (including any single-number rule), a `range` with neither bound, or a bare number in place of a rule. There is no coercion (for example `true -> 1`).
3. **Aggregation:** `per_conversation` (one value per run) or `per_turn_share{turn_rule}` (revision 7, P-58: replaces `per_turn_share{min_share}`; the threshold on the share is the ordinary `pass_rule`, Decision 3a). **not_applicable turns (user decision P-26, revision 5):** turns whose per-turn result is not_applicable are excluded from the denominator. **Undetermined turns (user decision P-56, revision 6):** a turn whose per-turn judge verdict is `undetermined` (`JudgeInfo.per_turn[].verdict`) is also excluded from the denominator. The share is `passed turns / (passed + failed turns)`, and whether the result passes is decided by the definition's `pass_rule` applied to the share (Decision 3a).
   - The result carries `PerTurnCounts{passed, failed, not_applicable, undetermined}` (value object; all four are integers >= 0 and required) inside `MetricResult.per_turn` (Decision 3a), so the excluded turns stay visible.
   - **Turn coverage** = counted turns / total turns, where counted = `passed + failed` and total = `passed + failed + not_applicable + undetermined`. It is the exact ratio of two integers carried by `PerTurnCounts` (never a rounded decimal) and is always shown as `"{counted}/{total} turns"`.
   - **Rendering rule (same pattern as `weight_coverage`, ADR 0013):** the share is never shown without its turn coverage. The one shared helper is `render_per_turn_share(result) -> str | None`, which returns `"turn share {share} (turn coverage {counted}/{total} turns)"` with the share formatted to 2 decimal places (display only), or `None` when the result is not scored. Other renderers call it.
   - **No counted turn** (`passed + failed == 0`): if at least one turn is undetermined, the result is `error` with `error.code=judge_undetermined` (consistent with P-09: a turn applied and the judge could not decide it); otherwise (every turn not_applicable) it is `not_applicable`, with the `na_reason` chosen from the turn reasons by the ADR 0004 precedence (P-10). The precedence between these two cases is a detail fixed while applying P-56.
3a. **Where the share is stored (user decision P-58, revision 7).** The share is stored in a separate field, never in `MetricResult.value`. This concerns the data record (the pydantic/JSON model, which the Phase 2 tables will mirror).
   - **`MetricResult.per_turn: PerTurnSummary?`** (value object) = `{share: DecimalString?, counts: PerTurnCounts, counted_turns: int, total_turns: int}`. `counted_turns = passed + failed` and `total_turns = passed + failed + not_applicable + undetermined` (>= 1) are the turn coverage, stored as two integers and checked against `counts` on load. (`JudgeInfo.per_turn[]`, the judge's per-turn verdict list, is a different field with the same name inside `JudgeInfo`.)
   - **The share** is a canonical `DecimalString`: the exact quotient `passed / (passed + failed)` in `Decimal`, rounded half-even at scale 18 when it does not terminate (the same rule as the weighted score, ADR 0013, and P-35). It lies in [0,1]. It is present iff `counted_turns > 0`. On load the share is recomputed from `counts` and compared; a share that disagrees, or one present with no counted turn, is rejected. A decimal string (not a float) is used because the value is an exact ratio of two integers that is compared with a stored threshold and digested; a float would make the equality check and the digest depend on division rounding.
   - **Presence:** for a definition with `aggregation=per_turn_share`, `per_turn` is required when `status=scored` (then `counted_turns > 0` and `share` present). It is also required for the two P-56 outcomes with no counted turn: `error`/`judge_undetermined` (some turn undetermined) and `not_applicable` (every turn not_applicable); then `share` is absent. It is absent when no per-turn outcome exists (for example `not_applicable` with `missing_input` before any turn was evaluated, or an `error` from a failed judge call). **Revision 32 (A-C6):** with a run-level reason (`missing_input`, `agent_channel_unknown`) it is forbidden: no turn was read, so `MetricResult` rejects a summary there at the field `per_turn` and the JSON Schema says the same. A bundle also recomputes `total_turns` and `counts.not_applicable` of a stored summary from the turns the result read (ADR 0004 Decision 9, T-B16). **Revision 33 (re-gate condition C10, N-R3):** a `per_turn_share` metric implies a transcript input: its per-turn outcomes are outcomes of turns, and turns are read only through a `transcript` or `agent_transcript` entry in `requires`. A metric that reads no transcript therefore reads no turn and stores no `per_turn` summary. `MetricDefinition` does not reject a `per_turn_share` definition without a transcript input in 0.0.1 (whether "transcript implies a turn" becomes a run rule is open, to be decided with the export builder); the rule is held on the results: a bundle rejects a stored summary on a per-turn result that read no turn at `per_turn.total_turns`, since a summary counts at least one turn (ADR 0004 Decision 9, P-C6); a scored one is reported at `status` (T-B13). For any other aggregation, `per_turn` is forbidden.
   - **`value` is `None`** for every result of a `per_turn_share` definition (forbidden, not merely optional). The per-turn values keep the definition's `value_type` and live in `JudgeInfo.per_turn` or per-turn evidence.
   - **`passed`** is computed by applying the definition's `pass_rule` to the share. For `per_turn_share` the pass rule must be a `range` whose bounds lie in [0,1] (`range{min: 0.8, inclusive: true}` reads "at least 80% of counted turns pass"); the comparison is done in `Decimal`, with a float bound converted through its shortest round-trip decimal form (the ECMAScript form JCS uses). Without a pass rule, `passed` is `None` (P-08). A stored `passed` that disagrees with the rule applied to the share is rejected.
   - **Exact rule for the share's pass rule (revision 8).** It is `None` or a `RangeRule`, whatever `value_type` is (`equals_true` and `one_of` are rejected). Every present bound b satisfies 0 <= b <= 1 in `Decimal`. The range must admit some value in [0,1], so `{min: 1, inclusive: false}`, `{max: 0, inclusive: false}` and `{min: x, max: x, inclusive: false}` are rejected. The value-type fit rule of Decision 2 applies to `turn_rule` instead.
   - **`turn_rule`** (required for `per_turn_share`) is a pass rule fitting the definition's `value_type`, applied to each turn's value to decide whether that turn passed: `equals_true` for boolean per-turn judge verdicts (`yes` passes, `no` fails, `undetermined` is counted as undetermined), `range` for numeric and rating values, `one_of` for enums. Without it no turn could be called passed or failed, and a direction would be implied, which P-25 forbids.
   - **Verdict and weighted score (ADR 0013 Decision 8a):** the metric is one check. Its outcome comes from `passed` (scored + passed -> passed; scored + not passed -> failed; P-56 outcomes -> errored or not_applicable). In the weighted score it contributes `w * passed` (1 or 0), never `w * share`.
4. **`MetricBinding`** (entity `mbd`, versioned) binds a definition `(id, version)` to an evaluator, with parameter overrides. Bindings are unique per evaluator and definition.
   - **Fields (revision 8):** `evaluator_id: EvaluatorId`, `metric: MetricDefinitionRef{id, version, content_digest?}`, `params: dict[MetricKey, I-JSON]` (required, may be empty, stored unchanged), `enabled: bool` (required).
   - Uniqueness counts every version and disabled bindings (`check_bindings_unique`).
   - A disabled binding may be listed by its evaluator, is never run, writes no MetricResult, and may not be referenced by a rubric item (ADR 0013 Decision 7). It is not a `not_applicable` outcome, because NA describes a run's inputs, not a configuration choice.
4a. **What `params` overrides (revision 8).** Only parameters the definition declares in `parameters: list[MetricParameter{name: MetricKey, value_type: boolean|integer|number|string|json, default?}]`. When a binding meets its definition (`check_binding_params`, called by Rubric and snapshot validation):
   - every key is declared;
   - every value matches its type strictly (no bool/number coercion);
   - every parameter without a default is present.
   The effective values are the defaults overlaid by `params`. Params never change a definition field (pass rule, requires, scale, unit, aggregation, languages, `script_sensitive`, kind, prompt). A different threshold is therefore a different definition or version (E6, **decided by the owner in revision 9: accepted**). Example: p95 latency limits of 800 ms and 1500 ms for two evaluators need two definitions, or two versions used by different evaluators. The rule also holds at result time: `MetricResult.passed` is computed from the definition's `pass_rule` alone, and binding params never enter that computation (P1-11). Reason: an override of the pass rule would put the threshold in two places, the problem P-58 removed, and an undeclared name would be silently ignored by a scorer.
5. **`MetricResult`** values: boolean -> JSON bool; rating -> integer within the scale; enum -> one of the options; numeric -> a finite JSON number. Status, NA and error rules are in ADR 0004. `evidence_refs[]` point to turns, spans or artifact ranges (ADR 0012).
   (Revision 10: the scorer build is recorded in `MetricResult.scorer`, Decision 5a. The language fields `language_source` and `declared_language_transcript_ids` are defined in ADR 0004 Decision 6g.)
5a. **The scorer that produced a result (P-61, decided by the owner in revision 10: accepted as proposed).** `MetricResult.scorer: ScorerInfo?`, with the value object `ScorerInfo{implementation_ref: MachineKey, version: MachineKey}` (ADR 0001 Decision 8).
   - **Presence.** `scorer` is required iff the definition's `kind` is `deterministic`, `audio` or `latency` and `status` is `scored` or `error`, which means a non-judge scorer ran. It is forbidden otherwise:
     - for `not_applicable`, which is decided before any scorer runs (ADR 0004);
     - for every `llm_judge` result, which carries `JudgeInfo` instead. A judge result with `scorer` is rejected.
     The rule is the same for both aggregations, so a non-judge `per_turn_share` result that is scored, or that errored, also carries `scorer`.
   - **`implementation_ref`** equals the definition's `implementation_ref`. The result alone cannot check this, so it is checked where the result meets its definition: the P1-11 result-against-definition check (P1-11 names the function) and the bundle consistency check of P1-14. A mismatch names the result ID and both values (they are scorer names, never credentials or personal data).
   - **`version`** is the version string that the scorer declares in the Phase 3 scorer registry. It is stored verbatim, never parsed or ordered, and compared only for equality. There is no semver assumption (ADR 0009 Decision 1 rejects semver for our own versions, and a scorer's version format is its own). `MachineKey` admits forms such as `3`, `1.4.2` and `2026.10.1+g1a2b3c`.
   - **A scorer that cannot run is a configuration error, not a result.** If the registry has no scorer for `implementation_ref`, or cannot state its version, the run stops before it starts (the same rule as a missing provider configuration, ADR 0007 Decision 1). No `error` result without `scorer` is ever written for a non-judge definition, so the presence rule never forces a guessed version. (Detail fixed while applying P-61; confirmed by the owner after revision 10, recorded in revision 11.)
   - **Rescoring** an old run with a newer scorer writes new results whose `scorer.version` differs. Reports compare results across runs only after checking that `scorer` is equal, and say so when it is not (Phase 3).
   - No Phase 1 mapping (F1-F8) imports metric results, so no current mapping is affected. A future importer of third-party scores that cannot name the scorer build cannot write such a result; that is a gap under ADR 0018, never a guessed version.
6. **`JudgeInfo{model_ref, prompt_sha256, params, per_turn[{turn_seq, verdict: yes|no|undetermined, p_yes?, reported_model?}], confidence?, reported_model?}`.** `p_yes` and `confidence` are present only if the judge produced them, never synthesized. Turn text sent to a judge is data: prompt-injection text inside a turn is stored verbatim and has no schema effect.
   - **The model that answered (P-62, decided by the owner: accepted as proposed; recorded in revision 11).** `model_ref` is the model the judge was asked for. `JudgeInfo.reported_model: VerbatimText?` is the model string from the provider's response to the call that produced the overall verdict, and `JudgeInfo.per_turn[].reported_model: VerbatimText?` the same for the call that produced each turn's verdict (value object `JudgeTurnVerdict`). Each is present iff that response carried a model string, non-empty when present, stored verbatim (code point for code point, rendered only through `display_safe()`, ADR 0017), never parsed, compared only for equality, and never filled from `model_ref`, the project configuration or a pricing catalog. An absent value means "the provider did not say". It does not replace `model_ref`, and nothing resolves keys or prices through it. Its bidi controls are detected by `contains_bidi_controls()`; like every raw provider string it has no stored flag (`docs/phase1/api-surface.md` section 22.3 N32).
7. Metric numeric values are floats (measurements). Monetary values are never metric values; they are `Money` in CostRecord.
8. **Evaluator, ScriptedTurn, ExpectedToolCall** (P1-09): `Evaluator.max_duration` is bounded; ScriptedTurn indexes are contiguous from 0; `ExpectedToolCall.match` is a closed enum; bindings are unique; ScriptedTurn language is a SupportedLanguage; profile values in Evaluator instructions and ScriptedTurn text appear only as `{{profile.<field>}}` placeholders (ADR 0006 Decision 9).
   **Fixed in revision 8** (api-surface 19.4.1).
   - **Evaluator fields:** `name: HumanLabel`, `language`, `instructions`, `expected_outcome` (both non-empty `VerbatimText`), `persona: PersonaRef`, `test_profile: TestProfileRef?`, `metric_bindings: list[MetricBindingRef]` (non-empty, unique by binding id at any version), `scripted_turns` and `expected_tool_calls` (default empty).
   - **`expected_tool_calls_exhaustive: bool | None = None`** (batch 17, finding F5-2, owner decision; placed after `expected_tool_calls`). A strict JSON boolean or `null` (like `MetricBinding.enabled`: `0`, `1`, `"true"` are rejected), optional in the JSON Schema with default `null`. `None`: not stated (nothing is said about calls other than the listed ones). `True`: a tool call other than the expected ones is a failure; with `expected_tool_calls == []` it means the agent must call nothing. `False`: stated and not exhaustive (other calls are allowed). An empty list with `None` or `False` is no expectation about tool calls. The flag is evaluator content, so it is inside the content digest (a changed flag is a new version). Additive (minor) under ADR 0008; 0.0.1 is unreleased, so `schema_version` stays `0.0.1` and the field is listed in `packages/evalschema/CHANGELOG.md`. Tests: `test_evaluator_exhaustive.py`.
   - **`max_duration_ms`:** a strict integer from 1 to 14,400,000 (4 h), emitted as `{"type": "integer", "minimum": 0, "exclusiveMinimum": 0, "maximum": 14400000}` (ADR 0002 Decision 2).
   - **Placeholders:** any profile placeholder requires `test_profile`, because nothing else could fill it.
   - **`ScriptedTurn{index, text, language}`:** the name is `index`, a list position, as in `Exchange.index`. It is not `seq`, because a scripted turn is not a Turn.
   - **`ExpectedToolCall{name, match, arguments?, order_index}`:**
     - `match` is `name_only` (no `arguments`), `arguments_exact` (`arguments` required, `{}` allowed) or `arguments_subset` (non-empty `arguments`). Comparison is by JSON value with the observed arguments.
     - `order_index` is a rank. Ranks form 0..R. All calls of rank r come before any call of rank r + 1, and equal ranks may occur in any order.
     - Each expected call matches a different observed call.
     - Truncated observed arguments can neither pass nor fail an argument comparison.
     - String values of `arguments`, at any depth, may hold profile placeholders, and so may `Evaluator.expected_outcome` (E7, decided by the owner in revision 9; ADR 0006 Decision 9a). The placeholders are resolved before the comparison and never stored resolved.
     - Without `arguments`, the argument correctness that the plan lists for tool calls could not be expressed.

## Rejected alternatives
- **Untyped `value: Any`.** "Scored value matches type" could not be validated, and a judge returning the string "yes" would be accepted for a boolean metric.
- **A single-number pass rule with an implied direction (dropped by the user, P-25).** A reader must remember which way it points, and a lower-is-better metric configured with it passes exactly the bad runs. `range{min}` and `range{max}` say the same thing with the direction written down, so a second way to express "at least" adds only a way to get it wrong.
- **A direction flag (`higher_is_better: bool`) on the definition.** It can be set wrongly or forgotten, and it separates the direction from the bound it governs.
- **Coercing booleans to numbers so a numeric rule covers them.** It is an undocumented conversion that differs between languages (JSON Schema does not treat `true` as `1`), so pydantic and JSON Schema would disagree on which results pass.
- **No pass rule for boolean checks (treat the boolean as the pass).** Then `test_required_metric_needs_pass_rule` would need an exception for booleans, and a check whose desired answer is `false` (for example "did the agent disclose the account number") could not be expressed.
- **not_applicable turns counted as failures in `per_turn_share`.** It punishes missing inputs and turns the share into a lower bound; counting them as passes rewards missing inputs.
- **Normalizing every metric to [0,1].** It loses units and interpretability, and the normalization itself becomes a hidden judgement.
- **Currency as a metric unit (`usd`).** It duplicates the cost model with float arithmetic and no provenance.
- **Decimal strings for metric values.** Metric values are measurements with inherent error, not ledger amounts. Statistical tooling needs floats.
- **Synthesizing a judge confidence from verdict counts.** That is fabrication. Calibrated confidence is an MVP-2 measurement.
- **`judge_model_ref` as a `ProviderConfigRef` (revision 8).** Its `config_ref` is a deployment detail. It would make a shared definition carry one machine's variable name, and renaming a variable would force a new definition version that changes no result.
- **Free-form binding `params` (revision 8).** A misspelled name would be ignored by the scorer without notice. A parameter that could replace the pass rule would duplicate the threshold.
- **A disabled binding reported as `not_applicable` (revision 8).** NA describes missing inputs of one run. Using it for a configuration choice would add an NA reason, and every run would stay inconclusive for a reason fixed at authoring time.

## Consequences
- Required metrics must have a pass rule (ADR 0013), and every value type has one.
- A boolean check whose desired answer is `false` is written as a definition whose question is phrased positively ("agent protected the account number") with `equals_true`; there is deliberately no `equals_false`, so every required boolean reads the same way in reports.
- F5 `min_score` maps to a `per_turn_share` definition whose pass rule is `range{min: min_score, inclusive: true}` (revision 7, P-58); an F5 numeric bound maps to `range`.
- `per_turn_share` needs per-turn results or `JudgeInfo.per_turn`. A metric using it must have turn-level evidence.

## Invariants (testable)
- I1. Inclusive and exclusive range rules evaluate correctly at both bounds. Test: `test_pass_rule_range_inclusive_and_exclusive`.
- I1a. A lower-is-better metric (latency in ms) is expressed with `range{max}` and passes at or below the bound; a higher-is-better metric (a judge score) is expressed with `range{min}` and passes at or above it. Tests: `test_latency_lower_is_better_expressed_with_range_max`, `test_score_higher_is_better_expressed_with_range_min`.
- I1b. A rule with no direction is rejected by pydantic and JSON Schema (an unknown kind such as a single-number rule, a `range` with neither bound, a bare number). Test: `test_pass_rule_without_direction_rejected`; the kind set (range, equals_true, one_of) is checked by `test_all_closed_enums_exact`.
- I2. A range needs at least one bound. Test: `test_range_requires_at_least_one_bound`.
- I3. `equals_true` passes exactly on `true`; `one_of` passes exactly on listed options. Tests: `test_equals_true_rule_boolean`, `test_one_of_rule_options_subset`.
- I4. The rule kind must fit the value type (no `range` on boolean or enum, no `equals_true` on numeric, no `one_of` outside enum, options a subset of the scale). Test: `test_pass_rule_kind_matches_value_type`.
- I5. A required boolean check (goal completion, expected outcome) with `equals_true` satisfies the rubric rule. Test: `test_required_boolean_check_with_equals_true_ok`.
- I6. Numeric units exclude currency. Test: `test_numeric_units_exclude_currency`.
- I7. For `per_turn_share`, the stored share and the bounds of the pass rule lie in [0,1] (revision 7 meaning, P-58; formerly `min_share`). Test: `test_per_turn_share_bounds_0_1`.
- I7c. (P-58) `value` is `None`; the share lives in `per_turn.share` and is checked against the counts; a mismatching share is rejected; coverage integers are checked against the counts; the share is absent iff no turn was counted; `passed` comes from the range pass rule applied to the share; a `per_turn_share` definition needs a `turn_rule` and, if it has a pass rule, a `range` within [0,1]. Tests: `test_per_turn_share_value_is_none`, `test_per_turn_share_stored_in_per_turn_summary`, `test_per_turn_share_checked_against_counts`, `test_per_turn_share_mismatch_rejected`, `test_per_turn_coverage_checked_against_counts`, `test_per_turn_share_absent_when_no_turn_counted`, `test_per_turn_share_pass_from_range_rule`, `test_per_turn_share_definition_requires_turn_rule`, `test_per_turn_share_pass_rule_must_be_range`.
- I7a. not_applicable turns are excluded from the denominator and counted in `per_turn.counts` (revision 7: formerly `per_turn_counts`); with no applicable turn the metric is not_applicable. Tests: `test_per_turn_share_excludes_na_turns_from_denominator`, `test_per_turn_share_not_applicable_when_no_turn_applies`.

## Proposal of revision 10, decided after it (kept for traceability)
- **P-62. Record the model that the judge provider reports (finding N16). [Proposed in revision 10; decided by the owner: accepted.]**
  - **Finding.** `JudgeInfo.model_ref` is the model the judge was asked for, often an alias (for example a "latest" name). Providers move aliases to new model builds, and most provider responses state which model answered. Without that string, two runs with equal snapshots and equal `model_ref` can have been judged by different models, and nothing in the records tells them apart. This is the judge-side twin of P-61.
  - **Proposal.**
    - `JudgeInfo.reported_model: VerbatimText?` (non-empty when present): the model string from the provider's response to the call that produced the overall verdict.
    - `JudgeInfo.per_turn[].reported_model: VerbatimText?`: the same for the call that produced that turn's verdict.
    - Each is present iff that response carried a model string. It is stored verbatim (code point for code point, rendered only through `display_safe()`, ADR 0017), never parsed, and compared only for equality.
    - It is never filled from `model_ref`, from the project configuration or from a pricing catalog. An absent value means "the provider did not say".
    - It does not replace `model_ref`, and nothing resolves keys or prices through it.
  - **Why `VerbatimText` and not `MachineKey`.** The value is provider output. A response whose model string falls outside the `MachineKey` charset must not make the result unwritable, which the core rule forbids. `VerbatimText` keeps it and flags bidi controls (ADR 0017).
  - **Why per call and not one list per result.** A per-turn judge makes one call per turn, and an alias can move during a run. A single result-level value would claim one model for every call. A deduplicated list would hide which turns were judged by which model, and whether some responses carried no model string.
  - **Places considered and rejected.** The ConfigSnapshot: it is frozen before the run, while the reported model is known only after each call. `UsageRecord.model`: usage records cost, not verdicts, and its `model` names the billed model as reported for billing. Linking a verdict to usage records would make a verdict's provenance depend on cost telemetry being present.
  - **Why it is proposed and not applied.** It adds fields that every judged result can show, which is user-visible beyond what the owner accepted for P-61. Both fields are optional, so no producer is blocked and no existing test changes.
  - **Recommendation: accept.** It is the reproducibility record for judges that P-61 is for scorers, and the cost is two optional fields.
  - **If decided otherwise.** `JudgeInfo` is unchanged, and `SCHEMA_POLICY.md` states the limitation: results judged through a moving alias cannot be told apart by model build.
  - **Conditional tests (P1-11):** `test_judge_reported_model_verbatim_and_optional` (result level: `None` when not reported, and an empty string rejected; a value equal to `model_ref.model` is valid, because a provider may report the name it was asked for; a present string is kept code point for code point, including one outside the `MachineKey` charset; bidi controls are flagged), `test_judge_per_turn_reported_model_verbatim_and_optional` (the same per turn, with turns that differ and turns that lack it).

## Proposal of revision 9, decided in revision 10 (kept for traceability)
- **P-61. Record the scorer and its version on each result. [Proposed in revision 9; decided by the owner in revision 10: accepted.]** Found in revision 8 (api-surface 19.6 N10) and proposed in revision 9.
  - **Finding.** `implementation_ref` names a scorer (for example `builtin:wer`) but not its build. The ConfigSnapshot freezes the definitions, not the scorer code. Suppose two runs share one snapshot digest and the WER text normalizer changed between releases. Their results can then differ, and nothing in the records tells them apart. Judged results are already covered, because `JudgeInfo` records the judge model and the prompt digest. Results of the other kinds are not.
  - **Proposal.** `MetricResult.scorer: ScorerInfo?`, a new value object `ScorerInfo{implementation_ref: MachineKey, version: MachineKey}` (ADR 0001 Decision 8 gains it if accepted).
    - Present iff the definition's `kind` is `deterministic`, `audio` or `latency` and `status` is `scored` or `error`, which means a scorer ran.
    - Absent for `not_applicable`: NA is decided before any scorer runs (ADR 0004).
    - Absent for `llm_judge` results, which carry `JudgeInfo`. A judge result with `scorer` is rejected.
    - `implementation_ref` equals the definition's `implementation_ref`. This is checked where the result meets its definition (P1-11, and the bundle check of P1-14).
    - `version` is the version string the scorer declares in the Phase 3 scorer registry, stored verbatim. It is never parsed, never ordered and compared only for equality: there is no semver assumption (ADR 0009 Decision 1 rejects semver for our own versions, and a scorer's version format is its own).
  - **Places considered and rejected.**
    - The ConfigSnapshot. Its digest is computed before the run. Two identical configurations run on different installations would get different digests, which defeats deduplication by digest (ADR 0006 Consequences). The snapshot would also name a scorer before any scorer ran, and rescoring an old run with a newer scorer would need a new snapshot.
    - A per-run map from `implementation_ref` to version. A rescore writes new results for the same run, so one map could not describe both sets. Per-result data keeps each record of fact self-describing.
    - Inside `implementation_ref` (`builtin:wer@3`). Every scorer upgrade would become a new definition version and a new definition digest for a code change. The definition would then claim a build it cannot guarantee, and `key@version` text is display-only in this schema.
  - **Why it is user-visible.** Every scored or errored non-judge result shows which scorer build produced it. Reports (Phase 3 and later) can flag comparisons across runs whose scorer versions differ. Because the field is required for those results, a producer that does not know the scorer version cannot write such a result. No Phase 1 mapping (F1-F8) imports metric results, so no current mapping is affected.
  - **Recommendation: accept.** Reproducibility is a stated goal of `Run.config_snapshot`. Without this field, a changed scorer silently changes values under an unchanged definition version.
  - **If decided otherwise.** There is no scorer field. `SCHEMA_POLICY.md` states the limitation: results from different scorer builds under one definition version cannot be told apart.
  - **Tests (conditional in revision 9, binding since revision 10):** `test_scorer_info_present_iff_non_judge_scored_or_error`, `test_scorer_info_matches_definition_implementation_ref`, `test_scorer_version_stored_verbatim` (P1-11).
