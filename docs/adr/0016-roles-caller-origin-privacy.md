# ADR 0016: Roles, caller origin, privacy markers and the export rule

## Context
The project evaluates one thing: the AI agent. The caller is either a human or a simulator. The framework scores both simulated test calls and recordings of real calls (post-call analytics). Real calls contain real people, and a recording or transcript can also contain speech whose speaker is not identified (for example an undiarized STT transcript), which may be a real person. Data about real people is personal data. It needs a consent and retention record, and it must not spread into shared exports or benchmarks unless it has been protected.

## Decision
1. **`Role ∈ {caller, agent, unknown}`** (closed; revision 5 user change). `agent` is the AI agent under evaluation; metrics evaluate only `agent` turns and audio. `caller` is the party calling the agent, a human or a simulator as stated by `Run.caller_origin`. `unknown` is speech whose speaker the source does not identify (for example Sarvam REST STT, which has no diarization). Caller and unknown speech is context (for example input to the judge, interruption timing).
2. **`Run.caller_origin ∈ {simulated, human}`**: required, with no default. `Run.mode=simulated` implies `caller_origin=simulated`. A `recorded` run may have either origin.
3. **`PrivacyMarker`** (value object): `{human_subject: bool, human_subject_reason?, consent?: ConsentRecord, retention?: RetentionPolicy}`:
   - `ConsentRecord{status: obtained|not_obtained|unknown, reference?, recorded_at?}`
   - `RetentionPolicy{retain_until?: UtcDatetime, policy_ref?, delete_on_expiry: bool}`
   - **Consent and retention (P-46):** required if and only if `human_subject=true`; absent when false (a consent record for a synthetic voice is meaningless and would read as a consent gap in reports).
   - `human_subject_reason ∈ {marked_before_role_evidence, real_person_likeness, manual}` (P-47, Decision 5).
4. **Payloads carry a marker.** A PrivacyMarker is required on every Artifact, every Transcript and every recording- or transcript-based DatasetItem. ToolCallEvent arguments and results belong to their run and take the run's derived value (Decision 5).
5. **The human-subject marker (user decision 1; P-47 decided in revision 5).**
   - `derive_human_subject(run, turns) -> bool` is a pure function (revision 11, N24 decided by the owner, option A: a Run does not hold its turns, so the caller passes the `Turn` records of the run's transcripts; `check_human_subject_marker(marker, run, turns)` takes the same arguments). **Role evidence is the set of roles found** in the supplied turns and in the run's channel maps, never the mere presence of a transcript or map: no turns supplied and no channel role means no role evidence, which gives `true`, never `false`. **`turns` is required (revision 12, O1 decided by the owner, option A):** it has no default in all three functions, so omitting it raises `TypeError`, and an explicitly empty sequence (`()` or `[]`) is the statement "no turns", which with no channel role is no role evidence and gives `true`. Reason: with a default, a caller that forgets the turns of a transcript holding an `unknown` turn, on a simulated run whose channel map shows only caller and agent, would get a silent `false`. Detail fixed while applying O1, confirmed by the owner in revision 13: `turns=None` is not a sequence of turns and raises `TypeError` too, so `None` cannot stand in for a forgotten argument; only a real sequence is accepted. It is `true` if `caller_origin=human`; `true` if any role evidence in the run (any Turn role in any transcript, any ChannelMap channel role) is `unknown`; `true` if the run has no role evidence at all (no transcript with roles and no channel map), because a real person cannot be ruled out. It is `false` only if `caller_origin=simulated`, role evidence exists, and every role in it is `caller` or `agent`. A `mixed` channel (ADR 0012, P-31) is evidence of exactly the caller and the agent: on a simulated run it rules a human out, on a human-origin run the origin already makes the run human-subject.
   - **The stored marker may be stricter than the derivation, never looser (P-47, user decision).** A stored `human_subject=true` where the derivation gives `false` is valid only with a `human_subject_reason`: `marked_before_role_evidence` (written while the run had no role evidence), `real_person_likeness` (real-person data invisible in roles and origin, for example a simulated caller voice cloned from a real person) or `manual` (a person chose to mark it). A person may always set `true` manually. A stored `false` where the derivation gives `true` is a validation error.
   - Producers set the marker from `derive_human_subject()`. A producer that writes a marker while the run has no role evidence writes `true` with reason `marked_before_role_evidence`, so the record stays valid when later evidence derives `false` (Artifact and Transcript are written-once records of fact, ADR 0009).
   - **A too-loose marker is corrected by a new record, never by editing the old one:** the corrected Artifact, Transcript or DatasetItem gets a new ID, and the loose record keeps failing validation wherever it is used (a bundle cannot hold two contents under one record ID, ADR 0009).
   - A DatasetItem with a recording and no source run has no role evidence and is therefore `human_subject=true`.
   - **`DatasetItem.source_run_id` is provenance only (revision 12, O7 decided by the owner, option A).** It names the run that the item's recording or transcript came from. It is not membership of a run (ADR 0001, N22) and is never required to resolve. The item's marker is checked with `check_human_subject_marker(item.privacy, run, turns)` against that run and its turns when the caller supplies them; an item without `source_run_id`, or whose run and turns are not supplied, has no role evidence and derives `true`.
6. **Caller identifiers (P-43).** A transport `user_id` (possibly a phone number) is stored only in `Run.caller_external_id: CallerExternalId{value: VerbatimText, privacy: PrivacyMarker}`, which gives one place to delete it on retention expiry and one place for an export builder to strip it. It never appears in a ConfigSnapshot or an ExportBundle. **Revision 22 (B8):** an `ExportBundle` of any purpose, `internal` included, rejects an embedded run that carries `caller_external_id` (`[caller_external_id]`, naming the run, never the value); the export builder strips it. A `RunBundle` on its own may carry it (it is the producer's record).
7. **`ExportBundle`** (entity `exp`): `purpose ∈ {internal, shared_export, benchmark}`.
   - **The export rule (user decision 1):** if the purpose is not `internal`, every audio, text and tool-argument/result payload that is marked (or, for tool calls, derived) as human-subject data must be a `SealedPayload` (ADR 0015) or carry a `RedactionRecord{method, tool_ref, performed_at, covers[]}`. This covers human callers, runs with unknown speakers and runs without role evidence. Profile digests in such bundles are dropped or keyed (ADR 0006).
   - **Consent for benchmarks (P-44, user decision):** in a `benchmark` export, every human-subject payload must also have `consent.status=obtained`. `not_obtained` blocks it even when it is redacted or sealed (voice redaction is not reliable, and benchmarks are published widely). `unknown` is treated as not obtained for benchmark purposes until consent is recorded. For a `shared_export`, sealing or redaction remains sufficient whatever the consent status.
   - Both rules apply to a payload according to its **export-time human-subject value** (Decision 7a), not directly to the stored marker.
   - **How the rule is checked (revision 22, P1-14; api-surface 25.4.2).** `ExportBundle{purpose, run_bundles, datasets, dataset_items, sealed_payloads, payload_redactions, provenance_redactions}` (`bundle.check_export_bundle`). A redaction is attached to its record by a `PayloadRedaction{subject_id, redaction: RedactionRecord}` entry (`subject_id` an artifact, transcript or tool call of the export, else `[redaction]`; entries for one subject add up). The payloads and what protects each, separately (I10; the map is `bundle.PAYLOAD_KIND_COVERS`): the audio of an artifact (every artifact counts as audio, B14) by a sealed `audio` payload or a redaction covering `audio`; the text of a transcript by a redaction covering `text`, or by a sealed `transcript_text` payload that replaced the transcript's turns (a transcript with no turn in the run bundle holds no text in the clear); the arguments of a tool call (present when `arguments_raw` or `arguments` is) by a redaction covering `tool_arguments` or a sealed `tool_arguments` payload that replaced both fields; its result (`result_raw`) likewise with `tool_result`. Missing protection is `[unprotected]`, missing benchmark consent `[consent]`, naming the record, never its content. A `ProvenanceRedaction` never counts. The export-time value is `export_human_subject(record.privacy, run, run_bundle.turns)` for an artifact or a transcript, and `derive_human_subject(run, run_bundle.turns)` for a tool call, which has no marker (Decision 4).
   - **Dataset items (B6).** An item that references an artifact or transcript of the export (`artifact_id`, `transcript_id`) and whose own export-time value is true (`export_human_subject(item.privacy, source_run, source_run_bundle.turns)` when its source run is in the export, else `true`) makes that payload human-subject too; never looser. In a benchmark such an item also needs `consent.status=obtained`.
   - **Benchmark consent of tool calls (B7).** A tool call has no marker, so in a benchmark the tool calls of a run whose derivation is true are covered by the consent of the run's human-subject artifacts and transcripts: at least one such record, and every one with `consent.status=obtained`; otherwise `[consent]`.
7a. **Precautionary markers at export time (user decision P-57, revision 6).** A marker set only as a precaution is re-derived at export time from the role evidence then available; the stored write-once record is never edited.
   - `export_human_subject(marker, run, turns) -> bool` (revision 11, N24: `turns` are the Turn records of the run's transcripts in the bundle being validated) is a pure function and the single entry point every export validator uses:
     - stored `human_subject=false` -> `false` (a stored `false` is valid only where the derivation is `false`, Decision 5);
     - stored `true` with reason `marked_before_role_evidence` -> `derive_human_subject(run, turns)` computed over the role evidence available at export time, meaning the run's transcripts and channel maps present in the bundle being validated; evidence outside the bundle does not count, so a bundle without role evidence keeps the payload human-subject;
     - stored `true` with reason `real_person_likeness` or `manual` -> `true`, always;
     - stored `true` without a reason (the derivation was `true` when it was written) -> `true`.
   - **Implemented (revision 22):** `privacy.export_human_subject(marker, run, turns) -> bool`, exactly these three parameters with no default; `turns=None`, a `str`, `bytes` or a missing argument is a `TypeError` whatever the marker says; `()` and `[]` mean no turn evidence.
   - **The stored record is unchanged.** Re-derivation happens only inside export validation; the Artifact, Transcript or DatasetItem, its marker, reason and consent record are not edited, so its digest and the write-once rule (ADR 0009) are unaffected.
   - **Human-caller recordings are unaffected:** `caller_origin=human` always derives `true`, so a precautionary marker on such a run stays `true`, and P-44 and the seal-or-redaction rule apply in full. A DatasetItem with a recording and no source run has no role evidence and stays `true`.
   - **Simulated runs whose evidence shows no human** (`caller_origin=simulated`, role evidence present in the bundle, every role `caller`, `agent` or a `mixed` channel) are treated as non-human at export.
   - **Consent for such payloads is not applicable (interaction with P-44 and P-46).** P-46 is unchanged for the stored record: a stored `true` marker carries consent and retention, and for a simulator the only truthful consent status is `unknown`. When the export-time value is `false`, the benchmark consent rule (P-44) and the seal-or-redaction rule do not apply to that payload, and its stored consent record is not consulted, so a simulated recording whose stored consent is `unknown` is not blocked from a benchmark. P-44 is unchanged for every payload whose export-time value is `true`: there `unknown` and `not_obtained` still block benchmarks.
8. **Channel map** declarations and inferences follow ADR 0012. `agent_channel_unknown` makes agent-audio metrics not_applicable.
9. **`DatasetItem.source_run_id` in exports (revision 12, O7 decided by the owner, option A).** An export treats `source_run_id` as an **unresolved reference**: export validation never requires the named run to be in the bundle, never fills or rewrites the field, and never uses evidence from outside the bundle. For the item's export-time human-subject value (Decision 7a), the role evidence is that of the source run and its turns only when both are in the bundle; otherwise the item has no role evidence and its payload stays human-subject. The field is kept only where the export policy allows. **Which purposes keep it (revision 13, O9 decided by the owner, option A):**
   - `internal` exports keep it, resolved or not.
   - `shared_export` and `benchmark` exports keep it only when the run it names is in the same bundle. Otherwise the export builder omits it from the exported copy and records the omission as a redaction. The stored item is not edited.
   - Reason: an unresolved run ID gives the recipient nothing it can check, while a UUIDv7 reveals its creation time and lets a recipient correlate items with the producer's internal runs. Omitting it only makes the item's export-time derivation stricter (no role evidence, so `true`), never looser.
   - **The recorded redaction** (detail fixed while applying O9; api-surface 22.12 item D2). The entry names the DatasetItem ID, the field `source_run_id` and the reason `unresolved_reference`, never the omitted run ID, and it is serialized in the ExportBundle. It is not a payload `RedactionRecord` (those assert that a tool redacted audio, text or tool-argument content), so it never satisfies the seal-or-redaction rule of Decision 7 for a human-subject payload. Export validation rejects a `shared_export` or `benchmark` bundle that still carries an unresolved `source_run_id`, naming the item ID and not the run ID, and rejects an omission entry whose item is absent or still carries the field. P1-14 pins the shape. Whether it is a new `RedactionRecord` form or a separate value object is decided there; if that choice would change an accepted decision, it goes to the owner first. **Shape (revision 22, P1-14; api-surface 25.2.2):** a separate value object `ProvenanceRedaction{item_id: DatasetItemId, field: "source_run_id", reason: "unresolved_reference"}` (closed sets of one member each) in `ExportBundle.provenance_redactions`; not a `RedactionRecord` and without `covers`. Export validation, at every purpose: an entry whose item is not in the export, whose item still carries the field, or a second entry for one item is `[provenance_redaction]`. In a `shared_export` or `benchmark`, an item that keeps a `source_run_id` naming no run bundle of the export is `[source_run]` (naming the item, never the run). The function that builds the exported copy is the export builder (deferred, B19). **B13 (revision 22):** an item with a payload whose stored marker is `false` and whose source run is outside the export cannot simply lose the field, because `DatasetItem` rejects a payload without a source run and with a `false` marker; the export builder must also set a human-subject marker (for example `true` with `marked_before_role_evidence`); until the builder exists such an item cannot enter a shared export, which is the safe failure.

## Rejected alternatives
- **A free-form speaker string.** Metrics could not reliably select the agent. Diarization labels such as `SPEAKER_01` are not roles.
- **Two roles only (caller/agent).** Undiarized speech would have to be assigned to one of them, which is a guess (ADR 0018), and an unidentified real person would vanish from the human-subject derivation.
- **A default `caller_origin=simulated`.** A recording of a real person ingested without the field would silently lose its privacy obligations. Required, with no default, forces the decision.
- **Infer caller_origin from mode.** Recorded runs can be either (a replay of our own simulated call, or a real call).
- **Trigger the export rule only on `caller_origin=human` (revision 2).** A simulated run whose recording contains an unidentified speaker could carry a real person's voice into a benchmark unprotected (user decision 1).
- **A user-set `human_subject` flag.** Forgetting it, or setting it wrongly, would silently remove the protection. Deriving it and rejecting markers looser than the derivation keeps it trustworthy, while P-47 still lets a person protect more.
- **Strict equality between stored and derived markers (revision 3).** Real-person data invisible in roles could not be protected, and written-once artifacts stored before role evidence would become invalid later.
- **Default to "not human" when roles are unknown.** It turns missing evidence into a privacy claim, the same fabrication pattern the core rule forbids for metrics.
- **Consent as a boolean.** "We do not know" is the common real state for third-party recordings and must not read as "obtained".
- **Redaction or sealing as enough for benchmarks without consent.** Voice identifies a person, so redaction of audio is not reliable, and a benchmark is published to people the data subject never dealt with.
- **Ban human-subject data from all exports.** Legitimate research sharing (with sealing or redaction) would become impossible, and people would export by hand without the safeguards.
- **Automatic redaction in the schema.** Redaction needs NLP/ASR tooling (Phase 3). The schema records that redaction happened and what it covered. It does not perform it.

## Consequences
- Importers must set `caller_origin`. If an importer cannot know it, the import fails with a clear message rather than guessing.
- Adding a transcript or channel map to a run can change its derived marker in either direction. A newly found `unknown` turn flips it to `true`; stored markers that say `false` are then too loose and must be replaced by new records. The first role evidence showing only caller and agent on a simulated run flips it from the "no evidence" default `true` to `false`; stored `true` markers stay valid because they carry `marked_before_role_evidence`.
- Simulated runs without any transcript or channel map are human-subject until role evidence exists, so they cannot be shared unsealed. That is the intended conservative default. Once role evidence in the exported bundle rules a human out, their precautionary markers (`marked_before_role_evidence`) evaluate to `false` at export time (Decision 7a, P-57), so they can enter benchmarks without seal, redaction or consent.
- Export validation needs the role evidence in the bundle. A producer that wants a simulated recording in a benchmark exports it together with the transcript or channel map that shows only the simulator and the agent.
- `RedactionRecord` is an assertion by a tool. The schema cannot verify that redaction was correct. `tool_ref` makes it auditable.
- Retention enforcement (deletion on expiry) is a Phase 2+ storage job. The schema carries the policy.
