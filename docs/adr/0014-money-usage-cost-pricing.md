## Context
Users compare voice stacks by quality *and* cost, and the framework reports cost in two domains: what our evaluation spent (judge, our STT, the simulated caller), and what the agent under test spent. The user's rule: "you cannot just extrapolate or assume." A cost is either reported by someone who knows it, or computed from known billable usage and a known price including billing rules. Anything else is `not_available`, never 0. Floats cannot represent prices such as 0.15 USD per 1M tokens exactly. Providers bill with rounding increments and minimum charges that change the result.

## Decision
### Money
1. **`Money{amount: DecimalString, currency: SupportedCurrency}`** is a value object (no ID). `DecimalString` is canonical: no exponent, no trailing fractional zeros, no trailing `.`, no `-0`, no leading `+`, scale <= 18, never NaN or Infinity. JSON numbers and Python floats are rejected. **Canonical input only (revision 7):** the type validates and never rewrites. A non-canonical spelling of a valid number (`"1.50"`, `"2.0"`, `"0.0"`) is rejected with a message that names the input and its canonical spelling (`decimal "1.50" is not in canonical form; write "1.5"`). The accepted set is exactly the JSON Schema pattern `^(?:0|-?[1-9][0-9]*|-?(?:0|[1-9][0-9]*)\.[0-9]{0,17}[1-9])$` (matched as a full match in Python, so a trailing newline is not accepted). Pydantic and JSON Schema therefore agree on every input (`test_invalid_rejected_by_both` needs no `KNOWN_SCHEMA_GAPS` entry). Results of our own arithmetic (`Money + Money`, `compute_cost()`) are produced in canonical form. The `currency` field is kept (not implied) so that the wire format, the digests and the Phase 2 `char(3)` column do not change shape when a currency is added.
1a. **Importers normalize decimal lexemes (revision 7).** A source number that is a valid decimal in another spelling (`"12.50"`, a JSON number lexeme `1.0` read as text) is converted to the canonical spelling by the importer, never by the type, with an IngestWarning `decimal_normalized` whose `raw` holds the lexeme as sent. Only lexical normalization is allowed (trailing zeros, trailing point); exponents, separators and anything that would change or round the value are not normalized. Such a value is not a `DecimalString` and stays raw (for example in `ReportedCostRaw.amount_raw`, which is never parsed). **Revision 15 (N59 decided by the owner, option A):** a reported amount that is not a valid decimal after this lexical normalization (for example `"1e3"`, `"1,000"`, `"abc"`, an empty text) or that is negative gets its own reason: the cost is `not_available` with `na_reason=amount_unparseable`, `reported_raw` keeps the amount and the currency label verbatim, and the importer records an ingest warning `amount_unparseable` whose `raw` is the lexeme as sent. There is no lenient parsing (no exponent, separator, sign or white-space handling beyond 1a) and the import as a whole is never rejected. Before revision 15 such an amount had no valid record (Decision 12 allowed `reported_raw` only with the two currency reasons), which was the contradiction qa found.
2. **`SupportedCurrency` (revision 4 user decision: USD only).** A closed set defined as data, not as a hard-coded enum: the vendored file `supported_currencies.json` lists the codes, and both the pydantic validator and the generated JSON Schema `enum` are built from it. **File shape (revision 6, matching the file dev created in P1-03b):** a JSON object `{"_meta": {...}, "currencies": [...]}`; the code list is the value of the key `currencies`, and `_meta` holds sources, retrieval date and the verification note like every vendored data file. In 0.0.1 the body is `{"_meta": {...}, "currencies": ["USD"]}`, so the `currencies` list is exactly `["USD"]`. Loaders read only `currencies`; a file without that key, or whose `currencies` is not a non-empty list of unique strings, is a packaging error. Every listed code must exist in the vendored ISO 4217 List One (`iso4217_active.json`). The JSON Schema is `{"type": "string", "enum": [<codes>]}`, never `const`, even with one code; the validator and the `enum` are built from the same tuple (ADR 0003 Decision 6; revision 7). Any other value is rejected, including lowercase `usd`, every other ISO 4217 code (for example `EUR`, `INR`, `XAF`), fund codes (`BOV`, `CLF`), X-codes (`XXX`, `XAU`) and non-ISO strings (`ABC`). Fund and X-codes need no rule of their own: they are rejected because they are not USD.
3. **Role of the ISO 4217 data file.** `iso4217_active.json` stays vendored and complete (all List One rows, with their `is_fund`/`is_x_code` flags as in the source). It is used only to recognise and name a non-USD code: in the validation error for a rejected `Money` validated on its own or inside a model that does not hide its input (for example "currency INR (Indian Rupee) is not supported in 0.0.1; only USD"), in the ingest warning for a reported non-USD cost, and to tell a known ISO code from an unknown string ("ABC is not an ISO 4217 code"). It never widens what `Money` accepts. **Revision 16 (N62 decided by the owner, option A):** inside a model that hides its input (ADR 0007 Decision 8), in particular `PriceEntry`, `PricingCatalog` and `CostRecord`, the error gives the location and the rule ("not supported in 0.0.1; only USD") and names neither the rejected code nor its ISO name (ADR 0007 Decision 8 (c), N42).
4. **No FX, single currency arithmetic.** There is no FX conversion. Because every `Money` is USD, addition needs no currency check and there is no `CurrencyMismatch` error in 0.0.1. Addition is exact `Decimal` addition.
5. **Adding a currency later.** For `Money` alone, adding a code to `supported_currencies.json` is the addition of a closed-set member, which ADR 0003 Decision 4 classes as additive. The cost model as a whole is not additive, though: `CostSummary.total` is a single amount and there is no FX, so a second currency forces a reshaped `CostSummary` (per-currency totals or an FX policy) and a mixed-currency guard on addition (Decision 16). **Classification: breaking.** During 0.0.x this changes nothing for readers (every release bumps the patch and requires an exact version match, ADR 0008 Decisions 2 and 4); the CHANGELOG records it as breaking with a migration note. From 0.1.0 the bump follows P-22. **Recommendation: treat adding any currency as a breaking change and ship it together with the CostSummary change and the mixed-currency guard in one release; never add a currency as a data-only change**, because the data file would then admit a `Money` that `CostSummary` cannot total. Which ISO codes may be added (the literal-versus-narrow X-code question of former P-41) is decided at that time.
6. Display rounding is a presentation function and never changes the stored amount. **Mode (revision 7):** `Money.display(places)` rounds half-even (the mode of P-35 and of the ADR 0013 display) and always shows exactly `places` fractional digits.
7. Storage (Phase 2): `NUMERIC` for amounts, `char(3)` for currency (always `USD` in 0.0.1). **Sign rules (P-38):** `Money` may be negative in general (credits, refunds are real ledger entries for later phases), while `PriceEntry.price`, `BillingRules.minimum` and `CostRecord.amount` must be >= 0, because a negative computed cost is always a bug. **Revision 16 (N45 (a) decided by the owner):** no usage quantity is negative, in any unit (token, character and request counts are integers >= 0, seconds are a `DecimalString` >= 0).

### Usage
8. **`UsageRecord`** (entity `use`): `{run_id, domain, stage, provider, model, provider_call_ref?, occurred_at?, quantities[{unit, count}], source, raw?}`.
   - **`occurred_at: UtcDatetime?` (revision 15, N43 decided by the owner, option A):** the instant of the billable event as the source reports it, or, for `source=measured`, as our runner records the call it made. It is absent when the source does not state it, and it is never filled with the ingest time, the run's start, "now" or a time derived from a file name. It is the first choice of the price date (Decision 15). An instant whose meaning the source does not state (request start, response end or log time) is still the event's reported time; the price date needs a day-level instant, not a latency.
   - `domain ∈ {evaluation, agent_under_test}`
   - `stage ∈ {stt, llm, tts, judge, sim_caller_llm, sim_caller_tts, realtime, other}`
   - `source ∈ {provider_reported, telemetry, measured}`, where `measured` means directly observed by us in a call **we** made. **`agent_under_test` usage with `source=measured` is rejected (P-39):** we never make the agent's billable calls, so we cannot measure its billable usage, and accepting such a record would reopen the path to estimating agent cost from recording length.
9. **Units are disjoint buckets:** `input_tokens` (uncached only), `cache_read_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `audio_input_seconds`, `audio_output_seconds`, `input_characters`, `requests`. Token, character and request counts are integers >= 0. Seconds are a DecimalString >= 0 (revision 16, N45 (a): a negative quantity is rejected in every unit, error at `count`). `raw` keeps the source payload verbatim.
   - **`quantities` (revision 16, N44 decided by the owner, option A):** non-empty, and exactly one quantity per unit (error at `quantities`). The type never sums repeated quantities of one unit: an importer that meets them either merges them before building the record or maps them to distinct units; it never relies on the schema to add them. **Revision 17 (N64 decided, auto-approved, option A):** an importer merges two or more quantities of one unit into one (their exact sum) only when the source payload, or its published API contract cited in the mapping's field-provenance table with URL and `retrieved_at` (as for P-53), states that they are parts of one billable event. Quantities of separate billable events go into separate usage records, one per call. Otherwise the importer records a mapping gap (ADR 0018 Decision 3a) and never sums, never keeps one count and drops the other: increment and minimum apply per usage record and unit (Decision 13b), so a merge can change the bill. **Revision 18 (N76 decided, auto-approved):** when the quantities cannot be merged the mapping builds no usage record for that call, records the IngestWarning `usage_quantities_not_merged` and a blocking gap-register row (ADR 0018 Decision 3a). An empty list is rejected because "no usage" is already expressed by the absence of a usage record (`no_usage`, `usage_not_reported`).
   - **Zero (revision 16, N45 (b)):** a count of 0 (or seconds `"0"`) is accepted. It is known usage of exactly nothing, not a missing value, and it costs exactly 0 (Decision 15).

### Pricing
10. **`PricingCatalog`** (entity `pcat`; versioned, digested, ADR 0009): `{id, version, entries, published_at}`.
   - **Revision 15 (N47 decided by the owner, option A):** `entries` is a non-empty list of `PriceEntry` value objects (Decision 11). An empty list is rejected at `entries` (a catalog that prices nothing has no use, and "no price" is already expressed by the absence of an entry). The catalog's `content_digest` uses the generic domain (ADR 0006 Decision 5) over the catalog document, so it covers every field of every entry; entries carry no `schema_version`, `created_at` or `metadata` of their own, so no nested exclusion is needed and the digest depends only on what the catalog version states about prices, billing rules, conditions, validity and provenance.
   - **Rules at `entries`:** each `entry_key` (revision 16, N61) appears at most once in a catalog; overlapping effective ranges under one key are rejected (Decision 11); entries under different keys that can match the same usage (one entry's `model` is another's alias, two entries share an alias, or two condition sets can both hold) are accepted by the catalog, and the resolver answers `ambiguous_price` when it meets them (Decision 15).
   - **Hides its input (revision 16, N62 decided by the owner, option A):** `PricingCatalog` sets `hide_input_in_errors=True`, because its validation reaches `PriceProvenance.url`, a credential-checked field (ADR 0007 Decision 8 (a)).
10a. **Catalog succession (revision 16, N47 remainder decided by the owner, option A).** P-24 is checked by the pure function `pricing.check_catalog_succession(previous, next) -> None`, which takes two `PricingCatalog` versions and raises `ValueError` (message containing "entry" and naming the `entry_key`, never a provenance URL) when (a) an `entry_key` of `previous` appears in `next` with different content, or (b) an entry of `next` has the same content as an entry of `previous` under a different `entry_key`. A key that disappears, and a new key with new content, are accepted. The function does no I/O and changes neither argument. Enforcement at a catalog publication step is later work (no publish step exists in Phase 1); until then the function is the tested statement of P-24. **Revision 17 (N65 decided, auto-approved, as recommended):** the content compared is every entry field except `entry_key`, `provenance` and `effective_to` (so `provider`, `model`, `aliases`, `unit`, `unit_quantity`, `price`, `billing`, `effective_from`, `applies_when`, `price_source`). A key therefore survives a re-checked price page and the closing of its range, which is what P-24 is for; provenance stays covered by the catalog digest (D4). The two catalogs must have the same `id` and `next.version` must be later than `previous.version` (not necessarily the next integer); otherwise the function raises `ValueError` before comparing entries, with a message containing "catalog" or "version" (detail D18). **Revision 18 (N72 decided, auto-approved, option A):** `applies_when` and `aliases` are compared as sets (their order carries no meaning, as in the overlap key), so reordering keeps the key; `aliases` holds no value twice and never the entry's own `model` (error at `aliases`, Decision 11).
11. **`PriceEntry`** (value object, revision 15; until revision 14 an entity with prefix `pce`, which is withdrawn and not reserved, ADR 0001 Decision 4 as corrected in revision 18): `{entry_key: MachineKey, provider, model (exact match; aliases[]), unit, unit_quantity, price: Money, billing, effective_from, effective_to?, applies_when?, price_source: catalog|user_supplied, provenance: PriceProvenance{kind, url?, retrieved_at, note?}}`.
   - **Value object (revision 15, N47 decided by the owner, option A).** A `PriceEntry` exists only inside one `PricingCatalog` version and has no `id`, `schema_version`, `created_at`, `metadata` or `metadata_flags` of its own (ADR 0001 Decision 8). It keeps a **stable entry key**, unique within its catalog and kept across catalog versions while the entry is unchanged (P-24, ADR 0009 Decision 5, checked by Decision 10a); `CostRecord.pricing_snapshot` names entries by it.
   - **`entry_key` (revision 16, N61 decided by the owner, option B).** The identifier is `entry_key: MachineKey`, assigned by the catalog author and unique within one catalog version. It is a key scoped by the catalog reference `(catalog_id, version)`, not a global identity: it is meaningful only together with that reference. It is not a `*_id` field, so the opaque-ID allowlist and principle of ADR 0001 I12 are unchanged, and tracer mints nothing for it. Rejected: `entry_id` on the opaque allowlist (option A, bends the I12 principle the gate checks) and a tracer-minted prefixed ID in a second registry (option C, brings back what N47 removed).
   - **Hides its input (revision 16, N62 decided by the owner, option A):** `PriceEntry` and `PriceProvenance` set `hide_input_in_errors=True` (ADR 0007 Decision 8 (a), closed under embedding), so a rejected provenance URL is never echoed; the non-USD price message inside them names the rule, not the code (Decision 3). This replaces the N60 statement that `PricingCatalog` and `PriceEntry` do not hide.
   - **Effective range (revision 15, N48 decided by the owner, option A):** half-open `[effective_from, effective_to)`; `effective_to` is optional (open-ended) and, when present, strictly later than `effective_from` (error at `effective_to`). Adjacent ranges (one ends where the next starts) do not overlap; a gap between ranges is allowed.
   - **`applies_when` values (revision 15, N49 accepted):** typed per kind: `context_tokens_gt` and `context_tokens_le` take a strict integer >= 0, `batch` a strict boolean, `region` a `MachineKey` compared exactly. The overlap key is `(provider, model, unit, applies_when)` with `applies_when` compared as a set, so the order of the conditions carries no meaning. **Revision 16 (N49 remainder decided by the owner, accepted as recommended):** (a) an empty list `[]` is rejected at `applies_when`; an unconditional entry omits the field, so one entry has one spelling and one digest; (b) a kind may appear at most once in one entry (error at `applies_when`); a band is `context_tokens_gt` plus `context_tokens_le`, and several regions are several entries; (c) conditions combine as all-must-hold: an entry applies only if every condition holds, so one condition known to be false removes the entry even when another condition is undecidable (deduction, not a guess), and an entry with no false condition and at least one undecidable condition is undecidable (`ambiguous_price`, Decision 15).
   - **`provenance.url` (revision 15, N50 decided by the owner, option A):** runs the URL credential rules of ADR 0007: userinfo is rejected (Decision 6), a query parameter whose name is one of the 25 credential names is rejected (Decisions 6a and 6b, the same decoding, folding and `-`/`_` comparison), and a Decision 5a credential pattern anywhere in the URL, as written or percent-decoded once, is rejected (Decision 6b). The error says which rule failed and in which URL part, never the value. **Revision 16 (N50 remainder decided by the owner, accepted as recommended; ADR 0007 Decision 6e):** (a) `provenance.url` is an absolute URI with the lowercase scheme `http` or `https` and a host, ASCII only, without white space or control characters, as in ADR 0007 Decision 6a; unlike endpoint and artifact URIs, a fragment is allowed (price pages use anchors), and the credential patterns are searched in it too; (b) `provenance.kind` is an open `MachineKey` naming the kind of source document (ADR 0003 Decision 2); (c) `provenance.note` is required when `price_source=user_supplied` (error at `provenance`/`note`), because the note is where the user states the source of the price and, for a converted price, the rate and date applied; it stays optional for catalog entries. **Revision 17 (N66 decided, auto-approved; ADR 0007 Decision 6e):** (a) the credential parameter names of ADR 0007 Decision 6b are also checked in the fragment (split at `&` and `;`, the same decoding, folding and `-`/`_` rule as in the query); (b) a loopback host by ADR 0007 Decision 6d is rejected in `provenance.url` on the record itself (error at `provenance`/`url`), because a price source is a public page; private, link-local and unspecified addresses stay accepted; (c) a present `note` that is empty or white space only is rejected at `provenance`/`note`, for catalog and user-supplied entries alike (detail D17). **Revision 18 (N70, N71 decided, auto-approved; qa findings 2 to 4):** a fragment piece without `=` is a name, as in the query (`#token` and `#a=1&key` rejected; `#tokens=1`, `#token-pricing`, `#access_token_ttl=5` accepted); "white space only" is `str.isspace()` (U+00A0 and U+3000 count, U+200B and U+FEFF do not); the errors name the URL part (`userinfo`, `query`, `path`, `fragment`) or the rule (`loopback host`), never a part of the URL (ADR 0007 Decision 6e). `aliases` (N72): distinct, and never the entry's own `model`. **N62 (revision 16, decided by the owner, option A):** the three pricing models hide their input (above).
   - **Prices are USD (revision 4).** `price` and `billing.minimum` are `Money`, so a non-USD price is a validation error. This applies equally to catalog entries and user-supplied prices (`price_source=user_supplied`): configured prices are inputs we control, so they are rejected rather than mapped to `not_available`. The error states the rule at the field's location; because `PriceEntry` and `PricingCatalog` hide their input (revision 16, N62), it does not name the rejected code or its ISO name there, while `Money` validated on its own still names it from the ISO 4217 data file (Decision 3). The framework does not convert. A provider that bills in another currency can only be priced through a USD `user_supplied` entry whose `provenance.note` states the rate and date the user applied; the resulting cost is `basis=computed` in USD at the user's rate, which may differ from the provider's bill, and the provenance makes that visible. The catalog shipped with the framework contains no converted prices.
   - **`billing` is required (accepted in revision 3)** and is either the literal `"unknown"` or `BillingRules{increment, minimum}` where **each part is required** and is either a value or the literal `"none"`:
     - `increment`: a positive DecimalString quantity in the entry's `unit`, or `"none"` (billed exactly).
     - `minimum`: a `Money` (USD; minimum charge per billable event), or `"none"`.
     An absent part is a validation error, so "no minimum" (`"none"`) and "we don't know" (`billing: "unknown"`) can never be confused.
   - Overlapping effective ranges under one `(provider, model, unit, applies_when)` key are rejected (A-25; the message contains "overlap"; revision 15: half-open ranges, `applies_when` compared as a set). Different keys that can match one usage are not overlaps (Decision 10).
   - An explicit price of 0 is allowed (it is a known price).
   - Provenance is required. A user-supplied price is marked `price_source=user_supplied` and carries `provenance.note` (revision 16, N50 remainder).
   - **`applies_when` (P-37)** is a list of typed conditions from a closed set (`AppliesWhenCondition{kind: context_tokens_gt|context_tokens_le|batch|region, value}`), so tiered prices (long context, batch) can be catalogued and evaluated deterministically. A condition the resolver cannot evaluate from known usage gives `ambiguous_price`. (Revision 15, N46: the facts a condition reads are passed by the caller as `PriceFacts`, Decision 15.)

### Cost
12. **`CostRecord`** (entity `cst`): `{domain, usage_record_ids, status, amount?, basis?, reported_by?, pricing_snapshot?, rounding?, na_reason?, unpriced_units[], reported_raw?}`:
    - **`basis` is present if and only if `status=available` (accepted in revision 3).**
    - `status=available`: `amount` (USD) and `basis` are required.
    - `basis=reported`: `reported_by ∈ {provider, telemetry_platform}` is required. Revision 15 (N51 accepted): a reported record has no `pricing_snapshot` and no `rounding`.
    - `basis=computed`: `pricing_snapshot{catalog_id, version, content_digest: ContentDigest, entry_keys: MachineKey[]}` is required (revision 15: the entries are named by their key, N47; revision 16, N61 option B: the field is `entry_keys`, keys scoped by the snapshot's `(catalog_id, version)`; until revision 14 `entry_ids` held `pce_` IDs, and `entry_ids` is now an unknown field and rejected). Revision 15 (N51 accepted): a computed record has no `reported_by`; `entry_keys` is non-empty and distinct; `rounding` appears only on an available computed record.
    - **`usage_record_ids` (revision 16, N51 remainder decided by the owner, accepted as recommended):** (a) an available record with `basis=reported` may have an empty list (a source that reports a cost without usage); an available `computed` record needs at least one usage record (error at `usage_record_ids`). 13. **`computed` requires both:**
    - (a) known usage of the actual billable event, either provider/telemetry-reported or measured by us in a call we made;
    - (b) a known price whose `billing` is a `BillingRules` value (not `"unknown"`).

    Otherwise the cost is `not_available`. A matching entry with `billing: "unknown"` gives `billing_rules_missing`. If any unit in the usage is unpriced, the whole record is `not_available` (`unit_unpriced`) and lists `unpriced_units`. A partial sum is never reported.
13a. **Which reason when causes mix (revision 15, N54 decided by the owner).** `compute_cost` resolves every quantity of every usage record on its own (Decision 15), each to a priced entry, `no_price_for_model` or `ambiguous_price`, and then gives the first reason that applies, in this order, and only that one:
    1. no usage record at all: `usage_not_reported` for `agent_under_test`, `no_usage` for `evaluation`;
    2. `no_price_for_model`: every quantity resolved to `no_price_for_model` (nothing in the catalog prices this usage, including a model that has entries only for other units, or only at other dates; detail D11);
    3. `billing_rules_missing`: some quantity resolved to an entry whose `billing` is `"unknown"`;
    4. `unit_unpriced`: some quantities, but not all, resolved to `no_price_for_model`; they are listed in `unpriced_units`;
    5. `ambiguous_price`: some quantity resolved to `ambiguous_price` (several entries, an undecidable condition, or no price date).
    This order differs from the one qa's oracle used (ambiguous first). `unpriced_units` is filled only with reason 4.
13b. **Billable event (revision 15, N55 accepted).** A billable event is one quantity: one usage record and one unit. The increment and the minimum apply to each such quantity, never to the sum of several usage records.

Not-available records (including `unsupported_currency`) are excluded and listed with their `na_reason`. `none` iff nothing is included, and **`total` is present if and only if at least one record is included**: a summary with nothing included has no total, never a total of `"0"`, which would read as "free". **Completeness (P-40, refined for covered exclusions in revision 6, Decision 16a):** `complete` iff at least one record is included and no exclusion is uncovered; `none` iff nothing is included; `partial` otherwise. With no covered exclusions this is exactly the P-40 rule ("nothing excluded and something included").
16a. **One usage, at most one included cost (user decision P-54, revision 6).**
    - **Invariant:** within one CostSummary, each UsageRecord ID appears in the `usage_record_ids` of at most one included CostRecord. A summary that includes two records sharing a usage is rejected.
    - **Precedence between a reported and a computed record for the same usage:** an available reported record (USD) is included, and the computed record is excluded with reason `duplicate_of_reported`. If the reported record is not available, in particular `unsupported_currency` because the provider's own figure is in another currency, the computed USD record is the included one, and the excluded reported record names it (`covered_by`), so a reader sees that the provider's own figure exists in another currency and that the total uses our computed figure at the stated USD price. The same applies to a reported record that is `currency_not_reported`.
    - **`CostExclusion{ref: cst_ID, reason, covered_by: cst_ID[]}`** (value object). `reason` is the excluded record's `na_reason`, or `duplicate_of_reported` for an available computed record set aside in favour of an available reported one, or (revision 15, Decision 16b) `overlaps_reported` for an available computed record that only partly overlaps included reported records. `covered_by` lists the included records of the same summary that cover the excluded record's usage; it is non-empty iff every UsageRecord of the excluded record is covered by included records, and every listed record must be included in the same summary and share at least one UsageRecord with the excluded one. `duplicate_of_reported` requires a non-empty `covered_by` that names the included reported record. **Revision 20 (N78 decided, auto-approved, option A):** `covered_by` names each record at most once, whatever the reason; a repeated ID is rejected at `covered_by` (inside a `CostSummary` the error is located under `excluded`), and the JSON Schema states it as `uniqueItems`. The order of distinct IDs is kept and never checked (Decision 16b).
    - **Covered exclusions and completeness (detail fixed while applying P-54):** an exclusion with a non-empty `covered_by` does not count against completeness, because its usage is already in the total. Without this, the case P-54 targets (a reported non-USD figure plus the included computed USD figure) would always read `partial` although no usage is missing from the total. An exclusion that is only partly covered (some of its usage is in no included record) is uncovered, so the summary is `partial`; a partial sum is never reported for it.
    - The schema has no tie-break between two records of the same basis for one usage (two computed or two reported records): a producer emits one; including both is rejected by the invariant.
    - Worked example (golden): UsageRecord `u1`; record A reported `"1000"` with currency label `INR` (not_available, `unsupported_currency`, `reported_raw` verbatim); record B computed `"12.5"` USD from a USD catalog entry. Summary: `included=[B]`, `total="12.5"`, `excluded=[{ref: A, reason: unsupported_currency, covered_by: [B]}]`, `completeness=complete`.

The P1-14 bundle maps a snapshot to a `PricingCatalogRef` (`catalog_id` as `id`, `version`, `content_digest`) for the bundle seam.
    - **Partial overlap (N53, option A):** an available computed record that shares some, but not all, of its usage records with included available reported records is excluded as a whole (its amount is never split between covered and uncovered usage), with the reason `overlaps_reported` (detail D8, accepted by the owner in revision 16) and an empty `covered_by`; because the exclusion is uncovered, the summary is `partial`. Reported records stay preferred over computed ones (P-54). `CostExclusion.reason` therefore gains `overlaps_reported`, valid only for an available computed record that shares at least one, but not every, usage record with included reported records; `check_cost_summary` enforces it. Before revision 15 the oracle raised a `ValueError` for this case.
    - **No-usage records and order (revision 16, N53 remainder decided by the owner, accepted as recommended):** (a) a record without usage records is never covered: as an exclusion its `covered_by` is empty and it counts against completeness (vacuous coverage would let any included record "cover" it); as an included record it covers nothing. (b) `included` and `excluded` keep the order of the input records; `summarize_costs` never sorts, and `check_cost_summary` does not check the order of `included`, `excluded` or `covered_by`.

## Rejected alternatives
- **Float amounts.** `0.1 + 0.2 != 0.3`. Token prices such as 1.5e-7 cannot be represented exactly, and different languages disagree on float formatting, which breaks digests.
- **Integer minor units (cents/paise).** Per-token prices are far below one minor unit, so exactness would need an arbitrary sub-unit scale per currency.
- **JSON numbers holding decimals.** Most JSON parsers turn them into binary floats on read, so the exactness is lost before validation runs.
- **An `estimated` basis** (for example deriving agent STT cost from recording length). Removed by the user (OQ4): an estimate looks like a cost in totals, and providers bill differently (increments, VAD-trimmed audio, minimums).
- **Treat missing price or usage as 0.** A total of 0 would be presented as "free". It is fabrication, and it makes totals look complete.
- **Partial sums for partially priced usage.** An undercount presented as a total. Whole-record not_available plus a listed exclusion is honest.
- **Optional billing parts, absent meaning "per unit, no minimum".** That is an assumption about provider billing, and it makes "no minimum" and "unknown minimum" indistinguishable. Short audio calls are exactly where minimums and increments dominate.
- **A `basis` on not_available records.** It would claim the cost was computed or reported when it was neither.
- **Any ISO 4217 currency except funds and X-codes (revision 3 rule, superseded in revision 4).** Accepting many currencies without FX forces per-currency totals, mixed-currency errors and a currency-code policy (which X-codes are legal tender, P-41) before any user needs a second currency. USD only removes that whole class of errors for 0.0.1 and keeps the shape ready for later.
- **Dropping `currency` from `Money` (implicit USD).** Adding a currency later would then change the wire format, every digest of a priced entity and the storage schema, and readers of old files could not tell an implicit USD from a missing field.
- **Hard-coding `USD` as a `Literal` in the model.** The JSON Schema, the validator and the error messages would each need editing when a currency is added; a data-driven set keeps one source of truth.
- **Rejecting provider output with a non-USD cost.** It breaks ingestion on data we do not control (core rule). Mapping it to `not_available` with the raw values kept loses nothing and fabricates nothing.
- **Converting a reported non-USD cost at a fixed or looked-up rate.** A rate needs a source and a date, an external, time-varying assumption; the result would look like a reported USD cost but is neither reported nor computed.
- **Treating non-USD configured prices as `not_available` instead of rejecting them.** A configured price is our own input. Accepting it silently would make every cost that depends on it disappear from totals with no error at configuration time.
- **Dropping fund and X-code rows (or the whole ISO file) from the vendored data.** The file would no longer be a faithful copy of ISO 4217 List One, and error messages could not name a rejected code or tell a real currency from a typo.
- **FX conversion into one currency.** It needs a rate source and date, an external, time-varying assumption.
- **Fuzzy model matching** (`gpt-4o*`). A wrong price is worse than no price. Aliases must be explicit.
- **(Revision 15, N43) Usage times as a separate argument (`usage_times={usage_id: datetime}`).** The time is a fact about the usage event; kept outside the record, it is lost when the record is stored, exported or recomputed later, and two callers can price the same record at different dates.
- **(Revision 15, N47) `PriceEntry` as an embedded entity.** Each entry would carry `schema_version`, `created_at` and `metadata` inside the catalog's digest domain, so the catalog digest of one `(id, version)` would change across schema versions unless a nested exclusion were added; and the entries never live outside their catalog version.
- **(Revision 15, N59) Lenient amount parsing, or rejecting the whole import.** Reading `"1e3"` or `"1,000"` as a number guesses the source's notation; rejecting the import breaks on data we do not control (core rule).
- **(Revision 15, N53) Splitting a partly overlapping computed record.** Apportioning its amount to the uncovered usage needs per-usage amounts the record does not hold, so any split is an estimate.
- **(Revision 16, N61) `entry_id` on the opaque-ID allowlist, or a tracer-minted prefixed ID for entries.** The first widens the gate-checked I12 principle (opaque `*_id` fields hold values assigned outside tracer) to author keys; the second needs a second ID registry and brings back the identity N47 removed. A key named `entry_key` says what it is: a catalog-scoped key.
- **(Revision 16, N62) Keeping `PricingCatalog` and `PriceEntry` echoing input.** pydantic's default error text would show a rejected provenance URL, including a presigned signature, which ADR 0007 Decision 8 (a) exists to stop; hiding only `PriceProvenance` does not help, because the outermost model governs.
- **(Revision 16, N45 (b)) A minimum charge on a zero quantity.** It would bill an unused bucket (for example `cache_read_input_tokens: 0`) as if a billable event had happened in it.
- **(Revision 16, N59 remainder) `unsupported_currency` for a USD label against a non-USD contract.** It would state that USD is unsupported; `currency_conflict` names what happened.
- **(Revision 16, N47 remainder) P-24 as a documented convention only.** Reports comparing entry keys across versions could not trust that one key means one content.

## Consequences
- At T0, agent-under-test cost is mostly `not_available`, and CostSummary says so. That is the correct, honest output.
- A provider or telemetry platform that reports cost in another currency (for example an Indian provider reporting INR) produces `not_available` (`unsupported_currency`) costs in 0.0.1. The reported values are kept verbatim, so nothing is lost, but such costs are not totalled until a second currency is added (Decision 5).
- Providers that bill in another currency (relevant for an Indic-first framework, for example a provider that publishes prices only in INR; which target providers do so is not verified) have no shipped catalog price in 0.0.1. Their usage-based cost is `not_available` (`no_price_for_model`) unless the user supplies a converted USD price; the framework records the user's note on the conversion but does not verify it.
- Catalog maintenance (prices, billing rules, provenance with `retrieved_at`) is recurring data work. Stale catalogs are visible through provenance. An entry whose billing rules the author cannot confirm must say `"unknown"`, which surfaces as `billing_rules_missing` instead of a wrong amount.
- Whether `gen_ai.usage.input_tokens` includes cached tokens is not verified. Until it is, F1 mapping cannot split the buckets, and the cost is `not_available` rather than double-counted.

## Decided items (formerly [Proposed]; all decided by the user in revision 5)
- **P-35. Results beyond scale 18. Decided by the user (revision 5): accepted as recommended.** Decision: round half-even at scale 18 and record it on the record (`rounding{scale: 18, mode: half_even, exact: false}`). Reason: division by `unit_quantity` can produce non-terminating decimals (1 USD per 3 units), and `DecimalString` allows scale <= 18; an unrecorded rounding would make two exact-looking amounts differ silently. Had it been decided otherwise (for example reject as not_available): such costs disappear from totals; the test becomes `test_compute_scale_overflow_not_available`. Test (binding): `test_compute_scale_overflow_rounds_half_even_and_records`.
- **P-36. Which date selects the price. Decided by the user (revision 5): accepted as recommended.** Decision: the usage event's time if the source reports it, otherwise `Run.started_at`; if neither is known, `ambiguous_price`. Reason: prices change; using "now" would reprice old runs, and guessing a date is fabrication. Had it been decided otherwise (always `Run.started_at`): multi-day runs straddling a price change are priced at the start price. Test (binding): `test_price_resolution_uses_usage_time`; revision 6 adds the fallback tests of I28 and lists `Run.started_at` in the Run spec.
- **P-37. `applies_when` grammar. Decided by the user (revision 5): accepted as recommended.** Decision: a closed set of typed conditions in 0.0.1 (for example `context_tokens_gt`, `context_tokens_le`, `batch`, `region`); a condition the resolver cannot evaluate from known usage gives `ambiguous_price`. Reason: tiered prices (long context, batch) exist; a free-text condition cannot be evaluated deterministically. Had it been decided otherwise (no `applies_when` in 0.0.1): tiered prices cannot be catalogued, and such usage is `no_price_for_model`. Test (binding): `test_unevaluable_applies_when_ambiguous`.
- **P-38. Negative amounts. Decided by the user (revision 5): accepted as recommended.** Decision: `Money` allows negative values in general (credits, refunds), while `PriceEntry.price`, `BillingRules.minimum` and `CostRecord.amount` must be >= 0. Reason: a negative computed cost is always a bug, but a refund is a real ledger entry for later phases. Had it been decided otherwise (no negatives anywhere): `DecimalString` for Money gets a non-negative pattern; the test becomes `test_money_rejects_negative`. Test (binding): `test_cost_amount_nonnegative`.
- **P-39. `agent_under_test` usage with `source=measured`. Decided by the user (revision 5): accepted as recommended.** Decision: rejected. Reason: we never make the agent's billable calls, so we cannot measure its billable usage; accepting it would reopen the path to estimating agent cost from recording length. Had it been decided otherwise: such records are accepted but never used for computed cost, which leaves a misleading record in bundles. Test (binding): `test_agent_domain_measured_usage_rejected`.
- **P-40. Completeness boundary. Decided by the user (revision 5): accepted as recommended.** Decision: `complete` iff nothing is excluded and at least one record is included; `none` iff nothing is included; `partial` otherwise. Reason: a summary with nothing included must not read as complete. Had it been decided otherwise: the truth table in `test_completeness_rules` changes. - **P-41. Which X-codes are rejected. Decided (revision 4): obsolete.** The user decided that `Money` is USD only in 0.0.1, so no X-code or fund code can be a `Money` currency and no rule about them is needed. Decided by the user (revision 5): the importer normalizes case and whitespace variants (`usd`, ` USD `) to USD with an ingest warning and keeps the raw label; the `Money` type stays strict (exact `USD` only); `$` and `US$` are never mapped.** Folded into Decision 12a. Tests: `test_reported_currency_case_variant_normalized_with_warning`, `test_reported_currency_symbol_not_normalized`.
- **P-53. Reported cost with no currency. - **P-54. One usage, a reported non-USD cost and a computed USD cost. Decided by the user (revision 6): accepted.** Each usage counts in at most one included cost record; if the provider's own report is in another currency, the computed USD record is the included one and the excluded reported record names it. Folded into Decision 16a, together with the rest of the accepted proposal (an available reported USD record takes precedence over a computed one, which is excluded as `duplicate_of_reported`). Reason: the provider's own report is the best evidence when we can total it; when we cannot, a computed USD figure from a known price is legitimate (`computed` rule, Decision 13), but the reader must see both. Rejected alternative: when any reported record exists, never include a computed one for the same usage; simpler, but it drops a correctly computed cost. Representing "names it" needed a typed exclusion entry, `CostExclusion{ref, reason, covered_by[]}` (a list, because the usage of one excluded record may be covered by several included ones), and completeness had to ignore covered exclusions (Decision 16a); both are details fixed while applying the decision. Tests (binding): `test_usage_record_in_at_most_one_included_cost`, `test_reported_non_usd_and_computed_usd_same_usage_counted_once`, `test_available_reported_preferred_over_computed_duplicate`, `test_cost_exclusion_covered_by_names_included_records_only`, `test_completeness_ignores_covered_exclusions`.
