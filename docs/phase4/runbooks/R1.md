## 4. The commands

Placeholders: `$IN` inputs directory, `$OUT` the run output directory (the same directory for all repeats), `$ENVF` the git-ignored env file holding `SARVAM_API_KEY`, `$AUTH` the authorisation reference (1 to 200 characters; only its SHA-256 is stored).

```
tracer simulate --target $IN/target.json --allowlist $IN/allowlist.txt \
  --evaluator $IN/evaluator.json --persona $IN/persona.json --sim-profile $IN/sim_profile_r1.json \
  --tts sarvam --caller scripted --stt sarvam \
  --max-call-seconds 180 --max-tts-chars 20000 --max-llm-tokens 100000 --max-stt-seconds 600 \
  --authorisation-reference "$AUTH" --env-file $ENVF --out $OUT          # add --dry-run for the plan
```

The warm-up (step 3) is the same command with `--agent fake:$IN/fake_agent_warm.json --sim-profile $IN/sim_profile_warm.json --stt fake` in place of `--target`, `--allowlist`, `--sim-profile sim_profile_r1.json`, `--stt sarvam`, and a different `--out`.

The wrapper `r1.sh` (kept by the lead outside the repository, with `make_inputs.py`, `check_allowlist.py`, `audit_dryrun.py`) builds exactly these commands. Its default is a plan. `--rehearse`, `--warm` and `--go` exist; `--warm` and `--go` refuse unless `R1_GO=yes-owner-approved-2026-10-28` is set, and also need `R1_SPEAKER`, `R1_ENV_FILE`, `R1_AUTH_REF`. `--go --count N` makes N calls (N from 1 to 5), stops at the first non-zero exit code or when `$OUT/kill-switch` exists, and sleeps 5 s between calls.

## 5. Steps

1. **Plan (no key, no send).** `r1.sh`. It writes the inputs, parses the allowlist entry locally (`check_allowlist.py`), runs the two dry runs under an audit hook (zero network events, zero file writes, the env file never opened) and starts and stops the bot. A dry run does not read the allowlist, the lock or the kill-switch file (it returns before step 2), which is why the allowlist is checked by the script.
2. **Read the plan.** Expected R1 plan: `caller: scripted (8 lines)`, `tts: sarvam, 250 characters to synthesise in 8 requests, 0 cache hits`, `llm: none`, `stt: sarvam, planned after the call from the agent audio`, the four caps as in section 2, `dry run: nothing was sent`. No cost line is printed by a dry run; the cost of the real run is `not available (no_usage)` or `not available` because no USD price file is supplied (the owner decision of 2026-10-25: Sarvam INR rates are never converted).
3. **Warm-up: pre-synthesis (OWNER-GATED SPEND, real Sarvam TTS).** `R1_GO=... R1_SPEAKER=... R1_ENV_FILE=... R1_AUTH_REF=... r1.sh --warm`. Sends 8 text-to-speech requests of 250 characters in total (cap 20000) to Sarvam, with an offline fake agent, no socket. The cache `tts-cache` (entries 0600) is copied into `$OUT`. Run the R1 dry run again: it must now say `0 requests, 8 cache hits`; `--go` re-checks this and refuses otherwise. If the owner prefers no separate step, skip step 3: the first R1 call then synthesises the same 8 lines at step 7 of its own invocation, still before the connect (the same request count and characters).
4. **Rehearsal (no spend, optional).** `r1.sh --rehearse`: the same target and allowlist on loopback with fake TTS and fake speech-to-text, in its own output directory. Observed 2026-10-28: call established, `script_complete`, `caller turns: 8 started, 8 completed`, `agent segments: 8`, about 31 s long, `inbound_messages_ignored` 0, exit 3 (the replay speech-to-text has no recorded bodies: expected).
5. **Call 1.** `r1.sh --go --count 1`. Read section 6 and 8 before any further call.
6. **Calls 2 to 5.** `r1.sh --go --count 4` (the `min_call_interval_ms` of 3000 ms is checked from the start of the previous call; the script's 5 s sleep is on top of the call length).
7. **Hand-off.** Counts only into the P4-36 measurement report. Do not paste text, paths or the recording into chat.

## 6. What is logged, and how to verify no TTS request during the call (BL-369)

Before the call: stdout plan lines (counts); `sim_call_log.jsonl` gets one `before` and one `after` line per request (stage, index, attempt, bytes, characters or audio seconds, status, elapsed, request id) and never text. After the call: stdout summary lines (counts, end reason, usage per stage), and the `end` line of the call log with `counts` (`caller_turns_started`, `caller_turns_completed`, `agent_segments`, `tts_requests`, `tts_cache_hits`, `stt_requests`, `frames_sent`, `frames_received`, `inbound_messages_ignored`, `signals_received`).

Verification of the mitigation, from `$OUT/sim_call_log.jsonl`: the line number of the `connect` event is greater than the line number of every line with `"stage":"tts"`, and the `end` line has `tts_requests` 0 (after step 3) or 8 only for a run that skipped step 3. With a complete cache, no `"stage":"tts"` line is written at all (a hit sends nothing); `tts_cache_hits` is then 8.

## 7. The five repeats and the 3 s gap

One invocation is one call (`call.lock` in `$OUT`, mode 0600, record written before the connect). Repeats share `$OUT`, so the cache and the store are shared (each run is a separate row; a second run joins the same store). The minimum gap is the sim profile value 3000 ms: a start less than 3 s after the previous start is refused at step 2 (exit 4, `min_call_interval_not_elapsed`), before any key is read. Repeat 1 alone first (step 5), inspect, then 2 to 5. The call is 31 s long in the rehearsal, so the gap is met with a margin; the script also sleeps 5 s.

## 8. Stop conditions, exit codes, pass and fail of the RUN

Stop: create `$OUT/kill-switch` (`touch`; any entry of that name): a call in progress hangs up within one frame and ends `kill_switch` (stored, exit 0); a later start is refused (exit 4, `kill_switch_file_present`). The tool never removes the file; the operator does. Ctrl-C (SIGINT/SIGTERM) hangs up gracefully; a second signal aborts; the command prints `usage recovery: <path|not written>` and writes `usage-recovery-<UTC>.json` (mode 0600, class names and usage records only).

| Exit | Meaning |
|---|---|
| 0 | call established; every result scored or `not_applicable` |
| 1 | unexpected failure (a recovery file may exist) |
| 2 | a result not scored (status `error`), or the caller's language model failed (not used in R1) |
| 3 | speech-to-text failed (`stt_failed` warning) |
| 4 | input refused (before any key read or connect) |
| 5 | call not established |
| 64 | usage |

R1 passes (as a run, not as a verdict on any agent) when all hold: exit 0; `result: call established`; `end reason: script_complete`; `caller turns: 8 started, 8 completed`; `agent segments` at least 1; `tts_requests` 0 and `tts_cache_hits` 8 in the `end` line, and no `tts` log line after `connect`; `stt_requests` at least 1 (the number is recorded; the book does not predict it); usage recorded for the `tts` stage (step 3) and the `stt` stage (stdout `stt usage:` is not `none`); the end reason is not `transport_error`, `setup_failed`, `spend_cap` or `max_silence`; `ingest warnings: 0`; no `stt_failed`; `inbound_messages_ignored` 0; the store, recording and report exist; no key, authorisation text, path or line of text in any stdout, stderr or file other than the recording and the store. R1 fails on any exit other than 0, or any item above missing; a failure is reported with its counts and the exit code, then the next call waits for the lead. Unknown until the first real call: how Sarvam speech-to-text answers a sine tone (empty text, a warning or an error). An `stt_failed` on tones is a finding about the apparatus, not about Sarvam, and is logged, not worked around.
